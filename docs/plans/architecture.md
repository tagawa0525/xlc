# PWR 炉心解析コード 全体計画

## 目的

ENDF 形式の評価済み核データから出発し、PWR 炉心全体の解析までを自前で行うコード体系を作る。

## 全体構成

計算を3つの段階に分け、Cargo workspace の3クレートとして実装する。段階間はファイルでデータを受け渡す。

| クレート  | 入力                           | 出力                        | 相当する既存コード |
| --------- | ------------------------------ | --------------------------- | ------------------ |
| `xs`      | ENDF/B-VIII.0                  | 多群断面積ライブラリ        | NJOY               |
| `lattice` | 多群ライブラリ、集合体の仕様   | 少数群定数テーブル          | CASMO, DRAGON      |
| `core`    | 少数群定数テーブル、炉心の仕様 | k_eff、出力分布、燃焼度分布 | SIMULATE, PARCS    |

- 段階ごとにクレートを分ける理由: 段階間の依存がファイル形式だけになり、段階ごとに単独で検証できる。既存コードの出力（NJOY で作ったライブラリなど）を差し込んで比較することもできる
- 依存クレートは、事実上の標準があるものはそれを使う（並列処理の rayon、複素数の num-complex、ファイルの読み書きの serde、
  エラーの thiserror と anyhow、ログの tracing など）。自前で書いたコードの保守の方が、定番のクレートへの依存より重いためである。
  定番のない数値計算（特殊関数、幅のゆらぎの積分、固有値計算、指数行列など）は、問題に特化しているので自前で実装する

## ファイルの約束事

段階間のファイルと入力ファイルは、すべてのクレートと検証用のツールに広がるので、後から変えにくい。M2 の途中で次のとおり決め、
既存の自前のテキスト形式と `String` のエラーは、M2 の中で移行する（[M2 の計画](m2-assembly.md) の進め方を参照）。

- 入力ファイル（人が書くもの）は TOML とする。コメントが書け、手書きの誤りに強く、Rust の serde 対応が安定しているため。
  YAML は Rust での serde 対応の保守が途絶えており、JSON はコメントが書けず、XML は手書きに向かない
- データファイル（プログラムが書いて読むもの: 多群ライブラリ、少数群定数など）は MessagePack とする。人が読む必要はなく、
  検証用のスクリプトから読めればよい（Python の `msgpack`）。f64 を 8 バイトの IEEE 754 のまま持つので、10 進表記との
  変換による誤差が原理的に起きない（JSON では、読み込み側の実装と設定によっては最下位のビットがずれる）。
  CBOR も同じ性質を持つが、Rust と Python での実績が多い MessagePack を選んだ。大きな表を一部だけ読む必要が出たら
  （燃焼の分岐テーブルを扱う M4 が目安）、HDF5 への移行を検討する。serde で型を定義しておけば、形式の変更は読み書きの部分だけで済む
- 後方互換は持たない（まだ誰も使っていないため）。形式を変えたら古いファイルは作り直し、古い形式を読むコードは残さない。
  形式の版も持たない
- 読み込みでは、未知の項目、欠けた項目、範囲外の値をすぐにエラーにする（serde の `deny_unknown_fields`）。推測で補ったり、
  既定値で黙って続けたりしない。データファイルは形式の名前（種類）を持ち、別の種類のファイルを渡されたらエラーにする
  - MessagePack はフィールド名付きの map 形式で書き、読むときも map 以外を拒否する。配列形式ではフィールド名がなく、
    未知の項目を検出できず、順番の変わったファイルを黙って誤読するため
  - データファイルの型に `Option` を使わない（serde は欠けた `Option` の項目を黙って `None` にする）。入力ファイルでは、
    省略に意味がある項目（出力しない、帯をセルの外周までとする、など）だけ省略を許す
- 単位: エネルギーは eV、微視的断面積は barn、長さは cm、温度は K、個数密度は 1/(barn cm)、巨視的断面積は 1/cm
- 群は高いエネルギーから順に並べる（群 0 が最も高い）
- 核種の名前は、元素記号と質量数をハイフンでつなぐ `U-235`, `H-1` の形とし、元素記号は先頭だけ大文字にする。
  準安定状態は `Am-242m` と書き、2番目以降は `Hf-178m2` のように番号を付ける（`m` は `m1` と同じ。番号は GNDS の
  metastableIndex に合わせる）。規格（IUPAC, IUPAP）が定めるのは上付きの記号 ²³⁵U と名前 uranium-235 だけで、
  上付きを使わない書き方の規格はない。この形は名前を記号で略しただけに見えるので、原子力分野の外でも読める。
  GNDS や OpenMC の `U235`, `Am242_m1` とは、受け渡すときに文字列の変換で対応させる
- エラーは、ライブラリ側を thiserror の型付きのエラー、コマンド側を anyhow で文脈を付けて表示する
- 計算結果（k など）は標準出力に、経過と診断はログとして標準エラーに出す。ログは tracing とし、ライブラリは
  マクロと区間（span）だけを使い、出力の設定は各コマンドで tracing-subscriber を使って行う。量は環境変数
  `RUST_LOG` で選ぶ（既定は info: 段階ごとの時間と反復の回数。debug: 反復ごとの経過と内訳の時間。trace:
  原因の調査用の細部）。log と env_logger より、区間で段階ごとの時間を測れるので性能の調査にも使える
- Python は検証用のツール（OpenMC の入力の作成、比較のスクリプト）にだけ使い、本体の計算には使わない。
  開発と検証の環境は `flake.nix` の devShell で固定する

## 手法の選択

### xs: 核データ処理

- 対象データは ENDF/B-VIII.0 とする（中性子、熱中性子散乱、崩壊、核分裂収率の各サブライブラリ）。ENDF ファイルはリポジトリに含めず、パスを設定して参照する
- 処理の流れは NJOY と同じく、共鳴の再構成 → ドップラー拡がり → 熱中性子散乱 → 群定数化 とする。共鳴パラメータの形式（MLBW / Reich-Moore / R-matrix limited）は、対象核種で実際に使われているものから順に対応する
- 群構造は WIMS 69群とする。公開されていて、PWR の格子計算での実績があるためである。より細かい群構造が必要になったら追加する
- 自己遮蔽は Bondarenko の f-table（背景断面積 σ0 と温度に依存する遮蔽因子）で扱う。格子計算の側で等価原理と Dancoff 係数を使って σ0 を決める。サブグループ法より実装が単純で、まず全体を通すことを優先した

### lattice: 格子計算

- 集合体全体の輸送計算は 2D MOC（特性曲線法）とする。円柱形の燃料ピンを近似なしで扱える現在の主流の手法だからである
- 自己遮蔽で使う Dancoff 係数は、燃料を黒体にした集合体の MOC でピンごとに求める（M2 で衝突確率法から変更。[M2 の計画](m2-assembly.md) を参照）
- 燃焼計算は CRAM（Chebyshev 有理近似）で解き、予測子・修正子法で時間を進める。燃焼チェーンは ENDF の崩壊・収率データから作り、PWR に必要な範囲に縮約する
- 出力は燃焼度ごとの2群の均質化定数、ADF、ピン出力形状とする。ホウ素濃度と制御棒挿入の有無は、各燃焼点からの分岐計算でテーブル化する。Xe と Sm は微視的断面積と数密度を別に出力し、炉心側で数密度を追跡できるようにする

### core: 炉心計算

- 3D NEM（ノード展開法）で2群の拡散計算を行う。1集合体を径方向に1ノード（必要なら2×2）とする。商用コードの標準的な手法で、ADF とピン出力の再構成を含めて確立しているためである
- 固有値は非線形 CMFD で加速する
- 燃焼度は各ノードで追跡し、ノードの断面積は燃焼度・ホウ素濃度・制御棒の有無からテーブルを補間して求める
- 熱水力のフィードバックは初期のマイルストーンでは扱わず、燃料温度・減速材温度は一定とする。燃焼後の結果を実機データと比べる段階で導入する

## 進め方

最初に、3つの段階を最小構成で端から端までつなぐ（縦切り）。段階間のデータ形式の設計ミスに早く気づくためである。その後で各段階を作り込む。

| マイルストーン  | 内容                                                                                       | 検証                                        |
| --------------- | ------------------------------------------------------------------------------------------ | ------------------------------------------- |
| M0 縦切り       | 少数核種（H-1, O-16, U-235, U-238）の無限希釈断面積 → ピンセル MOC → 均質な炉心の NEM      | 解析解、モンテカルロ計算                    |
| M1 核データ処理 | 共鳴の再構成・ドップラー拡がり・熱中性子散乱・f-table を備え、PWR に必要な全核種を処理する | NJOY の出力との比較                         |
| M2 集合体       | 17×17 集合体の MOC と自己遮蔽                                                              | C5G7, VERA Problem 1–2                      |
| M3 炉心 HZP     | 3D NEM、CMFD、ADF、ピン出力の再構成                                                        | VERA Problem 3–5                            |
| M4 燃焼         | 格子計算の燃焼と分岐計算、炉心での燃焼度追跡                                               | VERA Problem 6 以降、格子燃焼のベンチマーク |

「燃焼まで」（M4）を最初の到達目標とする。熱水力のフィードバックを含む BEAVRS との比較は、その後に検討する。

参照解を作るためのモンテカルロコード（OpenMC など）は検証にだけ使う外部ツールとし、本体の依存には含めない。
