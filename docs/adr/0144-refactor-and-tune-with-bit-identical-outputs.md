# ADR-0144: リファクタリングと簡易なチューニングは、出力のビット一致と時間の比較を条件に進め、長い関数を clippy で止める

## 背景

2026-10-12 のコードのレビューは、弱点として長い関数と大きなファイルを挙げ、性能の回帰を監視する仕組みがないこと、
`.clone()` が 463 箇所あり、どれがホットな経路かを見ていないことを指摘した。ファイルの大きさの半分はテストで、
置き方は ADR-0143 で決めた。

長い関数: clippy の `too_many_lines`（既定のしきい値 100 行。空行とコメントを数えない）を警告にして数えると、
main（14793ea7、2026-10-12）で 36 個の関数が超えた。本番のコードで 26 個、テストで 6 個、examples で 4 個。長い順に、
crates/lattice/src/moc.rs の `solve_with`（349 行）、crates/lattice/src/main.rs の `run`（316 行）、
crates/lattice/examples/swap_transfer.rs の `main`（273 行）、crates/lattice/src/shielding.rs の `shield_fuel_with`（265 行）、
crates/lattice/src/input.rs の `parse`（244 行）。

時間の内訳: 格子計算の時間の大半は MOC でなく自己遮蔽にある。VERA 2A の 1 状態は 118 秒で、自己遮蔽 110 秒、MOC 7.3 秒
（examples/vera/verification.md、e4dbc0de、2026-10-12）。自己遮蔽の中では、perf で円筒の等価なセルの衝突確率
（`cp::Cylinder::tracks`）が大半を占めた（#0039、2026-10-09。その後の高速化の前の値）。レビューが挙げた MOC の関数を
整えても、速さにはほとんど効かない。

結果を変えずに済むかの前提:

- 並列の和の順序は固定してある（ADR-0064、#0060 の表）。同じコードの経路なら、スレッド数によらず同じ和になる
- Rust は浮動小数点の積和を勝手に融合せず、演算の順も変えない（ADR-0109 で、コンパイルの対象の CPU を変えても少数群定数が
  ビット単位で同じだった）。関数を抜き出してインライン化が変わっても、演算の順が同じなら結果は変わらない
- DVC のステージ（ADR-0123）は出力を md5 で記録する。変えたコードを deps に持つ段階を走らせ直せば、出力のバイトの一致を
  `dvc.lock` の差分で確かめられる

判断の軸:

- 検証の記録の数値（OpenMC との比較など）が、整理のあとも成り立つこと
- 速さを落とさないこと
- 長い関数が、整理したあとに再び育たないこと

## 検討した案

結果を変えていないことの判定:

- 案 A1: 既存のテストと、検証の記録の許容幅（OpenMC との比較）で判定する。浮動小数点の丸めの差が入っても気づかず、
  許容幅の中で結果がずれていく
- 案 A2: 変えたコードを通る DVC のステージを走らせ直し、出力がバイト単位で一致することで判定する。上の前提から、整理と
  演算の順を変えない高速化では一致するはずで、一致しなければ演算の順か結果を変えたことが分かる

速さの判定:

- 案 B1: `cargo bench`（criterion など）のベンチマークを置く。依存が増え、時間を記録する測定は Slurm の排他のジョブで
  流す決まり（CLAUDE.md の「計算」）なので、`run-checks.sh` の検査には入れられない。小さな関数の時間は、自己遮蔽のような
  全体の時間の内訳を表さない
- 案 B2: 本番の実行ファイルに例の入力を与えて、分岐点と変更後を同じ排他のジョブで交互に測る（hyperfine。交互の実行と
  統計を持つ）

チューニングの範囲:

- 案 C1: 速くなる変更をすべてこの手順で入れる。和の順序や近似を変える高速化（#0039 の、衝突確率を少数の全断面積から
  内挿する案など）は結果を変えるので、A2 で判定できない
- 案 C2: この手順で入れるのは、出力をバイト単位で変えない高速化（メモリの確保の使い回し、ホットな経路の `clone` を
  除くこと、ビルドの設定など）に限る。結果を変える高速化は、それぞれの ADR で精度への影響を測って決める

関数の長さの再発:

- 案 D1: レビューで見る。今の 36 個も、レビューを通ってできた
- 案 D2: `too_many_lines` をワークスペースの lint で拒否にし、今の 36 個に `#[expect(clippy::too_many_lines, reason = "#0087")]`
  を付ける。`expect` は、分けて lint が出なくなると警告になるので、付けたまま残らない

## 決定と理由

A2、B2、C2、D2 を採る。

- リファクタリングと簡易なチューニングのブランチは、マージの前に（rebase のあとに。記録の計算の前に rebase する
  決まりと同じ理由）、変えたコードを deps に持つ DVC のステージを Slurm で走らせ直し、`dvc.lock` の出力の md5 が分岐点と
  同じことを確かめる。時間を含むログ（`*.log`。`tracing` が秒を書く）は比べない。一致しなければ原因を調べ、演算の順を
  変えていたら、元に戻すか、結果を変える変更として別に扱う
- 同じブランチで、分岐点と変更後の release の実行ファイルを、同じ排他のジョブで hyperfine により交互に測る。入力は
  変えたクレートの例の入力で、lattice は VERA 1B のピンセル（examples/vera/p1/pincell-1B.toml）と 2A の集合体
  （examples/vera/p2/assembly-2A.toml）。変更後の平均が、分岐点の平均より実行ごとの標準偏差を超えて遅ければ、
  マージしない
- チューニングは、perf で時間の内訳を測ってから、上位の箇所に手を入れる。測る前に `clone` の数などで箇所を選ばない
- `too_many_lines` は既定のしきい値（100 行）のまま拒否にする。xlc で別の値を決める根拠を持たないので、clippy の既定に従う

A1 を採らないのは、検証の記録の比較は許容幅を持つので、整理の誤りによる小さなずれを見落とすからである。B1 を採らないのは、
時間の大半が自己遮蔽という全体の経路にあり、測る対象は実行ファイル全体の時間だからである。

## 確認

- ビット一致: ブランチごとに、再実行した段階の `dvc.lock` の outs の md5（`*.log` を除く）が分岐点と同じこと。結果は
  #0087、#0088 に、実行したコミット、分岐点、日付とともに書く
- 時間: hyperfine の出力（平均と標準偏差）を、同じく issue に書く。速くなったものは examples/vera/verification.md の時間の
  記録を書き直す
- lint: `run-checks.sh` の clippy が、`#[expect]` のない 100 行を超える関数で失敗すること

## 帰結

- 実装の順序: 先に ADR-0143 のテストの移動、次に lint の導入（36 個に `#[expect]` を付ける）、そのあと #0087 の関数の
  分割と #0088 のチューニングを、ブランチごとに上の判定で進める。チューニングは時間の大きい自己遮蔽から測る
- DVC のステージを持たない例（examples/branches、examples/split など）だけが通るコードは、A2 で確かめられない。その経路を
  変えるときは、同じ入力の出力を分岐点と変更後で比べる（`cmp`）
- 時間の比較は、リファクタリングとチューニングのブランチでだけ行う。機能を足すブランチの意図しない遅れは、検証の記録の
  時間を書き直すまで見つからない
- hyperfine は開発のマシンにあるが devShell（flake.nix）にない。導入のブランチで devShell に足す
- 結果を変える高速化（#0039 の衝突確率の内挿など）は、この ADR の範囲の外で、それぞれの ADR で決める
