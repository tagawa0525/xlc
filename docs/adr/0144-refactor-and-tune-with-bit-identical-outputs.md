# ADR-0144: リファクタリングと簡易なチューニングは、計算の出力のビット一致と時間の比較を条件に進める

## 背景

2026-10-12 のコードのレビューは、弱点として長い関数と大きなファイルを挙げ、性能の回帰を見張る仕組みがないこと、
`.clone()` が多い（1842033d の `crates` の `*.rs` で、テストを含めて 483 個の出現）のに、どれがホットな経路かを
見ていないことを指摘した。ファイルの大きさの半分はテストで、置き方は ADR-0143 で決めた。

長い関数: clippy の `too_many_lines`（既定のしきい値 100 行。空行とコメントを数えない）を警告にして数えると、
main（1842033d、2026-10-12）で 36 個の関数が超えた。本番のコードで 26 個、テストで 6 個、examples で 4 個。長い順に、
crates/lattice/src/moc.rs の `solve_with`（349 行）、crates/lattice/src/main.rs の `run`（316 行）、
crates/lattice/examples/swap_transfer.rs の `main`（273 行）、crates/lattice/src/shielding.rs の `shield_fuel_with`（265 行）、
crates/lattice/src/input.rs の `parse`（244 行）。

時間の内訳: 格子計算の時間の大半は MOC でなく自己遮蔽にある。VERA 2A の 1 状態は 118 秒で、自己遮蔽 110 秒、MOC 7.3 秒
（examples/vera/verification.md、1f4fcaaf、2026-10-12）。自己遮蔽の大半は代表のピンの等価なセルの衝突確率で、perf で
`cp::Cylinder::tracks` 45%、`cp::interpolate` 23% だった（examples/vera/verification.md の「対称性」、2026-10-10）。
MOC は 1 状態の 6% なので、レビューが挙げた MOC の関数を整えても、全体の時間にはほとんど効かない。

結果を変えずに済むかの前提:

- 並列の和の順序は固定してある（ADR-0064、#0060 の表）。これはコードとテストで確かめたもので、段階の出力がスレッド数に
  よらずバイト一致するかは #0060 で確かめていない
- Rust は浮動小数点の積和を勝手に融合せず、演算の順も変えない（ADR-0109 で、コンパイルの対象の CPU を変えても少数群定数が
  ビット単位で同じだった）。関数を抜き出してインライン化が変わっても、ソースの演算の順が同じなら、多くの演算の結果は
  変わらない。ただし、インライン化で引数が定数になった `powi` などは別の命令列に下ろされうる（Rust は `powi` の精度を
  保証しない）
- DVC の段階（ADR-0123）は出力を md5 で記録する。計算の結果を書く出力（msgpack と標準出力）は、変えたコードを deps に
  持つ段階を走らせ直せば、`dvc.lock` の差分でバイトの一致を確かめられる。`tracing` のログ（examples/reflector の
  `*.log`）は時刻、秒、span の名前を含み、整理しただけでも変わる。ログの中の数値は、それを読む下流の段階
  （compare_axial.py などの比較の段階）の出力で比べられる

判断の軸:

- 検証の記録の数値（OpenMC との比較など）が、整理のあとも成り立つこと
- 速さを落とさないこと

## 検討した案

結果を変えていないことの判定:

- 案 A1: 既存のテストと、検証の記録の許容幅（OpenMC との比較）で判定する。浮動小数点の丸めの差が入っても気づかず、
  許容幅の中で結果がずれていく
- 案 A2: 変えたコードを通る DVC の段階を走らせ直し、計算の結果を書く出力がバイト単位で一致することで判定する。上の前提
  から、整理と演算の順を変えない高速化では一致するはずで、一致しなければ演算の順か結果を変えたことを疑える

速さの判定:

- 案 B1: `cargo bench`（criterion など）のベンチマークを置く。依存が増え、時間を記録する測定は Slurm の排他のジョブで
  流す決まり（CLAUDE.md の「計算」）なので、`run-checks.sh` の検査には入れられない。小さな関数の時間は、自己遮蔽のような
  全体の時間の内訳を表さない
- 案 B2: 本番の実行ファイルに例の入力を与えて、分岐点と変更後を同じ条件で測る

チューニングの範囲:

- 案 C1: 速くなる変更をすべてこの手順で入れる。和の順序や近似を変える高速化（#0039 の、衝突確率を少数の全断面積から
  内挿する案など）は結果を変えるので、A2 で判定できない
- 案 C2: この手順で入れるのは、計算の出力をバイト単位で変えない高速化（メモリの確保の使い回し、ホットな経路の `clone`
  を除くこと、ビルドの設定など）に限る。結果を変える高速化は、それぞれの ADR で精度への影響を測って決める

## 決定と理由

A2、B2、C2 を採る。

- リファクタリングと簡易なチューニングのブランチは、変えたコードを deps に持つ DVC の段階を走らせ直し、計算の結果を
  書く出力（ログを除き、ログの数値を読む下流の段階の出力を含む）が、分岐点のコードで走らせた出力とバイト単位で一致する
  ことを示してからマージする。main の `dvc.lock` の出力が分岐点より古いコードで作ったもの（ADR-0130 のとおり、rebase で
  deps が変わっても走らせ直さない）なら、分岐点で走らせ直して比べる元にする。分岐点と変更後は同じスレッド数で走らせ、
  #0060 の揺れを比べる条件から除く
- 一致しなければ原因を調べる。演算の順を変えていたら、元に戻すか、結果を変える変更として別に扱う
- 同じブランチで、分岐点と変更後の release の実行ファイルの時間を、同じ条件（同じマシン、排他のジョブ、同じ入力、同じ
  スレッド数）で比べ、遅くなっていないことを示す。比べる入力は、変えたコードの時間がかかる経路を通る例の入力にする
  （lattice では VERA 1B のピンセルや 2A の集合体）
- チューニングは、perf で今の時間の内訳を測ってから、上位の箇所に手を入れる。測る前に `clone` の数などで箇所を選ばない
- 走らせ直しと時間の測定の手順（道具、測る回数、遅くなったとみなす基準）と、重い計算を流す時期は、実装のブランチ
  （#0087、#0088）で決める

A1 を採らないのは、検証の記録の比較は許容幅を持つので、整理の誤りによる小さなずれを見落とすからである。B1 を採らないのは、
時間の大半が自己遮蔽という全体の経路にあり、測る対象は実行ファイル全体の時間だからである。

## 確認

この手順で進めた最初のブランチで、出力の一致と時間の比較の結果を、走らせたコミット、分岐点、日付とともにこの節に書き、
`status: accepted` にする。以後のブランチの結果は #0087、#0088 に書く。

## 帰結

- テストの移動（#0089）と同じファイルに触るので、#0087 の関数の分割はそのあとに行う。チューニングは時間の大きい
  自己遮蔽から測る
- 長い関数が再び育つのを lint（clippy の `too_many_lines` など）で止めるかは、この ADR では決めない（#0087）
- DVC の段階を持たない例（2026-10-12 に dvc.yaml があるのは m0、reflector、vera だけ）だけが通るコードと、
  `crates/*/examples` の道具（swap_transfer.rs、compare_njoy_*.rs など）は、段階の走らせ直しで確かめられない。
  その経路を変えるときは、同じ入力の出力を分岐点と変更後で比べる
- 時間の比較は、リファクタリングとチューニングのブランチでだけ行う。機能を足すブランチの意図しない遅れは、検証の記録の
  時間を書き直すまで見つからない
- 結果を変える高速化（#0039 の衝突確率の内挿など）は、この ADR の範囲の外で、それぞれの ADR で決める
