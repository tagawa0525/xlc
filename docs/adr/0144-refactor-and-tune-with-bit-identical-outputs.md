# ADR-0144: リファクタリングと簡易なチューニングは、計算の出力のビット一致と時間の比較を条件に進める

## 背景

2026-10-12 のコードのレビューは、弱点として長い関数と大きなファイルを挙げ、性能の回帰を監視する仕組みがないこと、
`.clone()` が多い（14793ea7 の `crates` の `*.rs` で、テストを含めて 483 個の出現）のに、どれがホットな経路かを
見ていないことを指摘した。ファイルの大きさの半分はテストで、置き方は ADR-0143 で決めた。

長い関数: clippy の `too_many_lines`（既定のしきい値 100 行。空行とコメントを数えない）を警告にして数えると、
main（14793ea7、2026-10-12）で 36 個の関数が超えた。本番のコードで 26 個、テストで 6 個、examples で 4 個。長い順に、
crates/lattice/src/moc.rs の `solve_with`（349 行）、crates/lattice/src/main.rs の `run`（316 行）、
crates/lattice/examples/swap_transfer.rs の `main`（273 行）、crates/lattice/src/shielding.rs の `shield_fuel_with`（265 行）、
crates/lattice/src/input.rs の `parse`（244 行）。

時間の内訳: 格子計算の時間の大半は MOC でなく自己遮蔽にある。VERA 2A の 1 状態は 118 秒で、自己遮蔽 110 秒、MOC 7.3 秒
（examples/vera/verification.md、e4dbc0de、2026-10-12）。自己遮蔽の大半は代表のピンの等価なセルの衝突確率で、VERA 2B の
1 状態（1/8 の対称性。1 状態 1 分 59 秒、うち自己遮蔽 約 110 秒の時間は d13f57d5 の測定）の perf で `cp::Cylinder::tracks` 45%、`cp::interpolate` 23% だった
（examples/vera/verification.md の「対称性」。2026-10-10 の測定で、コミットは記録になく、2A の 118 秒とは別の状態と時点）。
MOC は 1 状態の 6% なので、レビューが挙げた MOC の関数を整えても、全体の時間にはほとんど効かない。

結果を変えずに済むかの前提:

- 並列の和の順序は固定してある（ADR-0064、#0060 の表）。これはコードとテストで確かめたもので、ステージの出力がスレッド数に
  よらずバイト一致するかは #0060 で確かめていない
- Rust は浮動小数点の積和を勝手に融合せず、演算の順も変えない（Rust と LLVM の既定の規則。その観測として ADR-0109 で、コンパイルの対象の CPU を変えても少数群定数が
  ビット単位で同じだった）。関数を抜き出してインライン化が変わっても、ソースの演算の順が同じなら、多くの演算の結果は
  変わらない。ただし、インライン化で引数が定数になった `powi` や、定数の引数でコンパイル時に計算される数学関数（`exp` など）は、別の命令列や値になりうる（Rust は `powi` の精度を
  保証しない）
- DVC のステージ（ADR-0123）の出力には、全桁の msgpack と丸めた値が混ざる。main（db212cb1）では、examples/vera の xs の
  `vera.msgpack`、examples/m0 の lattice の `pincell-fg.msgpack`、examples/vera/p5 の集合体の少数群定数（自己遮蔽を
  通る）などは全桁で比べられる。examples/vera の lattice-1B の出力は 6 桁の k だけで、`tracing` のログは時刻や span の名前を
  含んで整理だけでも変わり、ログの数値を読む比較のステージは丸めた値を書く。main の `dvc.lock` の出力がどのコードと
  スレッド数で作られたかは、`dvc.lock` に記録されない（ADR-0130 のとおり、rebase で deps が変わっても再実行しない）
- lattice は、少数群定数（`few-group`。分岐の計算ではテーブル）とピン出力（`pin-powers`。分岐の計算では書けない）を
  msgpack に全桁で書ける。xs はライブラリを msgpack に書く。例の入力にこれらの出力を足せば、計算の結果を全桁で比べられる。
  core が全桁で書くのはピン出力の再構成だけで、k は 8 桁の標準出力である。`crates/*/examples` のツールにも、丸めた値しか
  書かないものがある

判断の軸:

- 検証の記録の数値（OpenMC との比較など）が、整理のあとも成り立つこと
- 速さを落とさないこと

## 検討した案

結果を変えていないことの判定:

- 案 A1: 既存のテストと、検証の記録の許容幅（OpenMC との比較）で判定する。浮動小数点の丸めの差が入っても気づかず、
  許容幅の中で結果がずれていく
- 案 A2: 変えたコードを通る DVC のステージを走らせ直し、`dvc.lock` の出力の md5 で判定する。手間は少ないが、上のとおり
  比べる元の出力を作ったコードとスレッド数が分からず、丸めた値しか書かないステージもある
- 案 A3: 分岐点と変更後の release の実行ファイルに、変えたコードを通る例の入力（全桁の msgpack を書くもの）を与えて、
  同じスレッド数で実行し、書いた msgpack がバイト単位で一致することで判定する。比べる元を毎回分岐点で作るので、main の
  `dvc.lock` の出力がどのコードとスレッド数で作られたかに依らない

速さの判定:

- 案 B1: `cargo bench`（criterion など）のベンチマークを置く。依存が増え、時間を記録する測定は Slurm の排他のジョブで
  流す決まり（CLAUDE.md の「計算」）なので、`run-checks.sh` の検査には入れられない。小さな関数の時間は、自己遮蔽のような
  全体の時間の内訳を表さない
- 案 B2: 本番の実行ファイルに例の入力を与えて、分岐点と変更後を同じ条件で測る

チューニングの範囲:

- 案 C1: 速くなる変更をすべてこの手順で入れる。和の順序や近似を変える高速化（#0039 の、衝突確率を少数の全断面積から
  内挿する案など）は結果を変えるので、バイトの一致では判定できない
- 案 C2: この手順で入れるのは、計算の出力をバイト単位で変えない高速化（メモリの確保の使い回し、ホットな経路の `clone`
  を除くことなど）に限る。結果を変える高速化は、それぞれの ADR で精度への影響を測って決める。ビルドの設定（LTO、
  `codegen-units`）はインライン化を変えるので、出力が変わるかは実行して分かる

## 決定と理由

A3、B2、C2 を採る。

- リファクタリングと簡易なチューニングのブランチは、A3 の比べ方で、書いた msgpack が分岐点とバイト単位で一致することを
  示してからマージする。比べるのは main に rebase したあと（記録の計算の前に rebase する決まりと同じ理由。マージの前にもう一度
  rebase して、main が変えたものが比べる経路のコード、ビルドの設定、ツールチェーン、依存に触れていれば比べ直す）で、分岐点と変更後の
  実行ファイルをそれぞれ 2 回実行し、どちらも自分とは一致することを確かめる（同じスレッド数での
  一致は、#0060 の経緯の M0 の lattice、ADR-0109 の VERA 1B と 2B の少数群定数（コンパイルの対象の CPU を変えたビルドの間の比較）で一致した記録があるが、すべての経路では
  確かめていない）。変えたコードの結果が全桁の出力に出ない
  経路（標準出力にだけ書く k、丸めた値だけを書くツールなど）は、全桁の出力を入力で選べる機能として、別のブランチで先に main に入れる
  （試行を入力で選ぶ決まり。ADR-0122。分岐点にその出力がないと比べられない）。一致しなければ原因を調べ、ソースの演算の順を変えていたら元に戻す。ソースの演算の順を変えずに
  変わったもの（ビルドの設定やインライン化による `powi` の下ろし方など）を含め、一致しない変更は結果を変える変更として
  扱い、入れるなら別の ADR で精度への影響を測って決める
- 同じ実行で、分岐点と変更後の時間を同じ条件（同じマシン、排他のジョブ、同じ入力、同じスレッド数）で比べ、遅くなって
  いないことを示す。入力は、変えたコードの時間がかかる経路を通るものにする（lattice の自己遮蔽なら VERA 1B のピンセルや
  2A の集合体に、少数群定数の出力を足したもの）。記録に書く入力は ADR-0122 のとおりコミットする
- チューニングは、perf で今の時間の内訳を測ってから、上位の箇所に手を入れる。測る前に `clone` の数などで箇所を選ばない
- A3 が判定するのは数値の出力である。数値を出さないふるまい（入力の検査、エラーのメッセージ、警告）は、既存の単体
  テストで守る。テストの関数だけを変えるブランチは、A3 の判定の対象にしない。examples のツールは、検証の記録が
  その出力を引くので対象にする
- 測定の手順（ツール、測る回数、遅くなったとみなす基準）と、重い計算を流す時期は、実装のブランチ（#0087、#0088）で決める
- DVC のステージは、ふだんの規則（ADR-0123、ADR-0130）のとおりに扱う。時間が変わったら、検証の記録（examples/*/verification.md）
  の時間を書き直す

A1 を採らないのは、検証の記録の比較は許容幅を持つので、整理の誤りによる小さなずれを見落とすからである。A2 を採らない
のは、比べる元の出力がどのコードとスレッド数で作られたかが分からず、丸めた値しか書かないステージもあるからである。B1 を採らないのは、
時間の大半が自己遮蔽という全体の経路にあり、測る対象は実行ファイル全体の時間だからである。

## 確認

この手順で進めた最初のブランチで、出力の一致と時間の比較の結果を、実行したコミット、分岐点、日付とともにこの節に書き、
`status: accepted` と `date` をその日にする。以後のブランチの結果は #0087、#0088 に書く。

## 帰結

- テストの移動（#0089）と同じファイルに触るので、#0087 の関数の分割と、#0088 のうちソースを変えるチューニングはそのあとに行う（perf の測定とビルドの設定は待たない）。チューニングは時間の大きい
  自己遮蔽から測る
- 長い関数が再び育つのを lint（clippy の `too_many_lines` など）で止めるかは、この ADR では決めない（#0087）
- 時間の比較は、リファクタリングとチューニングのブランチでだけ行う。機能を足すブランチの意図しない遅れは、検証の記録の
  時間を書き直すまで見つからない
- 結果を変える高速化（#0039 の衝突確率の内挿など）は、この ADR の範囲の外で、それぞれの ADR で決める
