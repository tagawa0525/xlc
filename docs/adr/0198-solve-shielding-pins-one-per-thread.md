# ADR-0198: 自己遮蔽のピンを、スレッドごとに 1 本ずつ取って解く

## 背景

自己遮蔽は、対称性で残した代表のピン（2A で 39 本）の UFG の減速計算を、ピンをまたいで並列に解き（`shielding.rs`）、ピンの中でも
飛程の表、衝突確率、核種ごとの縮約を rayon で並列に求める。ピンの並列は `solving.par_iter()` だった。2A の 1 輸送で、ピンの UFG の
区間は 16 スレッドで 1 スレッドの 7.8 倍（効率 49%）にとどまり、16 スレッドの輸送の 48% を占めた（#0161）。

切り分けの測定（examples/vera/verification.md の「格子計算の並列の効率（2A）」。Slurm 505 と 510）で、遮る原因は 2 つと分かった:

- 格子点の用意（`grid`）の間引き（ADR-0185）は、核種ごとに 1,265,966 点の和集合の格子の全体を流して巨視的な断面積の配列（点 × リングの
  物質 × 2）に足していた。核種の数（90）だけ数十 MB の配列を DRAM から読み書きするので、16 本が同時に走るとメモリの転送で詰まり、
  ピンの `grid` の段の和は 1 スレッドの 20.9 秒から 105.0 秒になった
- `par_iter` のピンは、ピンの中の並列を待つスレッドに丸ごと盗まれる。盗んだスレッドはそのピンを解き終えるまで元のピンに戻らないので、
  最長のピンは 1 スレッドの 3.3 秒から 14.1 秒になり、区間の全体（14.1 秒）がその 1 本で決まった

判断の軸:

- 結果をビットで変えない（点ごとの演算と足す順序を変えない。ADR-0188 と同じ考え方）
- スレッドの数は ADR-0067 のまま（物理コアの数）。入力の選択肢を足さない
- 39 本を 16 で割ると最後の周が 7 本になるので、ピンを取り終えたスレッドが残りのピンの中の並列を手伝えること

## 検討した案

- 案 A: ピンは `par_iter` のまま、間引きの和だけを点の塊ごとにする（下の「決定と理由」の 2 つ目）。16 スレッドのピンの UFG は 9.64 秒
  （Slurm 510 の `gridonly`）。盗みは残り、最長のピン（9.52 秒）が区間の全体を占めた
- 案 B: ピンの中の並列をなくし、ピンの間だけで並列にする。盗みはなくなるが、最後の周の 7 本を残りの 9 スレッドが手伝えず、1 本 2.4〜3 秒の
  逐次が尾になる。飛程の表（1 本 0.7 秒）はピンの中で並列にできるのに、それを捨てる。測っていない
- 案 C: `rayon::broadcast` で、プールの各スレッドが共有のカウンタからピンの番号を順に取る。broadcast の仕事はそのスレッドだけが実行し、
  ほかのスレッドの盗みの対象にならないので、待つスレッドが盗めるのはピンの中の並列の仕事だけになる。ピンを取り終えたスレッドは
  残りのピンの中の並列を手伝う
- 案 D: ピンを重い順に投げる。2A の代表のピンは 1 スレッドで 2.4〜3.3 秒とそろっていて（Slurm 510）、解く前に重さを知る手段がない（前の輸送の時間を
  持ち越す必要がある）。案 C の測定で、尾は最後の周の 7 本（5.8 秒から 8.0 秒。1 周目の 1 本が 5.0 秒かかり、そのスレッドが 4.9 秒から取った 1 本も 8.0 秒に終わる）で、順序で縮む余地は小さいので採らない

## 決定と理由

案 C にし、間引きの和を点の塊ごとにする。

- ピン: `shield_fuel_reusing` は `rayon::broadcast` の中で、`AtomicUsize` のカウンタから番号を取ってピンを解き、結果を番号の `OnceLock` に
  置く。結果の物質の追加、領域への割り当て、エラーは、これまでどおりピンの順に逐次に扱う
- 間引き（`ufg::thin`）: 巨視的な全断面積と弾性散乱断面積の和を、4,096 点の塊ごとに並列に求める。塊の中で核種の順に足すので、点ごとの
  和の順は変わらない。塊の始めのカーソルは、その点以下の最後の格子点の次（二分探索）で、`bracket` は上の点から下ってきたカーソルと
  同じ区間を返す。和集合の格子の整列も並列にする（全順序なので並びは同じ）

2A の 1 輸送の 16 スレッドで、ピンの UFG の区間は 14.11 秒 → 8.02 秒（同じ版の 1 スレッドの 93.73 秒の 11.7 倍。効率 73%。main は 95.03 秒の 6.7 倍）、プロセスの全体は
29.3 秒 → 23.6 秒（Slurm 510。main f3a143d74 と xlc 3bfe89aa7）。案 A の 9.64 秒より 1.6 秒短い。DRAM からの L2 の充填は 16 スレッドで
8.35e9 → 5.12e9 回、1 スレッドでも 5.96e9 → 3.77e9 回に減った。少数群定数の出力はスレッドの数（1、4、16）と版によらずビットで同じ。

## 確認

- テスト: `shielding::tests::lattice::pins_solved_on_many_threads_match_one_thread`（3×3 のピンを間引いた UFG で、1、3、4 スレッドの結果が等しい）
- 2A の 1 輸送の出力（`examples/depletion/trials-lattice-scaling/run.sh`）の md5 が、main と、この版の 1、4、16 スレッドで同じ（Slurm 510）
- 2A の最初の 10 点の燃焼（examples/depletion/issue-0137/2A-10.toml）の履歴が、同じジョブの main の実行とビットで同じ（examples/depletion/verification.md の「時間」）

## 帰結

16 スレッドでも、1 本のピンは 1 スレッドの 1.2 倍ほどかかり（区間の中央値 2.92 秒、1 スレッド 2.39 秒）、39 本の 3 周目は 7 本なので、
区間は 1 スレッドの 16 倍（5.9 秒）に届かない。残りの伸びの段は `slowing`（和 26.3 → 31.2 秒）と `grid`（20.7 → 28.0 秒。並列にした部分の
待ちに盗んだ時間を含む）で、メモリの転送の候補は残る（確かめていない。#0171）。構造材の塊は `par_iter` のままで、盗みの対策の効きは測っていない（#0171）。

`broadcast` はプールのすべてのスレッドが仕事を終えるまで返らず、待つスレッドはほかの `broadcast` の仕事も引き受ける。自己遮蔽は
今の呼び出し側（燃焼の輸送と分岐の状態のループ）でプールの外から 1 回ずつ呼ばれる。自己遮蔽をほかの並列の仕事と同時に呼ぶ形に
するときは、この前提を見直す。
