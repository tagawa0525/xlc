# ADR-0214: lattice のスレッド数の既定をプロセスに許された論理 CPU の数とする

## 背景

ADR-0067 は、スレッドの数の指定が無いときの既定を物理コアの数（このプロセスに許された CPU の数で抑えたもの）にした。根拠は 2B の
格子計算の P3（無限希釈の多群定数）の MOC で、1 コア 2 スレッド（SMT）の 16 → 32 スレッドで 12% 遅く、メモリが 8.9 → 11.9 GB に
増えたこと（docs/plans/m2-assembly.md、447e421 と ae658a1、2026-10-08）。xs（crates/xs/src/parallel.rs の `cores`）と、xs の核種の
ステージを流す runner（examples/stage_runner.py の `physical_cores`。ADR-0189、ADR-0193）も同じ規則にしてあるが、xs で SMT を測った
記録は無い。

その後、ADR-0209 の自己遮蔽（自由ガスの核）が燃焼の時間の大半になった。ADR-0213 の最終の版の 2A の燃焼（輸送 81 回）は、r995（16 コア ×
2 スレッド、`lscpu`）の Slurm の timed のジョブで次のとおり（ADR-0213 の「確認」、examples/depletion/verification.md）:

- 16 スレッド（既定。Slurm 580、`lattice` と比較のステージ）: 自己遮蔽の和 2,063.4 秒、MOC 260.8 秒、全体 2,375.5 秒、経過時間 40 分
  10 秒、MaxRSS 12.0 GB
- 32 スレッド（`RAYON_NUM_THREADS=32`。Slurm 579、`lattice` だけ）: 自己遮蔽の和 1,841.4 秒、MOC 301.8 秒、全体 2,194.3 秒、経過時間
  36 分 43 秒、MaxRSS 20.5 GB

MOC は ADR-0067 と同じく 32 スレッドで 16% 遅いが、自己遮蔽が 11% 短くなり、全体は 8% 速い。履歴は `seconds` のほかはビットで同じ
（スレッドの数は結果を変えない。ADR-0198）。

判断の軸:

- 実行速度（結果はスレッドの数に依らないので、速さで決める）
- メモリ（r995 は 91 GB）
- 保守性（並列の仕組みを増やさない）

## 検討した案

- 案 a: lattice の既定を、このプロセスに許された論理 CPU の数（SMT のハードウェアスレッドを含む。`std::thread::available_parallelism`
  で、affinity と cgroup の CPU の上限で抑えた数）にする。2A の燃焼は全体 8% 速い。MOC は 16% 遅いまま
- 案 b: 物理コアの数のまま（ADR-0067）。MOC は速いが、自己遮蔽が支配的な今の燃焼では全体で遅い
- 案 c: 自己遮蔽は論理 CPU の数、MOC は物理コアの数で解く（物理コアの数の rayon のプールをもう 1 つ持ち、MOC をその `install` の中で
  解くか、MOC の並列の塊を物理コアの数に抑える）。取り戻せるのは 2A の MOC の 32 と 16 スレッドの差 41.0 秒（全体の 1.9%）が上限で、
  燃焼、分岐、単一の格子計算の MOC の呼び出しの経路にプールを通し、物理コアの数え方（`num_cpus`）を lattice に残す。実装せず、測らない
- xs（と runner）の既定も論理 CPU の数にする: xs で SMT を測った記録が無く、速くなるかが分からない。`bin/xs` が変わると、`bin/xs` を
  deps にするステージ（examples の dvc.lock で 289。うち VERA、VERA の ENDF/B-VII.0、燃焼、燃焼の p2 の 4 本のライブラリのステージが
  283）が changed になり、ライブラリを作り直すまで、それを上流に持つ lattice のステージを流すと作り直しが始まる

## 決定と理由

案 a。lattice は `RAYON_NUM_THREADS` が無ければ、このプロセスに許された論理 CPU の数で rayon のプールを作る。数が求められなければ
エラーで止める（rayon の既定は 1 にして続けるので、自分で作る）。スレッドの数と、それを決めたもの（既定か `RAYON_NUM_THREADS`）を
始めにログに出す（記録にスレッドの数を書くときに、ログで確かめるため）。

- 2A の燃焼は 32 スレッドで全体 8% 速い（背景）。自己遮蔽のピンはスレッドごとに 1 本ずつ解く（ADR-0198）ので、39 本の解くピンを
  32 本ずつ並べられる
- 案 c は上限 1.9% のために MOC の経路に別のプールを通し、保守の費用に見合わない。MOC が支配的な計算（無限希釈の格子計算、ADR-0067
  の 2B の P3）が本番の時間の大半になったら見直す
- xs と runner は物理コアの数のまま（ADR-0067 の規則を引き継ぐ）。測った記録が無く、変えるとライブラリの作り直しが要るため。xs の
  ライブラリを次に作り直すときに、SMT の効きを測って決め直す

## 確認

- テスト: `crates/lattice/tests/threads.rs` の `uses_every_allowed_logical_cpu_without_rayon_num_threads`（`RAYON_NUM_THREADS` が
  無いとき、ログのスレッドの数がテストのプロセスの `available_parallelism` と同じ）と `uses_rayon_num_threads_when_given`

## 帰結

- ADR-0213 の持つ量の全体は、同時に解きうる減速計算の数（ピンはスレッドの数と解くピンの数の小さい方）で分けるので、2A では 16 から 32 で
  分け、1 本あたりの上限は半分になる。r995 の全体 59 GB ほど（ADR-0213）を 32 で分けて 1.8 GB ほどで、2A のピン（0.39 GB）は全部を持つ
- 2A の MaxRSS は 12.0 → 20.5 GB（Slurm 580 と 579）に増える。同時に解くピンの持つ区間と、スレッドごとの作業の配列が倍になることが
  候補（内訳は測っていない）
- MOC が支配的な計算は SMT で遅くなりうる（ADR-0067 の P3 で 12%、2A の燃焼の MOC で 16%）
- 時間を記録する測定のスレッドの数が r995 の排他のジョブで 16 から 32 になる。ADR-0122 の環境の変更で、時間の表は再測定する
- 燃焼と分岐のチェックポイントの指紋はスレッドの数を含む（ADR-0196）ので、既定の数で始めた途中の結果から、この変更の後には続けない
