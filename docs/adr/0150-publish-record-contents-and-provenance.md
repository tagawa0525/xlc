# ADR-0150: 公開する記録の単位、内容、出所の記録（データカード）、ライセンスを決める

## 背景

ADR-0148 は、公開と引用の置き場を Zenodo にした。Zenodo は 1 レコード 50 GB、100 ファイルまでで、公開した後は消せない
（<https://about.zenodo.org/policies/>、<https://help.zenodo.org/docs/deposit/manage-files/>、2026-10-12）。何を、どの単位で、
どんな出所の記録とライセンスで出すかを決める。

手元にあるもの（2026-10-12 の `du`、`ls`）:

- OpenMC の参照解（`references/openmc/vera-*`、`work-2F` など）: 1 問題が model.xml、summary.h5 と statepoint（約 100 MB）。
  statepoint の大半は源の粒子のバンク（100 万粒子 × 104 バイト = 104 MB。再開と世代の追加に要る）で、標準のタリーの組
  （ADR-0152）を入れた参照解では、それに 集合体で十数〜二十数 MB（小さな実行で測った値。ADR-0152） が加わる。
  `balance-1B` は 20 GB、`balance-2G` は 9.8 GB（世代ごとの statepoint がそれぞれ源の粒子のバンクを持つ。#0096）
- 連続エネルギーのライブラリ: `endfb80`（461 MB）、`endfb80-565`（591 MB）。ENDF/B-VIII.0 から NJOY 2016.79（ACER の
  パッチつき。docs/environment.md）で作った HDF5 の 62〜63 ファイル
- xlc のライブラリ `examples/vera/vera.msgpack`（139 MB。git で追跡しない）と、verification.md が引く結果
- 仕様書の PDF は再配布できない（docs/specs.sha256）ので含めない

判断の軸:

- 受け取った人が、再現するか信頼するかを判断できる出所が付くこと
- 上流（ENDF/B、NJOY、OpenMC）の利用条件に反しないこと
- 公開の後に直せない（レコードは消えない）ので、誤りの出荷を防ぐ確認を前に置けること

## 検討した案

公開の単位:

- 案 A（採用）: 3 つのレコード（概念）を作り、各レコードの版を節目ごとに増やす。(1) 連続エネルギーの核データのライブラリ、
  (2) OpenMC の参照解、(3) xlc の多群ライブラリと結果。参照解は問題ごとに 1 つのアーカイブ（`.tar.zst`）にして、100 ファイルの
  上限に収める。読む人が必要な問題だけ取れる
- 案 B: 全部を 1 レコードにする。ライブラリの更新（NJOY の版など）でも参照解の DOI が変わる。50 GB の上限にも近づく
- 案 C: 1 問題を 1 レコードにする。DOI が数十個になり、版の対応（どの問題がどのライブラリの版か）が分かりにくい

statepoint:

- 案 D（採用）: 最後の世代の statepoint（`statepoint.<世代数>.h5`）、summary.h5、model.xml を一次の成果物にする。statepoint は
  標準のタリーの組（ADR-0152）を持ち、xlc に限らず群ごと、物質ごと、核種ごと、面の量を、読む人が statepoint から
  抜き出せる。model.xml は計算の入力そのもので、summary.h5 は statepoint のフィルタの物質とセルを読むのに要る。抽出した
  結果（`k.json`、`pins.msgpack`、`fuel-xs.msgpack`、`pin-xs.msgpack`、`layers.msgpack`、`assemblies.msgpack` など）は派生物とし、
  作った `extract` のコマンドとコミットをデータカードに書いて添える（statepoint から作り直せる）。途中の世代の statepoint
  （再開のためのもの）は含めない。バランス（balance）の statepoint（20 GB と 9.8 GB）は含めず、抽出した msgpack だけを含める
  （#0096）。総量は、アーカイブを作って測り、50 GB を超えるならレコードを分けるか増量を申請する（総量は未測定。1 問題 100〜
  130 MB で、参照解が 20 問題ほどなら数 GB の見込み）
- 案 E: statepoint を含めず、抽出した結果だけを一次にする。小さくなるが、抽出していない量が要る人は計算をやり直す
  （2D の集合体で 30〜50 分、Problem 3 と 5-2D で 1 本 5〜6 時間）
- 案 F: balance の statepoint も含める。200 GB の増量でも 1 問題で 1/10 を占め、利用の見込みがない

連続エネルギーのライブラリ（ENDF/B-VIII.0 から NJOY で作った HDF5）:

- 案 G（採用）: 利用条件を確認できたときだけ HDF5 を含める。確認できないあいだは、作り方（`openmc-library.toml`、dvc.yaml、
  ENDF のファイルの sha256、NJOY の版とパッチ）だけを公開する。ENDF のファイルは sha256 で固定している（ADR-0124）ので、
  同じライブラリを再現できる。NNDC の ENDF/B-VIII.0 のページ（<https://www.nndc.bnl.gov/endf-b8.0/>）は、利用条件や再配布の
  記述を載せていない（2026-10-12 に取得。条件がないことの確認ではなく、確認できていない）
- 案 H: 確認せずに HDF5 を含める。レコードは消えないので、誤りの訂正が難しい
- 案 I: ライブラリは含めず、作り方だけを常に公開する。再現に 1 時間近く（ADR-0130 の確認で全体 57 分）かかる

ライセンス:

- 案 J（採用）: 参照解と xlc の結果と入力は CC BY 4.0。引用（DOI）を求める。ライブラリの HDF5 は、上流の条件の確認結果に従い、
  その結果をレコードに書く
- 案 K: CC0。引用を求めない。出所の記録（誰がどう作ったか）が付く利点の半分を捨てる
- 案 L: データも MIT/Apache。ソフトウェアの許諾で、データの再利用の条件が曖昧になる

xlc のコードのライセンスは、このリポジトリに LICENSE がなく、Cargo.toml にも license がない（2026-10-12）ので、決まっていない。
データの公開はコードのライセンスに依存しないが、データカードがコードを指すので、決める必要がある（#0095）。Zenodo は公開するファイルの
利用許諾の指定を必須とする（<https://about.zenodo.org/policies/>）。

出所の記録の形（データカード）:

- 案 M（採用）: 各レコードの直下に `README.md`（データカード）と、機械が読む `provenance.json` を置く。内容を下に決める。
  Zenodo のメタデータ（題名、作者、利用許諾、関連識別子）は、同じ値から作る
- 案 N: Zenodo のメタデータの説明欄だけ。構造がなく、検索や検証に使えない

## 決定と理由

案 A、D、G、J、M にする。

データカード（`README.md` と `provenance.json`）の項目:

- xlc のコミット（checkout すれば再現できるもの。ADR-0122）と、`dvc.lock` の md5（その段階の deps と outs）
- OpenMC の版（0.15.2）と NJOY の版（2016.79）とパッチ（docs/patches/）、`flake.lock` の rev、ENDF/B の版と各ファイルの sha256
- 入力: model.xml と入力の TOML、粒子数、世代数、非アクティブバッチ、乱数のシード、スレッド数、標準のタリーの組の版（ADR-0152）
- 結果: k と統計誤差、ファイルの一覧と各ファイルの sha256、一次（statepoint、summary.h5、model.xml）と派生（抽出した結果と、
  作ったコマンド）の別
- 計算機: ホスト名ではなく種類（CPU、コア数、メモリ。ツールが `lscpu` と `/proc/meminfo` から書き、ジョブを流した環境は Slurm のジョブから取る。手元の r995 か、クラウドの機種か）、作った日付。
  外部の計算機で作った結果にも同じ項目を書く（機種が違うと浮動小数点の結果が変わりうるかは確かめていない。同じ種と入力で
  機種が違う k の差を、最初の外部の計算のときに測る）
- 検証の立場: コード同士の検証（verification）であり、実測との比較による妥当性確認（validation）ではない（docs/adr/README.md）

含める・含めないは、既存の方針に従う: 仕様書の PDF は含めない。パッチ、環境変数、run shell で作った試行は含めない（入力と
本番のコードで再現できる結果だけ。CLAUDE.md の「試行は本番のコードに入力ファイルを与えて」）。

理由: 出所が付けば受け取った人が信頼を判断でき、公開が取り消せない以上、含めるものの利用条件の確認を前に置く。ライブラリを
案 G にするのは、上流の条件を確認できていないため。

## 確認

実装の PR で、公開用のアーカイブを作るツールのテスト（出所の項目が欠けたらエラーで止まる、`dvc.lock` の md5 が合わなければ止まる）
と、アーカイブの総量とファイル数（100 以下か。README と provenance.json、問題ごとのアーカイブを数える）の測定を示す。アーカイブに入れるのは `dvc.lock` が出力として挙げるファイルだけで、`dvc.lock` に無い出力（試行のもの）が混ざったら止まるテストも書く。条件の確認（ENDF/B の再配布）の結果は #0095 に書く。

## 帰結

- 公開の前に、(1) ENDF/B-VIII.0 から NJOY で処理した HDF5 の再配布の可否、(2) xlc のコードの LICENSE の有無、(3) 総量の測定が要る
  （#0095）
- verification.md の「計算」の節に、版の DOI を書く。記録は今の姿に書き直す（ADR-0117）ので、DOI は版ごとの識別子を書く
- 参照解を再測定したら（コード、入力、環境の変更。ADR-0122）、新しい版のレコードを作る
