# ADR-0122: 記録の数値はコミットと入力で再現し、試行は本番のコードに入力を与えて行う

## 背景

記録（examples/*/verification.md、docs/issues、ADR）の数値には、測ったときのコミットと日付を添えている（CLAUDE.md、
docs/adr/README.md）。その hash が何のためにあるか、hash が変わったときに何をするか、記録に書く試行（比べたい選択肢の
計算）の入力とツールをどこに置くかを決めていなかった。

- #0005 の候補を量るのに、仮の変更をパッチ（examples/vera/sab_residuals.patch）にし、環境変数で選び、run shell
  （sab_residuals.sh、free_gas_heavy.sh）が sed と Python で入力を組み立ててパッチを当てたソースをビルドした。レビューの
  指摘の大半がこの形から出た: 環境変数が `=0` でも有効になる、前の試行の値が環境に残る、結果が手順でしか再現できない、
  コードが進むとパッチが当たらなくなる
- 「記録に書く測定のコミットは、その結果を出したコード（ツールを含む）を含むコミットにする。rebase で hash が変わったら
  直す」（CLAUDE.md）を、ツールを直すたびに再測定して hash を揃えることと読み、2026-10-11 に #0005 の測定を 2 回、結果を
  変えないツールの直しのために再実行した
- 断面積のファイルや OpenMC の結果は手元に置いて再利用している（キャッシュ）。ツールと核データの固定は #0018 で扱う

判断の軸:

- 記録の数値を、あとから同じ条件で出し直せること
- 試行の選び方を、コードとテストで確かめられる形にすること
- 結果を変えない変更（rebase、文書、コメント、テスト）で計算を再実行しないこと
- main に、使い捨ての試行を積もらせないこと

## 検討した案

- 案 A: パッチ、環境変数、run shell で試行する（#0005 の sab_residuals.patch の形）。本番のコードを変えずに済むが、上の
  レビューの指摘がそのまま残る。環境変数は `=0` や空でも「設定あり」になり、前の試行の値が環境に残って黙って効く。
  パッチはコードが進むと当たらなくなり、手順（パッチを当て、ビルドし、sed で入力を作る）を辿らないと結果を出し直せない
- 案 B: 試行をすべて examples/ に残す。どの試行も出し直せるが、一度しか使わない入力が examples/ に溢れ、繰り返し使う
  ツールと採用した入力が埋もれる
- 案 C: 試行の置き場を `.gitignore` で無視するだけにする。手元の検討には足りるが、記録に数値を書いた試行の入力が
  どこにも残らず、hash を checkout しても出し直せない
- 案 D: ツールを直すたびに測り直し、記録の hash を最後のコミットに揃える。hash が常に新しくなるが、rebase を前提にした
  運用（マージの前に main に rebase する）では hash が変わるたびに再実行することになり終わらない。2026-10-11 に、結果を
  変えない直しのために 2 回再実行した
- 案 E（採用）: 試行は本番のコードに入力ファイルを与えて行い、記録に数値を書く試行の入力だけを `trials/` からコミット
  する。マージの前に残さない試行を消し、残す試行は examples/ に移す。hash は再現のための目印とし、結果を変えない変更
  では測り直さず、ツールで付け替える

## 決定と理由

案 E にする。

記録の数値に添えるコミットの hash は、「その hash を checkout すれば、固定した環境（#0018）のもとで当時の結果を出し
直せる」ためにある。開発の経緯を辿る手がかりとしても残す。バイナリの一致までは求めない。断面積のファイルや結果は手元に
置いて再利用してよいが、hash とコミットした入力から作り直せることは手放さない。

- rebase、文書、コメント、テストの変更で hash が変わっても、測り直さない。hash はツール（git の post-rewrite の hook が
  呼ぶ remap-commit-refs.sh。`remap.commitRefs`）で付け替える
- 再測定するのは、計算を変えたとき（コード、入力、環境）だけにする。そのときは、記録を今の姿に書き直す（ADR-0117）

試行の運用:

- 試行は、本番のコードに入力ファイルを与えて行う。比べたい選択肢が入力で選べないなら、入力で選べる機能として本番の
  コードに足す（既定値は ADR で決める）。パッチ、環境変数、sed や Python で入力を組み立てる run shell は作らない。
  run shell が要るのは足りない機能の印なので、issue に書く
- 手元の検討は、リポジトリの直下の `trials/`（`.gitignore` で無視する）で自由に作って捨てる
- 記録に数値を書く試行だけ、その入力を `git add -f` でコミットし、記録にコミットの hash と入力のパスを書く
- マージの前に、残さない試行を消すコミットを入れる。マージは `--no-ff` で、消す前のコミットは main から辿れるので、
  記録の hash を checkout すれば入力が戻る。残す試行（繰り返し比べるツール）と採用した入力は、examples/<問題>/ に
  `git mv` する。同じコードと同じ入力なので結果は変わらず、測り直さない
- 手で実行した確認も、あとで出し直せるようにスクリプトにする。git に入れるかどうかは、その結果を記録に書くかで決める

入力を本番のコードで読む形にすると、選択肢がコードとテストの対象になり、案 A の指摘（`=0` でも有効、環境に残る値、
当たらないパッチ）が起きる場所がなくなる。hash を目印とし再測定を計算の変更に限ると、案 D の再実行がなくなる。
記録に書いたものだけをコミットし、マージの前に消すと、案 B の氾濫と案 C の出し直せなさを両方避けられる。

## 確認

- `.gitignore` が `/trials` を無視する
- main が `trials/` を追跡しないことを、`cargo test` で走る crates/docs の検査（crates/docs/tests/consistency.rs）が
  確かめる。マージのコミットを作る前の hook が run-checks.sh を通して `cargo test` を実行するので、`trials/` を消し
  忘れたブランチはマージできない。ブランチの上では記録に書いた試行を追跡してよいので、この検査は今のブランチが main の
  ときだけ違反にする
- そのほかは運用の約束事なので、確かめるテストはない

## 結果

- #0005 の試行のツール（examples/vera/sab_residuals.patch、sab_residuals.sh、free_gas_heavy.sh）は案 A の形なので、
  main から消す。#0005 の記録はコミットの hash とパスで指しているので、その hash を checkout すれば出し直せる。続けて
  量る候補は、選択肢を入力で選べる機能として本番のコードに足してから量る
- 固定した環境（ツールと核データの版とハッシュ）は #0018 で整える。それまでは、hash から出し直せるのは
  docs/environment.md の手順の範囲に限られる
- ブランチの上で記録に書いた試行の入力は、マージの前の rebase で hash が変わっても、remap-commit-refs.sh が記録の
  hash を付け替える
