# ADR-0259: examples の計算は 1 ケース 1 ディレクトリに置き、本番はステージ、検討は dvc add と README で残し、ケースの文書を OKF の形で地図から結ぶ

## 背景

examples/ の下は、何がどこにあるかが分かりにくい。置き方の決まりが無いまま、issue ごとの検討が積もっている（ユーザーが
2026-11-19 の相談で指摘した）。

### 置き方の決まりの経緯

- ADR-0116（2026-10-10）は VERA の例だけを決めた（問題ごとの `p<n>/`、共有のライブラリの入力とスクリプトと記録は
  examples/vera/）。帰結は、ほかの例を「題目ごとのディレクトリのまま」とした
- ADR-0122（2026-10-11）の「試行の運用」は、手元の検討を直下の `trials/` に置き、残す試行（繰り返し比べるツール）と採用した入力を
  examples/<問題>/ に `git mv` すると決めた。移した先の中の置き方は決めていない
- ADR-0222（2026-10-31）は、記録と ADR が引く、ステージの出力でない生成物を `dvc add` で追うと決めた。理由の 1 つは、`.dvc` が
  deps もコマンドも持たないので、実行ファイルや上流が変わっても changed にならないことである
- examples/depletion/ の `issue-NNNN` のディレクトリの置き方を決めた ADR、スキル、README は無い（CLAUDE.md、.claude/skills、
  docs/adr/README.md、docs/issues/README.md、docs/plans を `git grep` して、ディレクトリの作り方を書いた文が無いことを見た。
  main 08d0a0d8b、2026-11-19）
- ADR-0258（proposed）の帰結は、検討の計算を DVC のステージにしなくてよいとしている

### ユーザーの決定と案、親のセッションの懸念

親のセッションが示した整理の方向に、ユーザーが返したもの（ユーザー 2026-11-19 の相談の要約）。ユーザーは、自分の判断が
絶対に正しいわけではないとも述べたので、案は事実で比べる。

決定:

- closed の issue の検討の結果は消さない。再検討が要ることも、思い違いで全部をやり直すこともある（現に、取り込む核種を
  思い違いで減らして全部をやり直している）
- 少なくとも本番では、xs、lattice、core まで一貫したステージを組む
- ファイルやディレクトリを動かしても再計算にしない。md5 が同じなら lock のパスを書き換えるだけにする
- 検討と本番の違いを定義する（問い）。同じ相談で、検討の段階に重い足かせを付ける理由が分からないとも述べた

案:

- U1: 1 つのケースに 1 つのディレクトリを作り、入力、出力、結果の要約までをそこに入れる。LLM に書かせられる今は、DVC の yaml と
  lock、背景と目的と分かったことを書いた文書も置く
- U2: ケースの文書は OKF で issue、ADR、検証の記録と結ぶ。examples の全体の地図も OKF の文書にする
- U3: 共通のツールを例と分け、使い方は手引きの文書でなくスキルにする

親のセッションの懸念:

- (a) すべてのケースに `dvc.yaml`、lock、文書を求めると、検討を 1 つ流す手数が増える
- (b) `.dvc` で保管している検討をステージにすると、ステージの数が増え、DVC の固定費（#0268）が延びる
- (c) 背景、目的、分かったことをケースの文書にも書くと、同じ結論が複数の場所に載り、食い違いうる
- (d) ケースのディレクトリを動かすと、入力の TOML の中の相対パスを書き換えることになり、入力の md5 も値の正規形も変わる
- (e) 使い方をスキルに書くと、ツールの docstring や `--help` と二重になる

### 判断の軸

- (1) ファイルがどのケースのものかが、場所で分かること
- (2) ケースごとに、何の問いの計算で、結果がどこにあるかを、そのディレクトリで読めること
- (3) 記録と ADR が引く結果を、検討でも本番でも、出どころ（入力、コード、上流の出力）まで辿れること（ADR-0122）
- (4) 作り直しの残高（ADR-0258 の changed）に、再実行しないものを混ぜないこと
- (5) 検討を 1 つ流す手数を増やさないこと
- (6) 同じ結論を 2 か所に書かないこと
- (7) 置き直しで再計算を起こさないこと

## 検討した案

### ケースの単位と、形を求める時点

- 案 A1: 今のまま。issue ごとに 1 つのディレクトリを作り、中の形は検討ごとに任せる。背景の `issue-0286` の形（350 ファイルが
  平たく並ぶ）が増える。軸 (1) と (2) を満たさない
- 案 A2（案 U1）: 流す計算のすべてを、始めからケースの形（ディレクトリ、`dvc.yaml`、lock、文書）にする。問いが定まる前の試しにも
  形を求めることになり、軸 (5) を満たさない（懸念 (a)）
- 案 A3（採用）: 1 つの問いに答える計算の組を 1 ケースとし、ケースごとに 1 つのディレクトリを作る。形を求めるのは、記録、ADR、
  issue がその結果を引くときからにする。それまでの試しは `trials/`（ADR-0122）のまま自由にする

### closed の issue の検討

- 案 B1（親のセッションが出した案）: closed の issue の検討を examples から片付ける（消すか、別の置き場に移す）。採らない。
  ユーザーが退けた（ユーザー 2026-11-19）。閉じた後も、再検討が要ることと、思い違いで全部をやり直すことがある。数でも、
  closed の 9 個はどれも外から引かれ、open の `issue-0286` は closed の `issue-0274` の入力から自分の入力を作っている（背景）
- 案 B2（採用）: closed でも消さず、ほかのケースと同じ形で残す

### 本番と検討の違いと、出力の追い方

- 案 C1: 今の姿。本番はステージ、検討は `dvc add` で、検討のディレクトリに文書は無い。何の問いの計算で、どのコミットで流したかを、
  記録か issue を探さないと読めない。軸 (2) を満たさない
- 案 C2: 設定の厳密さで分ける（CLAUDE.md の「本番は既定、結論が ±20 pcm で変わらない検討は簡易でよい」。ADR-0197）。これは
  計算の設定の線で、置き方と作り直しの扱いを決めない。この線はそのまま残す
- 案 C3（親のセッションの案。案 U1 の `dvc.yaml` と lock を含む）: 記録の残し方には違いを置かず、検討もステージにする。違いは
  作り直しの扱いだけで、検討は答えが出たら DVC の `frozen: true` で凍結し、changed に数えない。`frozen: true` は、ステージの deps の
  変更を `dvc status` から外す（「## 補足」の測定）。lock の deps の md5 が、読んだ上流の出力とコードの正規形を残す。成り立つが、
  次の費用がある
  - 入力の TOML は値の正規形で deps にする（ADR-0254）ので、検討の入力 1 本ごとに、直下の `dvc.yaml` の `toml-values` のステージと、
    git で追跡する正規形のファイルが 1 つずつ増える（今は 436）。`.dvc` の 612 件をステージにすると、同じ桁の数が加わる（懸念 (b)）
  - ステージは `bin/` の実行ファイルで流す。ブランチのコードで流す検討は、`build` で `bin/` を作り直し、上流のステージが changed の
    まま目標だけを流す経路（ADR-0258 の `-s` の経路。まだ実装されていない）が要る（懸念 (a)）
  - 凍結したステージの lock を守る仕組みが要る。cmd を変えた frozen のステージに `dvc repro -f` を実行すると、cmd を実行しないまま、
    lock の cmd と deps の md5 が今の値に書き換わった（「## 補足」の測定）
  - 既存の検討には使えない。計算をやり直さずに lock を作る `dvc commit` は、今の deps の md5 を lock に書く（「## 補足」の測定）。
    出力を作ったのでないコードの正規形が、作ったものとして記録される
- 案 C4（採用）: 作り直しの扱いで分け、出力の追い方をそれに合わせる。本番は、今のコードと入力の結果を保つケースで、ステージで
  流し、changed を作り直しの残高に数える。検討は、問いに答えた時点のコードと入力の結果を残すケースで、出力を `dvc add` で追い
  （ADR-0222 のまま）、実行したコミットを README.md に書く。`.dvc` は deps を持たないので、changed にならず、凍結の仕組みが
  要らない。出どころは、実行したコミットと、コミットした入力で辿る（ADR-0122）。案 C3 と比べて失うのは、読んだ上流の出力の md5 の
  機械的な記録である。上流がステージの出力なら、実行したコミットの上流の `dvc.lock` の outs から md5 を引けるが、実行したときの
  作業ツリーが lock のとおりだったことは記録されない

固定費の測定（main 08d0a0d8b と同じ木の worktree、出力を戻していない状態、手元、各 1 回、2026-11-19）: `dvc status --json` は、
`.dvc` の 1 件で 0.39 秒、4 ステージの `dvc.yaml` の 1 ステージで 0.38 秒、656 ステージの p2 の `dvc.yaml` の 1 ステージで 1.95 秒。
目標を指定した 1 操作の時間は、その `dvc.yaml` の大きさで決まり、ケースごとの小さな `dvc.yaml` は `.dvc` と変わらない。案 C3 の
費用は、1 操作の時間でなく、上の正規形のステージの数と、全体の `dvc status`（#0268 の「経緯」の 2026-11-19 の項）に出る。

### ケースの文書の中身

`issue-0283` と `issue-0045` で、2 つの形を試しに書いて比べた（ブランチには入れていない。2026-11-19）。

- 案 D1（案 U1 の文書）: 背景、目的、入力と実行、分かったことを README.md に書く。`issue-0283` では 29 行で、#0283 の「切り分け」に
  ある数値を 6 個コピーした。`issue-0045` では 14 行で、#0045 と ADR-0185 にある数値を 5 個コピーした。どちらも、新しい内容は入力と出力の
  対応だけで、背景と結論は issue の文の言い換えになった。issue か記録を直したときに、README.md が古いまま残りうる（懸念 (c)）
- 案 D2（採用）: README.md は、問い（表題）、結ぶ issue と ADR、結果と解釈の置き場（1 か所）、実行したコミット、入力と出力の一覧に
  とどめる。`issue-0283` で 31 行、`issue-0045` で 23 行で、ほかの文書の数値をコピーしなかった。ディレクトリを開いた読み手は、何の問いの
  計算かと、どのファイルがどの条件かを README.md で読み、結論は指された 1 か所で読む

### OKF で結ぶ方法

`design-records check` は、バンドルのルートを `docs` に固定している（claude-harness の `crates/design-records/src/okf.rs` の
`BUNDLE_ROOT`。c958f33a、2026-11-19）。examples の下は検査しない。OKF v0.3 の仕様（ADR-0256 が引く原典。コミット 527e81af）で
関わる点は次のとおり。

- §2: バンドルが大きなリポジトリの下位のディレクトリのとき、フロントマターを持つルートの `index.md` がバンドルのルートを示す
- §3.2: ルートの下の `.md` のうち、空でない `type` を持つものが概念である
- §6: リンクと、パスを値に持つ項目は、バンドルのルートの外に解けると外部のものとして扱われ、consumer は読まない
- §5.4: `status` は `draft`、`stable`、`deprecated` で、`deprecated` の文書は `superseded_by` で置き換えた先を指せる
- §8: `index.md` は、ディレクトリの中身を、開く前に見渡せるように並べる

xlc の文書どうしの参照は、Markdown のリンクでなく番号（`ADR-NNNN`、`#NNNN`）で書く（docs/adr/README.md）。番号の先が実在するかは
crates/docs の検査が見ており、examples の下の .md も既に読む（`crates/docs/src/check.rs` の `scanned_for_refs` と
`scanned_for_links`）。番号の参照は OKF のリンクではないので、どの案でも、ケースと issue や ADR の結びは番号とその検査で保つ。
案を分けるのは、ケースの文書が概念として索引に載るかと、形を何が検査するかである。

- 案 K1: examples/ を docs/ と別の 2 つ目のバンドルにする（examples/index.md のフロントマターに `okf_version`）。ケースの
  README.md と検証の記録が概念になり、ディレクトリごとの `index.md` が、その下のケースを 1 文の説明つきで並べる。`design-records`
  を、`okf_version` を持つ `index.md` のあるディレクトリをバンドルのルートとして見つける形に広げる必要がある（claude-harness の
  変更）。ケースのディレクトリごとに README.md の 1 行だけの `index.md` が要り、ケースの一覧は地図（下）と `index.md` の 2 か所に
  載る。`kind` などケースに固有のキーは `design-records` が知らないので、その検査は案 K3 と同じく crates/docs に書く
- 案 K2: バンドルのルートをリポジトリの直下に上げ、docs/ と examples/ を 1 つのバンドルにする。`design-records` の変更は案 K1 と
  同じ種類である。加えて、直下の CLAUDE.md が `type` の無い .md として違反になり（claude-harness の ADR-0092 の決まり）、ADR-0256 の
  決定（ルートは docs/）を変える。得るのは Markdown のリンクがバンドルの中の辺になることだが、xlc の参照は番号なので辺が少ない
- 案 K3（勧める）: ケースの README.md を OKF の概念の形（`type`、`title`、`description`、`status`）で書き、docs/ のバンドルに
  地図の文書を 1 つ置いて、ケースの一覧と辺をそこに描く。`design-records` を変えずに済む。README.md の形は crates/docs が検査する。
  短所は、README.md がどのバンドルの概念でもないこと（docs/ から見ると外部のファイル）
- 案 K4: ケースの文書を docs/cases/ に置き、examples のディレクトリをパスで指す。文書が今のバンドルの概念になるが、ケースの
  ディレクトリに文書が無くなり、軸 (2) を満たさない

### 共通のツールの置き場と使い方

- 案 T1: `scripts/` に移す。`scripts/` は今、hook、DVC の実行の入口、正規形のスクリプトを持つ（27 ファイル）。計算の入力と結果を
  扱うツールが混ざり、変えると例のステージが changed になるものが場所で分からなくなる
- 案 T2（採用）: リポジトリの直下に `tools/` を作り、2 つ以上のケースのステージか記録の手順が呼ぶ計算のツール（OpenMC の駆動、
  AWS、比較、記録の表と出どころ）を置く。ステージを流す入口の `stage_runner.py` は、同じ役割の `scripts/dvc-repro.py` のある
  `scripts/` に置く
- 案 T3: examples の中に共通のディレクトリ（examples/common/ など）を作る。import のパスの変更は小さいが、例とツールが同じ木に残る

使い方の置き場:

- 案 S1: `tools/` に手引きの文書（README）を置く。ユーザーが退けた（案 U3）
- 案 S2（案 U3 をそのまま読んだ形）: 引数と使い方をスキルに書く。今のツールは docstring に使い方を持つ（`record_provenance.py` の
  先頭の「使い方」など）ので、同じ説明が 2 か所になる（懸念 (e)）
- 案 S3（採用）: スキルには、いつ、どのツールを使うかと、呼び方の入口だけを書く。引数の説明は、ツールの docstring と `--help` の
  1 か所に置く

### 既存のディレクトリの合わせ方と、置き直し

入力の TOML は、上流の出力を相対パスで読む（`library = "../p2/depletion.msgpack"`）。ケースのディレクトリの深さを変えると、
この値を書き換えることになり、入力の md5 も値の正規形（ADR-0254）も変わる。「md5 が同じなら lock のパスを書き換えるだけ」は、
この移動には当たらない（懸念 (d)）。検討は lock を持たないので changed にはならないが、今の入力が、実行したコミットの入力と
違うものになる。追跡している入力は検討の出どころで、#0291 は、入力を書くスクリプトを再実行すると値が変わる検討（`issue-0045`、
`issue-0129` など）でも、追跡している入力を書き換えずに残した（#0291 の「経緯」の 2026-11-19 の項）。

- 案 M1: 既存の `issue-NNNN` を新しい置き場（下位のケースのディレクトリ）に動かす。下位の無いディレクトリを 1 段下ろし、直下の
  ファイルを使うケースに移す。上の理由で入力を書き換えることになり、21 件の ADR と記録が書くパスも古くなる。採らない
- 案 M2（採用）: 既存の検討は動かさない。今の `issue-NNNN/` か、その題目の下位を、そのままケースとみなし、README.md を足す。
  直下に複数の問いのファイルが並ぶもの（`issue-0286`、`issue-0133` の直下）は、1 つの README.md に、問いごとのファイルの組を
  表で書く。新しい置き場は、これから作るケースに当てる
- 案 M3: 既存の検討を、`dvc.yaml` と `dvc.lock` を持つ形に直す。案 C3 の最後の項の理由（`dvc commit` が今の deps を書く）で採らない

本番とツールの置き直し（cmd と deps のパスが変わり、lock を持つ）:

- 案 R1（採用）: 次の本番の作り直し（ADR-0258 の「changed の扱い」）の直前にまとめる。置き直しで changed になっても、続く
  作り直しが埋める
- 案 R2: 置き直しを先に行い、パスの書き換えを結果を変えない変更として lock に書く。相対パスを持つ入力の正規形と cmd の文字列が
  変わるので、md5 の一致だけでは判定できず、「書き換えたのはパスだけ」を確かめる仕組みが ADR-0258 の側に要る。その仕組みが
  入れば、作り直しを待たずに置き直せる

## 決定と理由

案 A3、B2、C4、D2、K3、T2 と S3、M2、R1 にする（proposed）。ユーザーの案 U1 のうち 1 ケース 1 ディレクトリは採り、すべての
ケースに `dvc.yaml` と lock を置くこと（案 C3）と、背景と結論を README.md に書くこと（案 D1）は、上の比較の理由で採らない。
案 U2 は、ケースの文書を OKF の概念の形にし、地図を OKF の文書にする形で採り、examples の全体をバンドルにすること（案 K1）は
勧めない。案 U3 は、引数の説明をツールの側に置く形（案 S3）で採る。本番と検討の定義（案 C4）、README.md の中身（案 D2）、
OKF の結び方（案 K3）は、ユーザーが読んでから確定する。

### ケースとディレクトリ

- ケースは、1 つの問いに答える計算の組である。ケースごとに 1 つのディレクトリを作り、次を置く
  - 入力（TOML と、このケースだけが使うスクリプト）
  - 出力。重い出力は DVC で追い、数十 KB までの要約（比較の JSON）は git で追跡する（ADR-0176 と同じ）
  - 本番のケースは `dvc.yaml` と `dvc.lock`、検討のケースは出力ごとの `.dvc`
  - `README.md`（下の「ケースの文書」）
- 形を求める時点: 記録、ADR、issue に、その計算の結果（数値か、結果から出した結論）を書くコミットで、ケースのディレクトリと
  README.md がそろっていること。それまでの試しは、直下の `trials/` で自由に作って捨てる（ADR-0122 の「試行の運用」）。ADR-0122 の
  「残す試行と採用した入力は examples/<問題>/ に `git mv` する」の移す先は、ケースのディレクトリである
- ケースのディレクトリには、そのケースのものだけを置く。2 つ以上のケースが使うスクリプトは `tools/` に置き（下の「共通の
  ツール」）、ほかのケースの出力は、そのケースの場所から読む（コピーしない）
- 新しいケースは入れ子にしない。ディレクトリは、ケースであるか、ケースを束ねるだけかのどちらかにする
- 新しいケースの置き場
  - 本番: `examples/<問題>/<ケース>/`（VERA の `p<n>/` は ADR-0116 のまま、この形に当たる）
  - 検討: `examples/<問題>/issue-NNNN/<ケース>/`。`NNNN` はきっかけの issue で、`issue-NNNN/` は束ねるだけにする。issue の無い
    検討は、issue を起こしてから置く。ケースの名前は、問いを表す英語の kebab-case にする
  - ケースが 1 つだけの問題（examples/m0 など）は、問題のディレクトリをケースのディレクトリにする
- closed の issue のケースも消さない（案 B2）。再検討は、元のケースを書き換えず、新しいケースとして流す

### ケースの文書

ケースのディレクトリに `README.md` を置き、OKF の概念の形で書く。ひな形:

```markdown
---
type: Case
title: <問いを 1 行で>
status: draft          # draft（進行中） | stable（答えが出た） | deprecated（置き換えたか、誤りと分かった）
superseded_by:         # status: deprecated で、置き換えたケースがあるときだけ。その README.md へのパス
kind: study            # production（本番） | study（検討）
issues: ["#NNNN"]      # きっかけの issue と、結果を使った issue
adrs: [ADR-NNNN]       # 結果を根拠にした ADR
answer: "#NNNN の「<節>」"   # 結果と解釈の置き場を 1 か所。issue の節、ADR の節、検証の記録の節のどれか
upstream: [../../p2]   # 出力や入力を読むケースのディレクトリ
tracking: dvc-add      # stage（dvc.yaml と dvc.lock） | dvc-add（.dvc） | none（出力を追跡していない）
ran-at: [0123abcd]     # 検討だけ。実行したコミット（8 桁）
ran-on: 2026-11-19     # 検討だけ。実行した日
---

# <title と同じ>

結果と解釈は <answer と同じ場所> にある。

## 入力と出力

入力のファイル、替えた条件、出力のファイルの対応（表）。流し方（コマンドか、ステージの名前）。

## 結果の数値

比較の JSON を持つケースだけ。ツールが JSON から描く表（手で直さない）。無ければ節ごと省く。
```

- 背景、目的、解釈は README.md に書かず、`answer` の 1 か所に置く（案 D2）。検討は issue の節か ADR、本番は検証の記録の節が
  普通である。README.md に書く数値は、ツールが比較の JSON から描く表だけにする（検証の記録の表と同じ形。ADR-0176）
- `status` は OKF の値（§5.4）をそのまま使う。新しい `type` なので、ADR と issue の `status` の値の食い違い（ADR-0256 の帰結）を
  持ち込まない。`deprecated` は、新しいケースが置き換えたときと、誤りと分かったときに書き、ファイルは消さない
- `issues`、`adrs` は ADR と issue のフロントマターと同じ番号の書き方にする。番号の先が実在するかは、crates/docs の今の検査が
  見る。OKF は拡張のキーに `x-<producer>-<name>` の名前を勧めるが（§4.1）、xlc の ADR と issue のキーに合わせて接頭辞を付けない
- `upstream` は、検討では手で書く（`.dvc` は deps を持たない）。本番では、地図のツールが `dvc.lock` の deps から出した辺と照らす
- 本番のケースは `ran-at` と `ran-on` を書かない。作り直しのたびに変わり、`dvc.lock` と記録が持つ（`record_provenance.py`）

### 本番と検討

違いは作り直しの扱いで、出力の追い方をそれに合わせる。

- 本番（`kind: production`）: 今のコードと入力の結果を保つケース
  - ステージ（`dvc.yaml` と `dvc.lock`）で流す
  - 入力は、上流のケースのステージの出力か、固定した外部のデータ（評価済み核データ、仕様書の参照解）だけにする。`dvc add` した
    中間のファイルを読まない
  - 設定は ADR で決めた既定にする（CLAUDE.md の方針）
  - changed は作り直しの残高に数え、作り直しのときに上流から一揃いで再実行する（ADR-0258）
  - 参照解（OpenMC）のステージは本番のケースに置き、再実行するかは今までどおり ADR-0130 と ADR-0184 に従う
- 検討（`kind: study`）: 問いに答えた時点のコードと入力の結果を残すケース
  - 本番の実行ファイルに入力を与えて流し（ADR-0122）、記録、ADR、issue が引く出力を `dvc add` で追う（ADR-0222）
  - 出どころは、README.md の `ran-at`（実行したコミット）と、コミットした入力で残す。本番の出力を読んでよく、読んだケースを
    `upstream` に書く
  - 設定は、結論が変わらない範囲で簡易でよい（CLAUDE.md の ±20 pcm の線。ADR-0197）
  - 答えが出た後は、コードや上流が変わっても再実行しない。`.dvc` は changed にならないので、作り直しの残高に入らない。再検討が
    要るときは、新しいケースとして流す
  - ケースの中で後段が前段の出力を読み、再実行を DVC に任せたい検討は、ステージで流してよい。その場合は、README.md を
    `status: stable` にするコミットで、そのケースのすべてのステージに `frozen: true` を書く（案 C3 の測定の注意のとおり、凍結した
    ステージには `dvc repro -f` を実行しない）
- CLAUDE.md の「本番は既定、結論が ±20 pcm で変わらない検討は簡易でよい」は設定の線で、上の定義と両立する

理由: 本番は、数日から 1 週間の作り直し（ADR-0258 の背景）の中で、どこから下が古いかを機械が示す必要があるので、ステージと
lock が要る。検討は再実行しないので、古さの判定が要らず、要るのは出どころだけである。出どころは実行したコミットと入力で
辿れ（ADR-0122）、`.dvc` はそれを changed なしで保つ（ADR-0222 の理由）。検討をステージにする案 C3 は、読んだ上流の md5 を機械が
記録する点で優れるが、入力ごとの正規形のステージ、`-s` の経路、凍結の守りを、再実行しない計算のために足すことになる。

### 本番のチェーン

本番は、xs、lattice、core までを一貫したステージにする（ユーザー 2026-11-19）。

- 本番のケースどうしの辺は、すべて `dvc.yaml` の deps と outs に書く。`dvc.yaml` はケースごとに分かれるが、DVC は deps と outs の
  パスでリポジトリの全体を 1 つのチェーンとして扱うので、下流のケースを目標にした `dvc repro` が上流のケースから流す
- 入力の TOML が相対パスで読むファイルは、そのステージの deps に書く。書き漏れは、地図のツールが入力のパスと deps を照らして
  見つける
- 今の切れ目は、テーブルから炉心の燃焼への接続である（背景）。ステージにするのは、炉心の計算が読むテーブルと、その上流の
  集合体の燃焼の履歴とブランチ計算である。今の置き場では、examples/depletion の `branches`（`.dvc` 59）、`history`（44）、
  `p9-gd`（24）のうち、炉心の入力（p9-timing の `core-p9`）と記録の今の姿が読むもの。どのファイルが本番で、どれが検討かは、
  移行の段 3 でファイルごとに決める
- 本番のステージは、定義（`dvc.yaml`）を先に書き、`dvc.lock` は次の本番の作り直しで埋める。今の `.dvc` の出力に `dvc commit` で
  lock を付けない（案 C3 の最後の項の理由）。作り直すまで、炉心の入力は今の `.dvc` のテーブルを読み続ける

### OKF と地図

- ケースの README.md は、上のひな形の OKF の概念の形で書く。examples はバンドルにしない（案 K3）
- examples の全体の地図を、docs/ のバンドルの文書 docs/examples.md（`type: Reference`）に置く
- 機械的に出せる部分は、ツール（`tools/` に置く）が表に描き、手で直さない（検証の記録の `<!-- table: -->` と同じ形。ADR-0176）
  - ケースの一覧: パス、`title`、`kind`、`status`、`issues`、`tracking`（README.md のフロントマターから）
  - ケースごとのステージの数（`dvc.yaml` と `dvc.lock`）と `.dvc` の数
  - ケースの間の辺: `dvc.lock` の deps から出る辺と、README.md の `upstream` の辺。本番の入力の TOML が読むパスのうち、deps に
    無いものは違反として出す
  - README.md の無いディレクトリの数（移行の残り）
- 手で書く部分は、チェーンの読み方（どの問題がどの問題の上流か）と、置き方の決まりへの参照だけにする。ケースごとの問いは README.md の
  `title` が持つので、地図に重ねて書かない
- 地図が今の木と合っているかと、README.md のフロントマター（キー、`kind`、`status`、`tracking` の値、`answer` があること、
  `status: stable` の検討のステージが frozen であること）は、crates/docs の検査か pre-commit の hook が確かめる
- issue と ADR の側には、ケースの一覧を書かない。issue からケースを探すときは、地図の `issues` の列か、`issue-NNNN` の
  ディレクトリの名前で引く

理由: 結びに要るのは、ケースから issue と ADR への番号の参照と、その先が実在することの検査で、どちらも今の crates/docs の
検査の範囲にある。案 K1 が足すのは、`design-records` による `type` と索引の検査と、ディレクトリごとの `index.md` だが、ケースの
一覧は地図のツールが描くので、`index.md` は同じ一覧のもう 1 つのコピーになる。別のリポジトリ（claude-harness）の変更を前提に
するだけの利点が無い。examples を読む OKF の consumer を使うようになったら、案 K1 に進む（README.md の形は変えずに済む）。

### 共通のツール

- `tools/` に、2 つ以上のケースのステージか記録の手順が呼ぶ計算のツールを置く（案 T2）。今の examples の直下の
  `openmc_*.py`、`record_provenance.py`、`verification_tables.py` とそのテスト、examples/aws、問題の直下にあって複数のケースが呼ぶ
  スクリプト（examples/depletion の `compare_*.py`、examples/vera の `compare_*.py` と `openmc_*.py` など）。中の分け方
  （OpenMC、AWS、比較、記録）は移行の段 4 で決める
- `stage_runner.py` とそのテストは `scripts/` に置く
- 1 つのケースだけが使うスクリプトは、そのケースのディレクトリに置く
- スキルには、いつ、どのツールを使うかと、呼び方の入口だけを書く（案 S3）。今のスキル openmc-reference（OpenMC と AWS）、
  verification-record（記録の表と出どころ）、compute（ステージの実行）が入口を持つ。引数の説明は、ツールの docstring と `--help` に
  置き、スキルにコピーしない。`tools/` に手引きの文書は置かない

### 既存のディレクトリの合わせ方

- 既存の検討は動かさない（案 M2）。`issue-NNNN/` の名前も変えない
  - 題目の下位を持つもの（`issue-0133`、`issue-0274`、`issue-0180`、`issue-0292`、`issue-0293` など）: 下位をそのままケースとし、
    README.md を足す。直下のファイルは動かさず、`issue-NNNN/` の README.md に、どのファイルがどの下位のものかを書く
  - 直下に複数の問いの入力が平たく並ぶもの（`issue-0286`）: `issue-NNNN/` を 1 つのケースとし、README.md の「入力と出力」に、
    名前の接頭辞の組ごとの問いを表で書く
  - 下位の無いもの（`issue-0045`、`issue-0283` など）: `issue-NNNN/` をそのままケースとし、README.md を足す
- `tracking` は今のまま書く（`dvc-add` か `none`）。`ran-at` には、記録か issue が書くコミットか、`record_provenance.py` が `.dvc` の
  履歴から出すコミットを書く
- 3 つを読んだ範囲の案なので、ケースの分け方は、ディレクトリごとに中身を読んで決める

### 移行

ファイルやディレクトリを動かしても再計算にしない（ユーザー 2026-11-19）。この ADR は、次の 2 つでそれを満たす。

- 検討は動かさない（案 M2）
- 本番とツールの置き直しは、次の本番の作り直しの直前にまとめる（案 R1）。パスの書き換えを結果を変えない変更として扱う仕組みが
  ADR-0258 に入れば（別のブランチ docs/0258-settle-open-points で書いている。main 08d0a0d8b の ADR-0258 にはまだ無い）、
  作り直しを待たずに置き直してよい（案 R2）。入力を書き換えずにディレクトリごと動かせる場合（中の相対パスが変わらない移動）は、
  outs のパスは `dvc.yaml` からの相対なので変わらず、ディレクトリの外を指す deps のパスだけが変わる（「## 補足」の測定）

段ごとに 1 本のブランチにする。決まりと地図を先に、既存のディレクトリを合わせる作業を後にする。

1. 決まりと地図。この ADR を確定する。置き方の決まりをスキルに書き、CLAUDE.md から指す。地図のツールと README.md の検査を TDD で
   作り、docs/examples.md と hook を足す。ファイルは動かさない
2. 既存の検討に README.md を足す。closed の 9 個から先に、ディレクトリごとか数個ごとのブランチで足す。open の 10 個は、
   その issue を扱うブランチの中か、閉じるときに足す。ファイルは動かさない
3. 本番のチェーン。examples/depletion の `branches`、`history`、`p9-gd`、`micro` などと直下のステージを、本番と検討に分け、本番の
   ステージの定義と README.md を書く。lock は本番の作り直しで埋める
4. 本番とツールの置き直し。共通のツールを `tools/` と `scripts/` に、本番のケースを新しい置き場に移す。次の本番の作り直しの
   直前のブランチにする（案 R2 の仕組みが入れば先に行う）
5. VERA と小さい例。README.md を足す。examples/vera の直下のステージ（ライブラリ、参照解のライブラリ、問題 1 と 2）を
   ケースのディレクトリに移すかは、段 4 と同じ時期に決め、移すなら ADR-0116 の決定を「## 変更」で直す

### DVC の測定

DVC 3.67.1、一時のリポジトリ（xlc の外）、手元、2026-11-19。dep を 1 つ読んで out を 1 つ書くステージ（単独と foreach）を
`dvc repro` で流してから、次を見た。

- dep を変えると、`dvc status --json` は 3 つのステージに `changed deps` を出した。`frozen: true`（foreach では `do:` の下）を
  書くと、同じ状態で `{}` になり、ステージごとに「is frozen. Its dependencies are not going to be shown in the status output」の
  警告が出た
- frozen のまま `dvc repro` を実行すると、ステージは実行されず、`dvc.lock` は変わらなかった
- frozen のステージの out を書き換えると `changed outs`、cmd を書き換えると `changed command` が出た
- cmd を書き換えた frozen のステージに `dvc repro -f` と `dvc repro -s -f` を続けて実行すると、cmd は実行されず（out は元のまま）、
  「Verifying outputs in frozen stage」と出て、lock の cmd と dep の md5 が今の値に書き換わった（どちらの呼び出しが書き換えたかは
  分けていない）
- ケースのディレクトリを別の場所に動かすと、frozen のままでは `dvc status` は `{}`、frozen を外すと、ディレクトリの外の dep
  （`../up/a.txt`）が `deleted` と出た。outs は変わらなかった
- 実行したことの無いステージ（cmd、dep、既にある out）に `dvc commit -f` を実行すると、今の dep の md5 と out の md5 を持つ
  lock ができ、`dvc status` は `{}` になった
