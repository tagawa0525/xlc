# ADR-0259: examples の計算は 1 ケース 1 ディレクトリに置き、本番も検討もステージで流して検討は凍結し、ケースの文書を結果の置き場にして OKF で結ぶ

## 背景

examples/ の下は、何がどこにあるかが分かりにくい。置き方の決まりが無いまま、issue ごとの検討が積もっている（ユーザーが
2026-11-19 の相談で指摘した）。

### 置き方の決まりの経緯

- ADR-0116（2026-10-10）は VERA の例だけを決めた（問題ごとの `p<n>/`、共有のライブラリの入力とスクリプトと記録は
  examples/vera/）。帰結は、ほかの例を「題目ごとのディレクトリのまま」とした
- ADR-0122（2026-10-11）の「試行の運用」は、手元の検討を直下の `trials/` に置き、残す試行（繰り返し比べるツール）と採用した入力を
  examples/<問題>/ に `git mv` すると決めた。移した先の中の置き方は決めていない
- ADR-0222（2026-10-31）は、記録と ADR が引く、ステージの出力でない生成物を `dvc add` で追うと決めた。理由の 1 つは、`.dvc` が
  deps もコマンドも持たないので、実行ファイルや上流が変わっても changed にならないことである
- examples/depletion/ の `issue-NNNN` のディレクトリの置き方を決めた ADR、スキル、README は無い（CLAUDE.md、.claude/skills、
  docs/adr/README.md、docs/issues/README.md、docs/plans を `git grep` して、ディレクトリの作り方を書いた文が無いことを見た。
  main 08d0a0d8b、2026-11-19）
- ADR-0258（proposed）の帰結は、検討の計算を DVC のステージにしなくてよいとしている

### ユーザーの決定と案、親のセッションの決定

親のセッションが示した整理の方向に、ユーザーが返したもの（ユーザー 2026-11-19 の相談の要約）。ユーザーは、自分の判断が
絶対に正しいわけではないとも述べたので、案は事実で比べる。

ユーザーの決定:

- closed の issue の検討の結果は消さない。再検討が要ることも、思い違いで全部をやり直すこともある（現に、取り込む核種を
  思い違いで減らして全部をやり直している）
- 少なくとも本番では、xs、lattice、core まで一貫したステージを組む
- ファイルやディレクトリを動かしても再計算にしない。その仕組みを早く入れる（仕組みは ADR-0258 の側で決める）

ユーザーの案と問い:

- U1: 1 つのケースに 1 つのディレクトリを作り、入力、出力、結果の要約までをそこに入れる。LLM に書かせられる今は、DVC の yaml と
  lock、背景と目的と分かったことを書いた文書も置く
- U2: ケースの文書は OKF で issue、ADR、検証の記録と結ぶ。examples の全体の地図も OKF の文書にする
- U3: 共通のツールを例と分け、使い方は手引きの文書でなくスキルにまとめる
- 検討と本番の違いは何か。検討の段階に重い足かせを付ける理由は分からない。検討を本番のチェーンから切れないのか

親のセッションの決定（ユーザーが、1 つの長い文書と分散した文書のどちらが整理しやすいかの問題なので任せるとした）:

- ケースの背景、目的、分かったことは、ケースの文書を 1 か所の置き場にする。検証の記録と issue は、同じ内容を繰り返さず、
  ケースの文書を引く

### 判断の軸

- (1) ファイルがどのケースのものかが、場所で分かること
- (2) ケースごとに、なぜ流し、何が分かったかを、そのディレクトリで読めること
- (3) 記録と ADR が引く結果を、検討でも本番でも、出どころ（入力、コード、上流の出力）まで辿れること（ADR-0122）
- (4) 作り直しの残高（ADR-0258 の changed）に、再実行しないものを混ぜず、検討が本番の作り直しに巻き込まれないこと
- (5) 問いが定まる前の試しに、形を求めないこと
- (6) 同じ結論を 2 か所に書かないこと
- (7) 置き直しで再計算を起こさないこと

## 検討した案

### ケースの単位と、形を求める時点

- 案 A1: 今のまま。issue ごとに 1 つのディレクトリを作り、中の形は検討ごとに任せる。背景の `issue-0286` の形（350 ファイルが
  平たく並ぶ）が増える。軸 (1) と (2) を満たさない
- 案 A2: 流す計算のすべてを、始めからケースの形にする。問いが定まる前の試しにも形を求めることになり、軸 (5) を満たさない
- 案 A3（採用）: 1 つの問いに答える計算の組を 1 ケースとし、ケースごとに 1 つのディレクトリを作る。記録、ADR、issue に結果を
  書く計算は、ケースのディレクトリで流す。書かない試しは `trials/`（ADR-0122）のまま自由にする
- 案 A4: 試しは `trials/` で流し、結果を引くと決めたときに、出力ごとケースのディレクトリに移す。`trials/` とケースの
  ディレクトリは深さが違うので、入力の TOML の中の相対パス（`library = "../p2/depletion.msgpack"`）を書き換えることになり、
  コミットした入力が実行した入力と違うものになる。また `trials/` は `.gitignore` にあるので、そこの出力は DVC で追えない
  （`dvc add` が、git が無視するパスとして断る。「## 補足」の測定）。採らない

### closed の issue の検討

- 案 B1（親のセッションが出した案）: closed の issue の検討を examples から片付ける（消すか、別の置き場に移す）。採らない。
  ユーザーが退けた（ユーザー 2026-11-19）。閉じた後も、再検討が要ることと、思い違いで全部をやり直すことがある。数でも、
  closed の 9 個はどれも外から引かれ、open の `issue-0286` は closed の `issue-0274` の入力から自分の入力を作っている（背景）
- 案 B2（採用）: closed でも消さず、ほかのケースと同じ形で残す

### 本番と検討の違いと、出力の追い方

- 案 C1: 今の姿。本番はステージ、検討は `dvc add` で、検討のディレクトリに文書は無い。軸 (2) を満たさない
- 案 C2: 設定の厳密さで分ける（CLAUDE.md の「本番は既定、結論が ±20 pcm で変わらない検討は簡易でよい」。ADR-0197）。これは
  計算の設定の線で、置き方と作り直しの扱いを決めない。設定の線は残し、「本番」と「検討」の語の定義をこの ADR に合わせる
- 案 C3（採用。親のセッションの案）: 記録の残し方（ディレクトリ、`dvc.yaml` と `dvc.lock`、文書）には違いを置かず、検討も
  ステージで流す。違いは作り直しの扱いだけで、検討は答えが出たら DVC の `frozen: true` で凍結する。凍結したステージは、deps が
  変わっても `dvc status` に changed と出ず、`dvc repro` も実行しない（「## 補足」の測定）。検討を本番のチェーンから切るという
  ユーザーの問いに、DVC の機能で答える。lock の deps の md5 が、読んだ上流の出力とコードの正規形を残す（軸 (3)）
- 案 C4: 検討は `dvc add` のまま（ADR-0222）にし、実行したコミットを文書に書く。`.dvc` は deps を持たないので changed にならず、
  凍結の仕組みが要らない。出どころは実行したコミットと入力で辿る（ADR-0122）。失うのは、読んだ上流の出力の md5 の機械的な
  記録である。実行したときの作業ツリーの上流の出力が lock のとおりだったかは、どこにも残らない。背景のとおり、検討は本番の
  出力を相対パスで読み、その辺が今は lock に無い。軸 (3) で案 C3 に劣る。採らない

案 C3 の費用と、確かめたこと:

- 1 操作の時間: ステージの数を 100、1,000、3,000 に変えた一時のリポジトリで、1 ステージを指定した `dvc status` は 0.26〜0.39 秒で
  変わらず、全体の `dvc status` は 0.4、2.7、6.4 秒とステージの数に比例した（1 ステージ約 2 ミリ秒。frozen でもほぼ同じ。
  「## 補足」の表）。ケースごとの `dvc.yaml` は小さいので、検討をステージにしても、目標を指定した操作は延びない。この測定の
  ステージは params を持たない。xlc の p2 の全体の `dvc status` の時間は、params のファイルの読みが占め、残る固定費は
  ステージの数 × params のファイルを 1 回読む時間である（#0268 の「経緯」の 2026-11-19 の項）。検討のステージが大きな TOML を
  params に持てば、全体の `dvc status` はその分延びる
- 入力の TOML は値の正規形で deps にする（ADR-0254）ので、検討の入力 1 本ごとに、直下の `dvc.yaml` の `toml-values` のステージと、
  git で追跡する正規形のファイルが 1 つずつ増える（今は 436。ADR-0258 の棚卸し）。凍結すれば deps を見ないので、検討の
  ステージの deps を入力の TOML そのものにして正規形を省けるかを、移行の段 1 で決める
- 検討は、上流のステージが changed のまま、そのケースのステージだけを流す。上流は、ブランチのコードを変えたときだけでなく、
  main でも changed の残高を持つ（実行ファイルだけで changed のステージが 1,046。ADR-0258 の帰結）。目標を指定した `dvc repro` は
  上流から再実行するので、ADR-0258 の `-s` の経路（上流の outs が `dvc.lock` のとおりなら、上流を飛ばして 1 本だけ流す。まだ
  実装されていない）が前提である
- 凍結した lock を守る仕組みが要る。frozen のステージの cmd を変えて `dvc repro` を実行すると（`-f` の有無によらず）、cmd を
  実行しないまま、lock の cmd と deps の md5 が今の値に書き換わった（「## 補足」の測定）。cmd の文字列は、ツールの置き場を
  変えると変わる
- この ADR の前に流した検討には使えない。計算をやり直さずに lock を作る `dvc commit` は、今の deps の md5 を lock に書く
  （「## 補足」の測定）。出力を作ったのでないコードの正規形が、作ったものとして記録される

凍結したケースを changed の数から除く方法:

- 案 F1: ケースごとに `dvc.yaml` を分けるだけにする。足りない。凍結したケースのステージも、deps が変われば `dvc status` に
  changed として出る（「## 補足」の表の「frozen なし」の行）
- 案 F2（採用）: `frozen: true` を、凍結したケースのすべてのステージに書く
- 案 F3: 凍結したケースを `dvc.yaml` から外し、出力を `dvc add` に移す。lock の deps が消える。採らない

### ケースの文書の中身

- 案 D1（採用。案 U1 の文書。親のセッションの決定）: 背景、目的、入力と実行、分かったことを README.md に書き、そこを 1 か所の
  置き場にする。検証の記録と issue は、同じ内容を繰り返さず README.md を引く。ディレクトリを開いた読み手が、問いから結論までを
  その場で読める。10,467 行の examples/depletion/verification.md から、検討ごとの節を README.md に分けられる
- 案 D2: README.md は、問い、結ぶ issue と ADR、結果と解釈の置き場（1 か所）、入力と出力の一覧にとどめ、結論は issue か記録に
  置いたままにする。同じ結論を 2 か所に書かない点は案 D1 と同じだが、結論の置き場が issue、ADR、記録に分かれたまま残り、
  ディレクトリを開いた読み手は、別の文書の節を引かないと結論を読めない
- 案 D3: 背景と結論を README.md にも書き、記録と issue にも今のまま残す。`issue-0283` と `issue-0045` で試しに書くと、README.md の
  背景と結論は issue の文の言い換えになり、#0283 の「切り分け」から数値を 6 個、#0045 と ADR-0185 から 5 個コピーした。
  片方を直したときにもう片方が古いまま残る。軸 (6) を満たさない。採らない

### OKF で結ぶ方法

`design-records check` は、バンドルのルートを `docs` に固定している（claude-harness の `crates/design-records/src/okf.rs` の
`BUNDLE_ROOT`。c958f33a、2026-11-19）。examples の下は検査しない。OKF v0.3 の仕様（ADR-0256 が引く原典。コミット 527e81af）で
関わる点は次のとおり。

- §2: バンドルが大きなリポジトリの下位のディレクトリのとき、フロントマターを持つルートの `index.md` がバンドルのルートを示す
- §3.2: ルートの下の `.md` のうち、空でない `type` を持つものが概念である
- §6、§6.4: バンドルの中の概念へのリンクと、パスを値に持つ項目が、バンドルのグラフの辺になる。バンドルのルートの外に解ける
  ものは外部のものとして扱われ、consumer は読まない
- §5.1: `sources` は、概念が拠る材料（バンドルの中のパスか URL）を、項目ごとの対応（`resource` など）の一覧で書く
- §5.4: `status` は `draft`、`stable`、`deprecated` で、`deprecated` の文書は `superseded_by` で置き換えた先を指せる
- §8: `index.md` は、ディレクトリの中身を、開く前に見渡せるように並べる。行には文書の `description` を載せる

xlc の文書どうしの参照は、ADR と issue へは番号（`ADR-NNNN`、`#NNNN`）で書き（docs/adr/README.md）、検証の記録へは
Markdown のリンクかパスで書く。番号の先とリンクの先が実在するかは crates/docs の検査が見ており、examples の下の .md も既に読む
（`crates/docs/src/check.rs` の `scanned_for_refs` と `scanned_for_links`）。番号の参照は OKF のリンクではない。

- 案 K1（勧める）: examples/ を docs/ と別の 2 つ目のバンドルにする（examples/index.md のフロントマターに `okf_version`）。
  ケースの README.md と検証の記録が同じバンドルの概念になり、記録から README.md へのリンクがバンドルの辺になる。ディレクトリ
  ごとの `index.md` が、その下のケースを `description` つきで並べる。`design-records` を、`okf_version` を持つ `index.md` のある
  ディレクトリをバンドルのルートとして見つけ、下位のディレクトリの行にその README.md の `description` を載せる形に広げる
  必要がある（claude-harness の変更。今は、下位のディレクトリの行は名前だけ）。docs/ の issue と ADR との間は、
  バンドルをまたぐので、今と同じく番号で結ぶ。短所は、ケースのディレクトリごとに README.md の 1 行だけの `index.md` が要ること
  （`design-records index` が書く）と、`kind` などケースに固有のキーは `design-records` が知らず、その検査を crates/docs に書くこと
- 案 K2: バンドルのルートをリポジトリの直下に上げ、docs/ と examples/ を 1 つのバンドルにする。issue と ADR からケースへの
  リンクもバンドルの辺になる。`design-records` の変更は案 K1 と同じ種類である。加えて、直下の CLAUDE.md が `type` の無い .md
  として違反になり（claude-harness の ADR-0092 の決まり）、ADR-0256 の決定（ルートは docs/）を変える。xlc は issue と ADR を番号で
  引くので、1 つにして増える辺が少ない。採らない
- 案 K3: examples はバンドルにせず、README.md を OKF の概念の形で書くだけにし、docs/ のバンドルに地図の文書を置く。
  `design-records` を変えずに済む。README.md と記録はどのバンドルの概念でもなく、記録から README.md へのリンクは OKF の辺に
  ならない。ケースの一覧を地図に描くので、ケースを足すたびに共有の 1 つのファイルが変わり、並行するブランチが rebase で
  衝突する。`design-records` を広げられないときの次善の案である
- 案 K4: ケースの文書を docs/cases/ に置き、examples のディレクトリをパスで指す。ケースのディレクトリに文書が無くなり、
  軸 (2) を満たさない。採らない

### 共通のツールの置き場と使い方

- 案 T1: `scripts/` に移す。`scripts/` は今、hook、DVC の実行の入口、正規形のスクリプトを持つ（27 ファイル）。計算の入力と結果を
  扱うツールが混ざり、変えると例のステージが changed になるものが場所で分からなくなる
- 案 T2（採用）: リポジトリの直下に `tools/` を作り、2 つ以上のケースのステージか記録の手順が呼ぶ計算のツール（OpenMC の駆動、
  AWS、比較、記録の表と出どころ）を置く。ステージを流す入口の `stage_runner.py` は、同じ役割の `scripts/dvc-repro.py` のある
  `scripts/` に置く
- 案 T3: examples の中に共通のディレクトリ（examples/common/ など）を作る。import のパスの変更は小さいが、例とツールが同じ木に残る

使い方の置き場。今のツールは、先頭の docstring に使い方を書き、引数が誤っていると docstring の全体を出す形が多い（examples と
scripts の .py のうち 86 ファイルが `__doc__` を出す。`grep -l` で数えた。main 08d0a0d8b）。

- 案 S1: `tools/` に手引きの文書（README）を置く。ユーザーが退けた（案 U3）
- 案 S2: 使い方を docstring に置いたまま、スキルには、いつ、どのツールを使うかだけを書く。使い方が、ツールごとの docstring と
  スキルに分かれて残る
- 案 S3（採用。案 U3）: 使い方の説明はスキルを 1 か所の置き場にする。ツールの側には、引数が誤っているときに出す 1〜2 行の
  使い方と、スキルの名前だけを残す。docstring には、そのツールが何をするか（コードの説明）を書く

### 既存のディレクトリの合わせ方と、置き直し

入力の TOML は、上流の出力を相対パスで読む。ケースのディレクトリの深さを変えると、この値を書き換えることになり、値の
正規形（ADR-0254）が変わる。「md5 が同じなら lock のパスを書き換えるだけ」は、この移動にそのままは当たらない。

- 案 M1: 既存の検討を動かさず、今の `issue-NNNN/` か、その下位を、そのままケースとみなして README.md を足す。再計算は
  起きないが、`issue-0286` は 350 ファイルの 1 ケースになり、新しいケースの置き場（`issue-NNNN/` は束ねるだけ）と形が食い違う。
  同じ issue の新しい検討を足すと、ケースの中にケースが入る。採らない
- 案 M2（採用）: 既存の検討も、新しい置き場に置き直す。置き直すのは、パスを変えても再計算にしない仕組み（ADR-0258 の側で
  決める）が入った後にする（ユーザー 2026-11-19）
- 案 M3: 既存の検討を、`dvc.yaml` と `dvc.lock` を持つ形に直す。案 C3 の最後の項の理由（`dvc commit` が今の deps を書く）で採らない。
  既存の検討は `.dvc` のまま置き直す

## 決定と理由

案 A3、B2、C3 と F2、D1、K1、T2 と S3、M2 にする（proposed）。本番と検討の定義（案 C3）は親のセッションの案、OKF の結び方
（案 K1）はこの ADR の担当が比べた推奨で、どちらも、ユーザーが読んでから確定する。

### ケースとディレクトリ

- ケースは、1 つの問いに答える計算の組である。ケースごとに 1 つのディレクトリを作り、次を置く
  - 入力（TOML と、このケースだけが使うスクリプト）
  - 出力。重い出力は DVC で追い、数十 KB までの要約（比較の JSON）は git で追跡する（ADR-0176 と同じ）
  - `dvc.yaml` と `dvc.lock`
  - `README.md`（下の「ケースの文書」）
- 形を求める時点: 記録、ADR、issue に結果（数値か、結果から出した結論）を書く計算は、ケースのディレクトリで、ステージで流す。
  書かない試しは、直下の `trials/` で自由に作って捨てる（ADR-0122 の「試行の運用」）。試しの結果を書くことにしたら、ケースの
  ディレクトリに入力を置いて、そこで再実行する（案 A4 の理由。試しはステージでないので、流したときの deps の md5 が残らず、
  再実行せずに lock を作る方法が無い）
- ADR の「検討した案」に案を比べる目安として書く時間（ADR-0122 の決定と理由の例外の項）は、ケースにしなくてよい
- ADR-0122 の「記録に数値を書く試行だけ、その入力を `git add -f` でコミットし」「残す試行と採用した入力は examples/<問題>/ に
  `git mv` する」は、記録に書く計算を始めからケースのディレクトリで流す形に直す（移行の段 1 で、ADR-0122 の「## 変更」に書く）
- ケースのディレクトリには、そのケースのものだけを置く。2 つ以上のケースが使うスクリプトは `tools/` に置き（下の「共通の
  ツール」）、ほかのケースの出力は、そのケースの場所から deps で読む（コピーしない）
- ケースは入れ子にしない。ディレクトリは、ケースであるか、ケースを束ねるだけかのどちらかにする
- 置き場
  - 本番: `examples/<問題>/<ケース>/`（VERA の `p<n>/` は ADR-0116 のまま、この形に当たる）
  - 検討: `examples/<問題>/issue-NNNN/<ケース>/`。`NNNN` はきっかけの issue で、`issue-NNNN/` は束ねるだけにする。issue の無い
    検討は、issue を起こしてから置く。ケースの名前は、問いを表す英語の kebab-case にする
  - ケースが 1 つだけの問題（examples/m0 など）は、問題のディレクトリをケースのディレクトリにする。その問題に 2 つ目の
    ケースを足すときに、元のケースを下位に下ろす
- closed の issue のケースも消さない（案 B2）。再検討は、元のケースを書き換えず、同じ `issue-NNNN/` の下に新しいケースとして流す

### ケースの文書

ケースのディレクトリに `README.md` を置き、OKF の概念の形で書く。背景、目的、分かったことは、ここを 1 か所の置き場にする。
ひな形:

```markdown
---
type: Case
title: <問いを 1 行で>
description: <何を確かめ、何が分かったかを 1 文で。索引の行に載る>
status: draft          # draft（進行中） | stable（答えが出た。検討は凍結した） | deprecated（置き換えたか、誤りと分かった）
superseded_by:         # status: deprecated で、置き換えたケースがあるときだけ。その README.md へのパス
kind: study            # production（本番） | study（検討）
issues: ["#NNNN"]      # きっかけの issue と、結果を使った issue
adrs: [ADR-NNNN]       # 結果を根拠にした ADR
upstream: [../../p2]   # 出力や入力を読むケースのディレクトリ。dvc.lock に無い辺も書く
tracking: stage        # stage（dvc.yaml と dvc.lock） | dvc-add（.dvc。この ADR の前に流した検討） | none（出力を追跡していない）
ran-at: ["0123abcd"]   # 検討だけ。実行したコミット（8 桁。引用符で括る）
ran-on: 2026-11-19     # 検討だけ。実行した日
---

# <title と同じ>

## 背景

なぜこの計算が要ったか。きっかけの issue と、その時点で分かっていたこと。

## 目的

答える問いを 1 つ。何が分かれば終わりか。

## 入力と実行

入力のファイル、替えた条件、出力のファイルの対応（表）。流し方（ステージの名前）。読んだ上流の出力。実行したコミットが
出力ごとに違うときは、表の列に書く。

## 分かったこと

問いへの答えと、それを支える数値（出典の JSON かログ、コミット、日付）。表は、比較の JSON があればツールが描く。

## 残ること

答えが出なかった点と、続きのケースか issue。無ければ節ごと省く。
```

- 検証の記録と issue は、ケースの背景、目的、結果を繰り返さず、README.md を Markdown のリンクで引く（ADR も同じ）。リンクの先が
  実在するかは crates/docs の今の検査が見る。文字で書いたパスは検査されないので、README.md を引くときはリンクにする。検証の記録（`verification*.md`）には、複数のケースをまたぐ今の姿（問題ごとの参照解との差の
  一覧、ケースをまたぐ比較）と、各ケースへのリンクを残す
- 本番のケースの「分かったこと」は今の姿を書き（ADR-0117）、作り直しのたびに書き直す。検討のケースは、凍結した時点の値を書き、
  凍結の後は直さない（誤りと分かったら `status: deprecated` にして、理由を 1 行足す）
- `status` は OKF の値（§5.4）をそのまま使う。新しい `type` なので、ADR と issue の `status` の値の食い違い（ADR-0256 の帰結）を
  持ち込まない
- `issues`、`adrs` は ADR と issue のフロントマターと同じ番号の書き方にする。番号の先が実在するかは、crates/docs の今の検査が
  見る。OKF は拡張のキーに `x-<producer>-<name>` の名前を勧めるが（§4.1）、xlc の ADR と issue のキーに合わせて接頭辞を付けない
- `upstream` は OKF の `sources`（§5.1）に近い役割だが、拡張のキーなので OKF のグラフの辺にはならない（辺になるパスの項目は
  §6.2 のものだけ）。`sources` は項目ごとの対応の一覧で、複数行になる。xlc のフロントマターは 1 行の一覧で書く決まり
  （スキル adr）なので、パスだけの 1 行の一覧にする。`upstream` と `superseded_by` のパスの先が実在するかは、README.md の検査に
  入れる（移行の段 1）。`dvc.lock` の deps から出せる辺は、地図のツールが
  照らす（下の「OKF と地図」）
- 本番のケースは `ran-at` と `ran-on` を書かない。作り直しのたびに変わり、`dvc.lock` と記録が持つ（`record_provenance.py`）
- この ADR の前に流した検討の `ran-at` は、記録か issue が書く実行したコミットにする。`record_provenance.py` が `.dvc` の履歴から
  出すのは `.dvc` を入れたコミットで、実行したコミットではないので、`ran-at` に書かない。実行したコミットが分からなければ
  空にし、「入力と実行」に、分からないことと `.dvc` を入れたコミットを書く

### 本番と検討

記録の残し方（ディレクトリ、`dvc.yaml` と `dvc.lock`、README.md）には違いを置かない。違いは作り直しの扱いだけである。

- 本番（`kind: production`）: 今のコードと入力の結果を保つケース
  - 入力は、上流のケースのステージの出力か、固定した外部のデータ（評価済み核データ、仕様書の参照解）だけにする。`dvc add` した
    中間のファイルを読まない
  - 設定は ADR で決めた既定にする（CLAUDE.md の方針）
  - changed は作り直しの残高に数え、作り直しのときに上流から一揃いで再実行する（ADR-0258）
  - 参照解（OpenMC）のステージは本番のケースに置き、再実行するかは今までどおり ADR-0130 と ADR-0184 に従う
- 検討（`kind: study`）: 問いに答えた時点のコードと入力で凍結するケース
  - 本番の出力を、deps に書いて読んでよい。lock の deps の md5 が、読んだ版を残す
  - 設定は、結論が変わらない範囲で簡易でよい（CLAUDE.md の ±20 pcm の線。ADR-0197）
  - 答えが出たら凍結する。README.md を `status: stable` にするコミットで、そのケースの `dvc.yaml` のすべてのステージに
    `frozen: true` を書く
  - 凍結した後は、コードや上流が変わっても再実行せず、作り直しの残高に数えない。本番の作り直しにも巻き込まれない。再検討が
    要るときは、新しいケースとして流す
- 凍結したケースの lock を守る。凍結したケースを目標にした実行を、入口（`scripts/dvc-repro.py`）が止める。手元の生の
  `dvc repro` は入口を通らないので、凍結したケースの `dvc.lock` の変更を、パスの書き換え（下の「移行」）のほかは、コミットの
  検査が止める。どちらも、最初のケースを凍結する前に入れる
  （移行の段 1）
- CLAUDE.md の「本番（記録に載せる燃焼、p2 のステージ）は既定、結論が ±20 pcm で変わらない検討は簡易でよい」と、ADR-0258 の
  帰結の「ステージと lock の決まりが掛かるのは、記録に載せる計算である。検討の計算は DVC のステージにしなくてよく」は、
  記録に載せるかで線を引いている。この ADR では、記録に載せる検討もあり、検討もステージで流す。2 つの文は、移行の段 1 で
  この ADR の定義に合わせる

理由: 検討の出力は、記録と ADR が根拠として引く（背景）。検討を `dvc add` だけで残すと、読んだ上流の出力の版が残らない。一方、
検討を本番と同じく changed に数えると、答えの出たステージが、コードを直すたびに残高に入り、残高から「作り直すもの」を
読めなくなる。`frozen: true` は、lock に出どころを残したまま、検討を本番のチェーンから切る。目標を指定した操作の時間は、
ステージの数が増えても変わらなかった（案 C3 の測定）。

### 本番のチェーン

本番は、xs、lattice、core までを一貫したステージにする（ユーザー 2026-11-19）。

- 本番のケースどうしの辺は、すべて `dvc.yaml` の deps と outs に書く。`dvc.yaml` はケースごとに分かれるが、DVC は deps と outs の
  パスでリポジトリの全体を 1 つのチェーンとして扱うので、下流のケースを目標にした `dvc repro` が上流のケースから流す
- 入力の TOML が相対パスで読むファイルは、そのステージの deps に書く。書き漏れは、地図のツールが入力のパスと deps を照らして
  見つける
- 今の切れ目は、テーブルから炉心の燃焼への接続である（背景）。ステージにするのは、炉心の計算が読むテーブルと、その上流の
  集合体の燃焼の履歴とブランチ計算である。今の置き場では、examples/depletion の `branches`（`.dvc` 59）、`history`（44）、
  `p9-gd`（24）のうち、炉心の入力（p9-timing の `core-p9`）と記録の今の姿が読むもの。どのファイルが本番で、どれが検討かは、
  移行の段 5 でファイルごとに決める
- 本番のステージの定義は、次の本番の作り直し（ADR-0258 の「changed の扱い」）のブランチで、今の `.dvc` と置き換えて書く。
  同じ出力を `.dvc` とステージの両方が持つと、DVC は出力の重複として、無関係なステージの `dvc repro` と `dvc add` も止める
  （「## 補足」の測定）ので、定義だけを先に足さない。今の `.dvc` の出力に `dvc commit` で lock を付けることも
  しない（案 C3 の最後の項の理由）。作り直すまで、炉心の入力は今の `.dvc` のテーブルを読み続ける

### OKF と地図

- examples/ を、docs/ と別の OKF v0.3 のバンドルにする（案 K1）。examples/index.md のフロントマターに `okf_version: "0.3"`、
  `title`、`description` を書く
- 概念は、ケースの README.md（`type: Case`）、検証の記録（`type: Verification`）、地図（`type: Reference`）である。README.md は
  仕様では `type` が無ければ概念でないファイルだが（§3.2）、ケースの README.md には `type` を書いて概念にする
- 文書か下位のディレクトリを持つディレクトリに `index.md` を置き、`design-records index` で書く。今の `design-records index` は、
  下位のディレクトリの行を名前だけで書き、`description` を載せるのは同じディレクトリの文書の行だけである（claude-harness
  c958f33a の `entry_line`）。問題のディレクトリと `issue-NNNN/` の `index.md` が、その下のケースを README.md の `description`
  つきで並べるには、下位のディレクトリの行に、その README.md の `description` を載せる変更も要る。ケースの一覧は、これを正とし、
  ほかの文書に描かない
- 検証の記録からケースへは Markdown のリンクで結ぶ（バンドルの中の辺）。ケースから docs/ の issue と ADR へは番号（`ADR-NNNN`、
  `#NNNN`）で、issue と ADR からケースへは Markdown のリンクで結ぶ。バンドルをまたぐリンクは OKF では外部のリンクだが（§6）、
  番号とリンクの先は crates/docs が検査する
- examples の全体の地図を examples/map.md に置く。手で書く部分は、チェーンの読み方（どの問題がどの問題の上流か）と、置き方の
  決まりへの参照だけにする。本番のケースの間の辺は、ツール（`tools/` に置く）が `dvc.lock` の deps から表に描き、手で直さない
  （検証の記録の `<!-- table: -->` と同じ形。ADR-0176）
- 検討ごとに変わる数（ケースごとのステージの数、frozen の数、`.dvc` の数、README.md の無いディレクトリの数）と、検討の
  `upstream` の辺は、地図に書かず、同じツールの出力で読む。地図のファイルは、本番のチェーンが変わったときだけ変わる
- README.md のフロントマター（キー、`kind`、`status`、`tracking` の値、`status: stable` の検討のステージがすべて frozen で
  あること）は、crates/docs の検査が確かめる
- `design-records` がバンドルのルートを `docs` のほかにも見つけ、下位のディレクトリの行に説明を載せることが前提である
  （claude-harness の変更。移行の段 2）。
  それまでは examples/index.md を置かず、README.md は同じ形で先に書く。`design-records` を広げないと決まったら、案 K3 にし、
  この ADR の決定を直す

理由: ケースの文書を結果の置き場にすると、検証の記録はケースへのリンクの集まりになる。記録とケースを同じバンドルに入れれば、
そのリンクが OKF の辺になり、ディレクトリごとの索引が、開く前に中身を見渡すという `index.md` の目的（§8）のとおり、背景の
「何がどこにあるか分からない」に、その場所で答える。索引は `design-records` が書いて検査するので、ケースの一覧を描く共有の
ファイルを別に持たずに済む。

### 移行

ファイルやディレクトリを動かしても再計算にしない（ユーザー 2026-11-19）。仕組みは ADR-0258 の側で決める。main 08d0a0d8b の
ADR-0258 にはまだ無く、別のブランチ docs/0258-settle-open-points（996d76b44、2026-11-19。マージされていない）が案を書いている:
lock のパスを書き換えるツール、入力の TOML の中のパスだけを書き換えた変更を値で比べて同じツールで扱うこと、入力のパスと
md5 を出力の JSON に持つ比較のステージは書き換えずに再実行すること。その案のままなら、比較のステージを持つケースは、
動かした後に比較のステージの再実行が要る。凍結したケースの比較のステージをどうするか（凍結の前に動かすか、置き直しの
ときだけ再実行を許すか）は、仕組みが決まった後に、段 4 の前に決める。ファイルを動かす段（下の 3〜6）は、その仕組みが入った後にする。ディレクトリごと
動かすと、outs のパスは `dvc.yaml` からの相対なので変わらず、ディレクトリの外を指す deps のパスが変わる（「## 補足」の測定）。

前提になる、この ADR の外の変更:

- パスを変えても再計算にしない仕組み（ADR-0258）: 段 3〜6
- 上流を飛ばして 1 本だけ流す `-s` の経路（ADR-0258 の移行の段 2）: ブランチのコードで検討をステージで流すこと
- `design-records` がバンドルのルートを見つけ、下位のディレクトリの行に説明を載せること（claude-harness）: 段 2

段ごとに 1 本のブランチにする。決まりを先に、既存のディレクトリを合わせる作業を後にする。

1. 決まり。この ADR を確定する。置き方の決まりをスキルに書き、CLAUDE.md から指す。CLAUDE.md の「本番」の文、ADR-0258 の帰結の
   検討の項、ADR-0122 の「試行の運用」を、この ADR に合わせる。README.md の検査（crates/docs）と、凍結したケースを守る入口と
   検査を TDD で作る。`frozen: true` を xlc の DVC のツールがどう扱うかと、検討のステージの deps の形（正規形を省けるか）を
   確かめて決める。ファイルは動かさない。この段と ADR-0258 の `-s` の経路の両方が入った後に作るケースは、新しい形にする
   （それまでの検討は、今までどおり `dvc add` で追う。ADR-0222）
2. examples をバンドルにする。examples/index.md、検証の記録 14 件の `type`、各ディレクトリの `index.md`、地図とそのツールを足す
3. 共通のツールを `tools/` と `scripts/` に移し、使い方をスキルに集める
4. 既存の検討を置き直す。`issue-NNNN` を、closed の 9 個から先に、ディレクトリごとか数個ごとのブランチで置き直し、README.md を
   足し、記録の節を移す。open の 10 個は、その issue のブランチが動いていないときに行う
5. 本番のチェーン。examples/depletion の `branches`、`history`、`p9-gd`、`micro` などと直下のステージ、本番のディレクトリの下に
   ある検討（p9-timing の `trial-NNNN` など）を、本番と検討に分けて置き直し、README.md を書く。本番のステージの定義は、本番の作り直しのブランチで `.dvc` と置き換える
6. VERA と小さい例。README.md を足す。examples/vera の直下のステージ（ライブラリ、参照解のライブラリ、問題 1 と 2）をケースの

### 帰結

- 実装は決定に追いついていない。上の移行の段がすべて残る。この ADR は issue を起こさず、確定のときに、段ごとの issue を
  起こして `issues` に結ぶ（proposed の間は、段の中身が変わりうる）
- 段 2 は claude-harness の変更に依る。`design-records` を広げるかは、claude-harness を管理するセッションが決める
- ADR-0222（記録と ADR が引く、ステージの出力でない生成物を `dvc add` で追う）の対象は、新しい検討がステージの出力になるので
  減る。ステージの外で出た生成物（この ADR の前の検討を含む）には、引き続き掛かる。ADR-0222 の決定は変えない
- 検討の入力ごとに正規形のステージとファイルが増えうる（案 C3 の費用）。段 1 で、検討のステージの deps の形を決める
- 段 3 で .py の import のパスを書き換えると、その .py の正規形（ADR-0210）が変わり、それを deps に持つ本番のステージは changed に
  なる。パスだけが変わる場合と違うので、作り直しの残高に入る。import を変えずに移せるか（検証用のツールのパッケージ。
  ADR-0212）は、段 3 で決める
- 使い方をスキルに集めると（案 S3）、引数が誤っているときに docstring の全体を出しているコードを替えることになる。docstring は
  正規形に入らないが、コードは入るので、正規形を持つ .py では、import を変えなくても、それを deps に持つ本番のステージが
  changed になる
- `record_provenance.py` は、lock と `.dvc` の履歴を今のパスの `git log` で読み、改名を辿らない。置き直しの後は、出どころの
  コミットが移動のコミットになる。段 3 で、移動をまたいで辿る形に直す
- 凍結したケースが読んだ上流の出力は、上流を作り直すと作業ツリーから無くなる。lock の deps の md5 は残るが、その版の
  ファイルをキャッシュから戻せるかは `dvc gc` の運用に依る（確かめていない）
- `frozen: true` を、xlc の DVC のツール（`scripts/dvc-checkout.py`、`scripts/count-changed-stages.py`、
  `scripts/check-skip-upstream.py`、`scripts/check-dvc-lock.sh`、ADR-0257 の数え方）がどう扱うかは確かめていない（段 1）。
  `dvc status` は frozen のステージごとに警告を 1 行ずつ出す
- 検証の記録にフロントマターを足したときに、`verification_tables.py` と記録を読むほかのツールが変わらず動くかは確かめて
  いない（段 2）
- `verification_tables.py`（5,711 行）は、個別の検討のパスを中に持つ（背景）。ケースの README.md の表を描く形にどう分けるかは、
  段 3 で決める
- この ADR の前に流した検討は、lock を持たないまま残る。どの上流の出力から出たかは、README.md の `ran-at` のコミットを
  checkout して辿る（ADR-0122）
- 置き場が変わると、ADR、issue、記録が書くパスが古くなる。確定した ADR の凍結する部分は、壊れたリンクの修正だけを直せる
  （docs/adr/README.md の「運用」）。文字で書いたパスは直さず、`git log --follow` で辿る
- この ADR は、ケースの置き方と、共通のツールの置き場と使い方を 1 件に書いている。確定のときに、共通のツールの決定を別の
  ADR に分けるかを決める

### DVC の測定

DVC 3.67.1、一時のリポジトリ（xlc の外）、手元、2026-11-19。dep を 1 つ読んで out を 1 つ書くステージ（単独と foreach）を
`dvc repro` で流してから、次を見た。

- dep を変えると、`dvc status --json` は 3 つのステージに `changed deps` を出した。`frozen: true`（foreach では `do:` の下）を
  書くと、同じ状態で `{}` になり、ステージごとに「is frozen. Its dependencies are not going to be shown in the status output」の
  警告が出た
- dep だけが変わった frozen のステージに `dvc repro` を実行すると、ステージは実行されず、`dvc.lock` は変わらなかった
- cmd と dep を変えた frozen のステージに、`-f` を付けない `dvc repro` を実行すると、cmd は実行されず（out は元のまま）、lock の
  cmd と dep の md5 が今の値に書き換わった
- frozen のステージの out を書き換えると `changed outs`、cmd を書き換えると `changed command` が出た
- cmd を書き換えた frozen のステージに `dvc repro -f` と `dvc repro -s -f` を続けて実行すると、cmd は実行されず（out は元のまま）、
  「Verifying outputs in frozen stage」と出て、lock の cmd と dep の md5 が今の値に書き換わった（どちらの呼び出しが書き換えたかは
  分けていない）
- ケースのディレクトリを別の場所に動かすと、frozen のままでは `dvc status` は `{}`、frozen を外すと、ディレクトリの外の dep
  （`../up/a.txt`）が `deleted` と出た。outs は変わらなかった
- 実行したことの無いステージ（cmd、dep、既にある out）に `dvc commit -f` を実行すると、今の dep の md5 と out の md5 を持つ
  lock ができ、`dvc status` は `{}` になった
- `dvc add` で追っているファイルを outs に持つステージを `dvc.yaml` に足すと、別のファイルの `dvc add` と、別の `dvc.yaml` の
