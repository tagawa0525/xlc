# ADR-0258: DVC のステージと deps の正規形は残し、changed を作り直しの残高として扱い、rebase の後の付け直しを 1 本のコマンドにし、上流を飛ばす実行は上流の出力が dvc.lock のとおりかで決める

## 背景

計算のステージは ADR-0123（2026-10-11。a9fb661a7）で DVC に載せ、ADR-0159 が deps をビルドした実行ファイルにした。DVC は deps の md5 で
出力の古さを判定する。deps にはコード（`bin/` の実行ファイルの正規形。ADR-0159、ADR-0255）と Python のツールの正規形
（ADR-0210）が入るので、xs、lattice、core と比較のツールを直すと、それを deps に持つステージが changed になる。

### 直すべきものを直さない判断

changed になることを理由に、直すべきものを直さない判断が繰り返し出た:

- #0149（閉じた）: ADR-0186 のレビューの 2 周目の指摘を、xs を変えるとライブラリ（約 2 時間）が changed になるので直さなかった
- #0150: 同じブランチで、作り直しを避けるため 2 周目の指摘を issue に残した
- #0241: lattice の CMFD の複製を共通のクレートに移すのを、15 の dvc.lock の約 380 行が changed になるので後回しにした
- #0174: p2 の入力に `few-group` を書くかを、入力を変えると changed になるので ADR-0196 で決めなかった
- #0106（2026-11-19 に閉じた）: 実行中の statepoint を間引く修正を、`openmc_resume.py` の正規形が変わって `openmc-5A-2D-extract` が
  changed になるので、その extract を再実行できるブランチまで待つとしていた
- 2026-11-19 の issue の片付けで、ツールの誤り #0104、#0106、#0236 を、直すと extract と compare のステージが changed になる
  という理由で残し、xs と lattice のコードを触る修正も同じ理由で範囲から外した（親の依頼による。#0104 と #0106 は同じ日に
  別のブランチで直して閉じた。main 2d1678eed）

ユーザーは、再実行の引き金になるから問題を放置するのは本末転倒だと指摘した（ユーザー 2026-11-19）。

この ADR の前の版（main adc380560 にある版。2026-11-19）は、原因を DVC の判定に付いた手続き（正規形の書き直しと rebase の後の
付け直し）に求め、正規形の 3 種と付け直しをやめる案（下の案 C2）を勧めた。その版の背景は、費用として核種ごとのライブラリの
約 2 時間（#0150）だけを挙げ、下流の全部の作り直しの規模を数えていなかった。ユーザーはその案を退けた（ユーザー 2026-11-19 の相談）。

### 作り直しの規模

本番の出力の全部の作り直しは、数日から 1 週間の規模である（ユーザー 2026-11-19 の相談での値）。文書にある見積もり:

- docs/plans/m4-depletion.md の「CPU と記憶の見積もり（xlc）」: Problem 9 の 10 種の燃焼とブランチ計算で約 32〜47 時間
  （3 × 3 × 3 の格子点と ADR-0209 の前の 1 状態の時間からの見積もり）。Problem 10 でさらに 6〜7 種が加わる
- ADR-0239 の帰結の「テーブルの作成の見積もり」: 本番の格子点で、制御棒のない組が 10 種前後に約 35〜118 時間、制御棒を入れた
  組が種類ごとに約 5.5〜14.9 時間（1 状態 27.0 秒の古い時間からの値）。10 種として足すと 35 + 10 × 5.5 = 90 時間から
  118 + 10 × 14.9 = 267 時間で、約 4〜11 日に当たる（この ADR で足した値。排他のジョブを 1 本ずつ流すとした和）
- #0278 の「問題」の時間の見積もりの項: 今の既定と入力（燃料の温度 4 点、ブランチ条件は 15 燃焼点、制御棒の軸なし）で、2A の 1 種が
  約 6.3 時間の見込み（測定でない）
- ライブラリ: p2 の 545 核種の作り直しが 2 時間 3 分（Slurm 887、2026-11-15。#0268 の「問題」）

参照解（OpenMC）と VERA の各問題の再実行は、これらに入っていない。合計を 1 つの値にまとめた文書は無い。ADR-0239 の値を足した
和の上の端（約 11 日）は、ユーザーの値より大きい。

この規模では、何がどの版のコードと入力から出たか、どこから下が古いかを、機械が追う必要がある。また、結果を変えない編集
（注釈、書き方、行の番号）で下流の全部を古くしない仕組みが要る。deps の正規形は DVC が無くても要るもので、注釈だけが違う
実行ファイルを同じとみなすことも要る（ユーザー 2026-11-19 の相談の要約）。

### 原因の見直し

上の 6 件に共通する原因は、DVC の仕組み（古さの判定、正規形、lock）でなく、changed を即時の作り直しの義務と取り違えたことだと
見る（ユーザーとの相談の結論。ユーザー 2026-11-19）。ADR-0130 の帰結は、changed は「そのままでよい」「結果が要るときだけ流す」と
決めている。それでも、#0241、#0174、#0106、2026-11-19 の片付けでは、changed になることが修正を後回しにする理由として書かれた。
一方、#0149 と #0150 は事情が違い、記録の数値を出すブランチの中で xs を変えると、ADR-0122 のとおりそのブランチでライブラリを
作り直すことになるので、指摘を残した。これも、修正を作り直しと同じブランチに結びつけていたことから来る。

### 上流を飛ばす実行を数秒のステージに限る規則の経緯

- 2026-10-11: CLAUDE.md に、例は `dvc repro examples/<問題>/dvc.yaml` で実行し「手で段階を選ばない」が、DVC の導入とともに
  入った（0f492a417）
- 2026-10-12: a548a9098 が ADR-0130 と CLAUDE.md に、rebase で deps が変わっても重いステージは再実行せず、数秒で終わるステージ
  だけは再実行してよい、を入れた。コミットの本文は、rebase のたびに再実行せずに結果の環境を復元できることをユーザーが求めた
  ため、と書く。ここでの「数秒」は、軽いものは再実行してよいという許可である
- 2026-10-22: 3c11ece7f が ADR-0184 を入れた。きっかけは、/code-review が CLAUDE.md の文言と docs/plans/m4-depletion.md の手順の
  食い違いを指摘したことで（ADR-0184 の背景）、`-s` を /dvc-relock の数秒のステージだけに限った。この時点で、軽いものは
  再実行してよいという許可が、上流を飛ばせるのは軽いものだけという制限に変わった。この前後の会話の記録に、この制限に
  ついてのユーザーの発言は無い（親が会話の記録の 2026-10-22 のユーザーの発言を読んだ。担当は記録を開いていない）
- 2026-11-03: 50c2b69ef が `-s` の 2 つ目の例外（上流の changed が deps だけで outs が `dvc.lock` のとおりのとき、数秒の下流に
  `-s` を許す）を足した。本文の「ユーザーの判断」は、親が出した推奨への承認で、「数秒」の限定は親の文に入っていた（親が
  会話の記録の 2026-11-03 の発言を読んだ。担当は記録を開いていない）
- ADR-0184 の決定と理由の最後の段落は、数秒の下流に限る理由を「上流を今の deps で再実行したときに下流も数秒で作り直せるため」と
  書く。`dvc.lock` の上流と下流のつながりの条件ではない

ユーザーは、この制限を求めたことは無く、制限の向きが逆だとした: 本番では一揃いで計算できるべきだが、検討の段階では、
時間のかかる計算ほど上流を作り直したくない（ユーザー 2026-11-19 の相談の要約）。

「数秒」という時間の線にも、ユーザーの発言の出どころは見当たらない（親が 2026-11-19 に計算の規則の出どころを調べた結果。
担当は次の 1 件だけを会話の記録で読んだ）。記録にあるのは、履歴の書き換えで全例の `dvc.lock` が deps と食い違ったときに、
再実行せずに lock を付け直してよいかを尋ねられ、再実行にかかる時間による、2 時間程度なら待ってもよい、と答えた発言である
（ユーザー 2026-10-22）。

### 判断の軸

- (a) 記録の数値がどのコードと入力から出たかを辿れること（ADR-0122）と、どこから下が古いかを機械が示せること
- (b) 重い出力（ライブラリ、参照解、燃焼の履歴、テーブル）を作り直さずに使い回せること
- (c) 直すべきものを直すことが、手続きの費用と作り直しの費用で妨げられないこと
- (d) 結果を変えない編集で、下流の全部を古くしないこと

## 検討した案

案 A〜E は前の版で比べた案で、案 F がこの ADR の決定である。

- 案 A: DVC をすべてやめる。重い出力は追跡しない置き場に置き、出どころは記録と、出力に添える出どころのファイルで辿る。
  前の版を残して戻すには、DVC のキャッシュと `dvc add`、`dvc checkout`、`dvc gc` を作り直すことになる（ADR-0123 の案 G が
  退けた保守）。残さなければ、記録が引く版を戻せない（ADR-0222 が案 C、D を退けた理由）。(a) の後半は案 B と同じく
  満たさない。採らない
- 案 B: ステージと lock（`dvc.yaml`、`dvc.lock`、正規形、付け直し）をやめ、`dvc add` と `.dvc` による保管だけを残す。実行は
  例ごとのコマンドの一覧と手書きの runner に移し、出どころは `.dvc` の `meta` に書く。古さを機械が判定しないので、(c) の
  手続きの費用は無くなる。採らない。理由は 2 つある
  - 規模（背景の「作り直しの規模」）。全部の作り直しが数日から 1 週間かかるので、古い出力と新しい出力が長く混ざる。案 B は
    どこから下が古いかの一覧（`dvc status`）を失い、(a) の後半を人の記憶と記録の読み比べに戻す
  - 品質の検査を足すと、DVC の作り直しになる。案 B の runner に、上流の出力が出どころのとおりかの照合と、記録から出どころを
    上流までたどる検査を足すと、それは `dvc.lock` の deps と outs の md5 と `dvc status` が今持つ働きである。事実上の標準の
    ツールを手書きで作り直すことになる（グローバルの CLAUDE.md の設計指針）
- 案 C: DVC のステージも正規形も今のまま残し、changed を再実行の義務として扱う規則だけをやめる。前の版は、正規形を書き直して
  lock をコミットする手続きが修正のたびに付くことと、`-s` を広げると上流の outs を戻していない作業ツリーで下流を作る誤りが
  戻ることを理由に退けた。案 F は、この案に、手続きを機械に移すこと（付け直しのコマンド、正規形を書き直す hook）と、`-s` の
  前の上流の確認を足したものである
- 案 C2: DVC のステージと dvc.lock は残し、正規形の 3 種、rebase の後の付け直し、`-s` を数秒に限る決まりをやめる。deps は元の
  ファイル（`bin/`、.py、TOML）に戻す。前の版が勧めた案。採らない。理由は規模と (d) である。正規形をやめると、注釈 1 行の
  編集や、実行ファイルに入るソースの行の番号がずれるだけの Rust の編集で、それを deps に持つステージの全部が changed になる。
  数日から 1 週間の作り直しの残高に、結果を変えない編集の分が混ざり、残高から「結果を変える修正の後に作り直すもの」を
  読めなくなる。前の版は、今も実行ファイルの正規形を deps に持つ 1,048 のステージのすべてが changed で正規形が効いていない
  ことを挙げたが、それは正規形を入れる前からの残高が作り直されていないことを示すだけで、作り直した後に正規形が要らない
  ことを示さない。`-s` の条件をやめる部分は、案 F が引き継ぐ
- 案 D: DVC のステージを残し、deps からコード（実行ファイルと Python の正規形）を外して、入力の TOML と上流の出力だけにする。
  lock が最新と示しながら、出力は前のコードのものでありうる（ADR-0159 の案 C と #0150 の 1 つ目の案が残した、人が動くまで DVC が
  古さを知らない形）。(a) の後半を満たさない。採らない
- 案 E: ほかの駆動のツール（Snakemake、make、Nix の derivation）に替える。ADR-0123 の案 C、E、F で退けた理由に加え、コードを
  deps に持てば changed の扱いの問題は同じく残り、持たなければ案 D と同じになる。採らない
- 案 F（採用）: DVC のステージ、dvc.lock、正規形の 3 種を残す。changed を作り直しの残高として扱い、修正は作り直しを待たずに
  入れる。rebase の後の付け直しは 1 本のコマンドにし、Python と TOML の正規形は pre-commit の hook が書き直す。`-s` を数秒の
  ステージに限る条件をやめる
  - (a): 満たす。lock の deps と outs が出どころを持ち、`dvc status` が古さを示す
  - (b): 満たす（キャッシュと `.dvc` は今のまま）
  - (c): 作り直しの費用は、修正と作り直しを切り離して外す（決定と理由の「changed の扱い」）。手続きの費用は、機械に移して
    減らす（「rebase の後の付け直し」「正規形の置き場」）。上流の作り直しを背負わずに 1 本だけ実行する経路を開く（「実行」）
  - (d): 満たす（正規形）

案 F の中で比べた案は 4 組ある（パスを動かしたときの lock の扱いは、ADR-0260 に分けた）。

正規形を書くステージの置き場:

- 案 P1（採用）: 3 種とも直下の `dvc.yaml` のステージのまま残し、pre-commit の hook が、直下の `dvc.yaml` の foreach の並びを
  例の deps に合わせて書き直してから、`dvc repro -s` で Python と TOML の正規形のステージを実行する。仕組みは今の 1 つのままで、
  `-s` を付けない `dvc repro` は、今と同じく上流の正規形のステージを自動で実行する。`check-skip-upstream.py` の `RUN_FIRST`、
  正規形のテスト、元の .py と正規形のスクリプトの md5 の記録（直下の `dvc.lock` の deps）も変わらない。短所は 2 つある。hook は
  直下の `dvc.lock` を書き直す。直下の lock は元のファイルの md5 を持つので、注釈だけの編集でも lock が変わり、hook はコミットを
  止めて書き直したファイルを示す（今は同じことを、止まった後に人が `dvc repro -s` で行っている）。また、hook が DVC の
  worktree ごとの排他を取るので、同じ worktree で `dvc repro` が走っている間のコミットが止まりうる（#0268 の経緯の排他の項から
  の見込みで、確かめていない。ジョブが走っている worktree は変えない決まりなので、当たる場面は少ない）
- 案 P2（親の案）: Python と TOML の正規形を DVC のステージから外し、git で追跡する普通のファイルにする。pre-commit の hook が
  正規形のスクリプトを直接呼んで書き直し、テストが元のファイルと照らす。実行ファイルの正規形（binary-forms）は `build` の
  出力（`bin/`）に依るので、`build` とともに直下の `dvc.yaml` に残す。直下の `dvc.lock` の項は 481 から 5（`build` と
  binary-forms の 4）に減る。成り立つが、次を作り直すことになる
  - `-s` を付けない `dvc repro` が正規形を書き直さなくなる。入力の TOML を変えてコミットの前に `dvc repro` を流すと、正規形が
    古いので、ステージが飛ぶか、新しい TOML で走って lock に古い正規形の md5 が入る。すべての実行の入口（`scripts/dvc-repro.py`、
    `examples/stage_runner.py`、付け直しのコマンド）が、`dvc status` の前に正規形を書き直すか照合する必要がある
  - Python の正規形のバイトは Python の版に依る（ADR-0210）。今のテストは、直下の `dvc.lock` が記録した元の .py の md5 と同じものを
    比べ直さないことで、Python の版を上げた後に、変えていないファイルの正規形を書き直させない。この記録と、正規形のスクリプト
    自身（`scripts/normalize_python.py`。今は python-ast のステージの deps）が変わったことの検出を、lock の外に持つ必要がある
  - 書く対象の並びは、例の deps に加えて、直下の `dvc.yaml` に残る binary-forms の deps
    （`python-ast/scripts/normalize_binary.py.ast`）からも決める
  - `check-skip-upstream.py` の `RUN_FIRST` から `python-ast@` と `toml-values@` を外し、上の照合に替える。これらのステージの名前を
    読むのは、`check-skip-upstream.py` とそのテスト、`scripts/test_normalize_python.py`、`scripts/test_normalize_toml.py` である
    （main adc380560 で `git grep`）。スキル dvc-relock、compute、openmc-reference の `dvc repro -s dvc.yaml:python-ast` などの
    手順も同じブランチで直す
- 案 P3: 3 種とも DVC から外す。実行ファイルの正規形を書くには先にビルドが要り、`bin/` は追跡しないので、コミットの hook では
  書けない。採らない

測った値（この ADR のブランチの worktree、main adc380560 と同じ木、1 コア、手元、2026-11-19。各 1 回）: 正規形のステージの
`dvc status dvc.yaml:python-ast dvc.yaml:toml-values` は 5.7 秒、何も変わっていないときの同じ 2 組の `dvc repro -s` は 1.8 秒。
正規形のスクリプトを 476 ファイルに 1 つずつ直接呼ぶと 9.4 秒（1 ファイル約 20 ミリ秒。プロセスの起動を含む）で、同じ
プロセスですべての TOML の正規形を作って比べるテスト（`test_normalize_toml.py` の `RepositoryDepsTest`）は 0.6 秒。時間はどちらの
案でも数秒で、時間は案を分けない。

直下の `dvc.lock` の衝突も、案をほとんど分けない。直下の lock だけを変えたコミット 226（棚卸し）を、変えた項で分けると、
`build` だけが 181、python-ast だけが 30、toml-values だけが 6、python-ast と toml-values が 1、`build` と python-ast が 5、
`build` と binary-forms が 1、`build` と binary-forms と python-ast が 2 である（main adc380560 で、コミットとその親の直下の
`dvc.lock` を YAML で読み、項が違うステージの組の名前で分けた。2026-11-19）。案 P2 で直下の lock を変えなくなるのは、python-ast か
toml-values だけを変えた 37 で、`build` を変えた 189 は案 P2 でも残る。

どちらの案でも、rebase の pick では pre-commit の hook が走らないので、rebase の後に正規形を書き直すのは付け直しのコマンドである。

rebase の後に、付け直しのコマンドがどの計算のステージを再実行するか（この ADR の前は、スキル dvc-relock の前半の 3 の「数秒で終わると
分かっているステージだけ実行する」を人が選んでいた）:

- 案 T1（この ADR の前の版が勧めた）: ステージごとの実行時間を記録し、付け直しのコマンドが、changed のステージのうち前回の時間が閾値より
  短いものだけを再実行する。記録が無いステージは実行せず、一覧に出す。同じ記録から、changed のステージの時間の和（作り直しの
  残高の見積もり）を出せる（決定と理由の「changed の扱い」の計画に使う）。今ある記録は、核種ごとの xs の前回の CPU 時間
  （`stage-cpu-seconds.json`。`examples/stage_runner.py` が書く。ADR-0193）だけで、4 つの例にある。すべてのステージに広げるには、
  決めることが 2 つある。1 つは量で、CPU 時間は複数のスレッドのステージで経過時間の数倍になるので、閾値と残高の見積もり
  （排他のジョブの経過時間）には、経過時間とスレッドの数を記録する。もう 1 つは書き手で、`scripts/dvc-repro.py` は数えた後に
  `os.execvp` で dvc に置き換わり、`dvc repro` は複数のステージを 1 つのプロセスで流すので、今の入口はステージごとの時間を
  取れない（ステージを 1 本ずつ呼ぶか、cmd を時間を測るラッパーで呼ぶかは、実装のブランチで決める）。短所は、記録のファイルが
  増え、実行のたびに書き換わることと、重いステージの記録が次に実行するまで生まれないこと（最初の本番の作り直しの計画には
  使えない。検証の記録と Slurm のログにある時間から最初の値を入れるかは、実装のブランチで決める）。採らない。軽いステージを
  自動で流す必要を示せない（自動で流すのは構わないが、わざわざ自動で流す必要があるのかが分からない、がユーザーの返事。
  ユーザー 2026-11-19）。要ると分かったときに足す
- 案 T2: `dvc.yaml` のステージに、rebase の後に再実行してよいことを宣言する（ステージの `meta`）。判断はステージを足すときの
  1 回になり、レビューで見える。時間が延びたステージの宣言が古いまま残りうる。残高の見積もりには使えない。採らない。
  理由は案 T1 と同じで、自動で流す必要を示せない
- 案 T3: 付け直しのコマンドは計算のステージを実行しない。軽いステージの再実行は、`-s` の入口を人が呼ぶ。比較のツールを
  main が直した後の rebase のたびに、数秒で作り直せる比較の JSON が changed のまま残り、残高に軽いものが混ざる。採らない。
  再実行と lock の整えが別の呼び出しに分かれ、再実行の後の検査（`check-dvc-lock.sh`）を呼ぶ側が続けて行うことになる
- 案 T4（採用）: 付け直しのコマンドは、呼ぶ側が名前で指定したステージだけを再実行する。指定が無ければ、計算のステージを
  実行しない。時間の閾値も、実行時間の記録も持たない。再実行するかは、その結果が要るかと時間の見積もりで、流す側が決める
  （changed は残高で、結果が要るときだけ流す、と同じ決め方）。短所は案 T3 と同じで、指定しなかった軽いステージは changed の
  まま残る。コマンドが残した changed のステージの一覧を出すので、呼ぶ側はそこから選べる
- 案 T5: 案 T4 に、上流の outs が lock のとおりで、前に実行した記録が軽いステージをまとめて流す指定を足す（親の案）。
  ねらいは、自動の再実行を外すと失うものを残すことである: rebase の後に軽いステージ（小さな格子計算、比較）の lock と比較の
  JSON が前のコードのまま残って記録の表の出どころが古くなることと、今のコードで再実行して結果の変化に気付く機会が減ること。
  確かめた事実（main 08d0a0d8b、2026-11-19）:
  - ほかの検査は、これを担っていない。`cargo test` のうち本番のライブラリを読むテスト（crates/lattice/tests/track_table.rs）は
    `#[ignore]` で、既定では走らない。pre-commit の hook `verification-tables` は、記録の表が比較の JSON と合うかを見るだけで、
    JSON が今のコードの結果かは見ない
  - 今の自動の再実行も、これを担っていない。付け直し（スキル dvc-relock）は DVC のステージを含むブランチの rebase の後にだけ
    行い、対象は rebase で deps が変わったステージである。ステージを含まないブランチがコードを変えても、main の軽いステージは
    再実行されず、changed のまま残る
  - 「記録が軽い」を機械が決めるには、案 T1 のステージごとの実行時間の記録が要る

  採らない。記録の出どころが古くなることは、changed を残高として扱う決定に含まれ、記録は出どころのコミットを持つ（ADR-0122）。
  結果の変化に気付くことは要るが、付け直しのコマンドに持たせても、ステージを含むブランチの rebase のときにしか働かない。
  コードを変えるブランチのすべてに掛かる検査として別に決める（#0299）

形式を変える修正（修正の後の実行ファイルが、`dvc.lock` の指す上流の出力を読めなくなる修正）を見分ける方法。形式の名前と
読み手の今の姿（main 08d0a0d8b、2026-11-19 に読んだ）:

- 形式の名前の定数は 9 つある（`xlc-multigroup`、`xlc-table`、`xlc-medium`、`xlc-pin-powers`、`xlc-axial-pin-powers`、`xlc-chain`、
  `xlc-depletion-history`、`xlc-core-history`、`xlc-lattice-checkpoint`。`git grep -n 'const \(AXIAL_\)\?FORMAT' crates`）。どれも版の数を
  持たない。足した後に名前を変えたコミットは無い（`git log -G'^const (AXIAL_)?FORMAT' -- crates` の 12 コミットは、定数を足したか、
  `xlc-fewgroup` を消したか、ファイルを移したもの）
- Rust の読み手があるのは 7 つである（`xlc-multigroup`、`xlc-table`、`xlc-medium`、`xlc-chain`、`xlc-depletion-history`、
  `xlc-core-history` の `from_msgpack` と、`xlc-lattice-checkpoint` の `Checkpoint::read`）。`xlc-pin-powers` と
  `xlc-axial-pin-powers` は書くだけで（crates/format/src/pins.rs）、読むのは Python の比較のツールである。Python のツールにも
  形式の名前を確かめる読み手がある（ピン出力の examples/c5g7/compare.py、チェーンの examples/depletion/compare_chain.py、
  ライブラリの examples/vera/positive_library.py など。履歴とテーブルを読むツールもある）。Python のツールが書いて Rust が読む
  出力もある（examples/colorset/without_df.py が書くテーブル）
- Rust の読み手は、読んだ後に名前が定数と同じかを確かめる。古い形式を止めるのは名前でなく、serde が読む
  ときの項目の検査である: 必須の項目が無い、知らない項目がある（読む構造体の `deny_unknown_fields`）、そのあとの値の検査。
  例: 6395d298e（2026-11-07）は `xlc-multigroup` に必須の項目 `inverse_velocity` と `activation` を足し、名前は変えていない。
  それより前のライブラリは、項目の欠けで止まる
- `#[serde(default)]` を付けた項目（`xlc-table` の `kinetics`、`cooling` など。1f1ad849a）を足した修正では、古い出力は、その項目が
  無いものとして読める

- 案 R0: 人が差分を読んで判断する（前の版。判断の方法を書いていなかった）。どうやって判断するのかをユーザーが尋ねた
  （ユーザー 2026-11-19）。採らない
- 案 R1（採用。親の案を一部変えた）: 読むだけの検査。マージの前に、ブランチの実行ファイルの読み手で、`dvc.lock` が指す上流の
  出力を読み、読めなければ形式を変える修正とする。例外の目的（修正の後に下流の計算が止まるか）を、そのまま確かめる。
  親の案は形式ごとに 1 つを読むとしたが、同じ形式の出力でも、changed のまま残る古いものと作り直した新しいものでは、
  書いた実行ファイルが違い、同じ実行ファイルが書いたものでも、省ける項目（`xlc-table` の `micro`、`kinetics` など）の有無が
  違う。1 つでは、読まなかった組の中の項目を変えた修正を拾えないので、対象の出力をすべて読む。
  拾えないのは、形を変えずに項目の意味だけを変えた修正（古い出力が読めてしまう）と、Python の読み手だけが読む形式である
- 案 R2: 形式の名前に版の数を足し（`xlc-table-2` など）、ブランチの差分に名前の定数の変更があれば形式を変える修正とする。
  読まないので、出力もビルドも要らない。採らない。版を上げるのは書き手の判断で、上げ忘れを拾えない。上の例のとおり、
  これまでの形式の変更は名前を変えずに入っている。版の数を今すべての形式に足すと、すべての出力が読めなくなる
- 案 R3: 形式ごとに小さな見本のファイルをコミットし、読み手がそれを読むテストを置く。形式を変えると見本を作り直すので、
  見本の差分で分かる。採らない。見本は本番の出力の持つ項目（省ける項目の有無の組）を尽くさず、`dvc.lock` の指す出力が
  読めるかを確かめない

案 R1 の実装（移行の段 5 のブランチ feat/0298-readable-outputs-check で比べた）。判断の軸は、読み手が本番と同じコードを
通ること、検査の時間、出力を戻していない worktree での扱い、仕組みを増やす保守の費用である:

- 案 E1（採用）: 読み手だけを呼ぶ実行ファイル（crates/outputs の `read-outputs`）を足す。出力の `format` を読み、その名前の
  定数を持つ形式の `from_msgpack` に渡す（定数を公開した）。名前を変えた形式の古い出力は、どの読み手にも当たらずに止まる
- 案 E2: 本番の実行ファイル（`bin/xs`、`bin/lattice`、`bin/core`）に読むだけのサブコマンドを足し、出力を deps にするステージの
  実行ファイルで読む。採らない。呼ぶ読み手の関数は案 E1 と同じで、本番と同じコードを通ることは案を分けない。同じ形式を読む
  実行ファイルの数だけ読み直し、検査の前に `build` を流すと直下の `dvc.lock` が書き換わる
- 中身を作業ツリーから読む案: 採らない。出力を戻していない worktree で読めず、走っているジョブが書いている途中の出力に
  当たりうる。DVC のキャッシュから lock の md5 で読めば、どちらも起きない（採用）
- 検査を実行する場所。pre-commit の hook は、実行ファイルを変えうるブランチのコミットのたびに読み、rebase の pick では
  走らない。マージの hook（pre-merge-commit）はリポジトリの外の claude-harness にあり、run-checks.sh を呼ぶ。run-checks.sh が
  どの差分でも実行する `scripts/run-rust-docs-tests.sh` から呼ぶ（採用）。実行ファイルを変えうるブランチかは、検査が差分から
  決める（文で人に判断させない）
- Python のツールの読み手を検査に入れる案: 採らない。形式の名前を確かめて読む Python のファイルは 32 あり（形式の名前の
  `git grep`、main 10824a18b）、共通の読み手が無いので、読むだけの入口はツールごとに要る。入れるには、先に 32 の読み手を
  1 つの部品に寄せることになり、Python を検証のツールにだけ使う決まり（ADR-0019）の下で、その保守を検査のために持つことに
  なる。Python の読み手も形式の名前を確かめるので、読めない出力は黙って誤らずに止まる

手元の生の `dvc repro -s`（例のステージを目標にしたもの）を Claude Code の hook で止めるか（移行の段 2 のブランチ
feat/0298-skip-upstream-route で比べた）。判断の軸は、上流の確認を飛ばす誤りを防げるか、普通の呼び方を誤って止めないか、hook が
増える保守の費用で、hook にするのは例外の無い規則だけとする:

- 案 H1: 止める。例のステージを目標にした生の `dvc repro -s` を hook が止め、`scripts/dvc-repro.py -s` へ導く。手元でも上流の
  確認を飛ばせなくなる。採らない。規則に例外があり、その線を hook がコマンドの文字列から確かに引けない。直下の `dvc.yaml` の
  ステージ（`build` と正規形）の `-s` は、スキル dvc-relock が直接呼ぶ（段 1 の pre-commit の hook と段 3 の付け直しのコマンドも呼ぶ）。目標が例のステージかは、目標の書き方と
  cwd で決まる（直下からの `dvc repro -s build` は直下のステージ、`cd examples/vera && dvc repro -s lattice-1B` は例のステージ）ので、
  hook はコマンドの中の `cd` と Claude Code の cwd をたどって目標を解く必要がある。`-s` は `--single-item` や、束ねた短い
  オプション（`-fs`）でも書ける。読み違えれば普通の呼び方を止めるか、止め損なう。止める hook とテストが 1 組増える
- 案 H2（採用）: 止めない。重い計算は Slurm に流し（スキル compute）、Slurm に投げる生の `dvc repro` は `-s` の有無によらず
  今の hook（ADR-0257）が止めるので、hook の外に残るのは手元で流す軽いステージだけである。そこで上流を確かめずに作っても、
  上流の `changed outs` は `dvc status` に残り、作り直しは軽い。例のステージの `-s` をラッパーに通すことは、スキル compute の文で
  示す。短所は、手元では文に頼る（ADR-0257 の背景の、文で守る形）ことで、手元の生の `-s` で上流の確認を飛ばした例が出たら
  案 H1 を比べ直す

docs/0258-settle-open-points で比べ始め、ADR-0260 に分けた。DVC の挙動、比べた案、採らなかった案の理由は、ADR-0260 の背景と

## 決定と理由

案 F にする。正規形の置き場は案 P1、rebase の後に再実行するステージは案 T4、形式を変える修正の見分け方は案 R1、手元の生の
`-s` は案 H2（hook で止めない）にする。
案 F、案 P1、案 T4 の向き（自動で流さない）、案 R1 の向き（判断を機械の検査にする）は、ユーザーの決定である（ユーザー
2026-11-19）。案 R1 の方式は、担当が事実を確かめて比べた結果である。案 R1 の検査の位置づけ（「形式を変える修正の検査」の
最初の項）と、その実装を移行の最後に回すことは、親のセッションの決定である（2026-11-20）。案 H2 は、移行の段 2 の担当が
比べて決めた（2026-11-20）。案 R1 の実装（案 E1、キャッシュから読むこと、run-checks.sh から呼ぶこと、Python の
ツールの読み手を入れないこと）は、移行の段 5 の担当が比べて決めた（2026-11-20）。ユーザーは、機能を足せば結果が
変わって再実行するのは当たり前で、それを担保するのが DVC ではないかと尋ね、親が位置づけを答えた。ユーザーは、位置づけへの
賛否を述べていない（ユーザー 2026-11-20）。パスを動かしたときの lock の扱いは、ADR-0260 に分けた。

### changed の扱い

- changed は、出力が今のコードと入力より前のものだという情報で、作り直しの残高である。即時の作り直しの義務ではない
  （ADR-0130 の帰結と同じ）。残高は `dvc.lock` に残り、`dvc status` と `scripts/count-changed-stages.py` で読む
- 修正は、作り直しを待たずに main に入れる。結果を変える修正も、結果を変えない修正も同じである
- 上流の出力の形式を変える修正は別に扱う。形式を変えたら古い形式の読み込みを残さない（CLAUDE.md の方針）ので、その修正を
  入れた後の実行ファイルは古い上流の出力を読めず、上流を作り直すまで下流の計算が止まる。形式を変える修正は、上流の作り直しの
  見積もりと合わせて、入れる時期を決める。どの修正がこれに当たるかは、人の読みでなく下の「形式を変える修正の検査」で決める
- 作り直しは、結果を変える修正をまとめてから、時間を見積もって計画し、1 回で行う。形は docs/plans/upstream-error-budget.md の
  「進め方の決まり」（「作り直しの前」の列が「要」の項目を小さな計算で見積もり、まとめて修正してから作り直す）と同じである
- 依頼とレビューの判断に「ステージが changed になる修正は行わない」と書かない。changed を増やすことを、修正を後回しにする
  理由にしない
- 作り直す前の出力を読む作業は、今までどおり、記録に出どころのコミットを書く（ADR-0122）

### 残すもの

- 例の `dvc.yaml` と `dvc.lock`、キャッシュ、`.dvc` による保管（ADR-0222）
- deps の正規形の 3 種（python-ast、toml-values、binary-forms。ADR-0210、ADR-0254、ADR-0255）。正規形は git にコミットしたまま
  残す。コミットしてあれば、checkout の後に書き出し直さずに DVC が deps として読め、正規形の差分がレビューで見える
  （ユーザー 2026-11-19 の相談の要約）
- 走るステージを数えるラッパーと hook（ADR-0257）、生の `dvc checkout` を止める hook（ADR-0223）

### rebase の後の付け直し

- rebase の後の付け直し（スキル dvc-relock の前半）は続ける。rebase で deps が変わったことを理由には、計算のステージを再実行しない（ADR-0130 の帰結）
- 文章の手順を、1 本のコマンドに移す。既にある部品（`scripts/dvc-checkout.py`、`build` と正規形の 3 組のステージの実行、
  `scripts/check-references-shell.sh`、`scripts/count-changed-stages.py`、`scripts/check-skip-upstream.py`、
  `scripts/check-dvc-lock.sh`）を順に呼び、止まるべきところで終了コード 1 で止まる、テストできる Python にする。止まるところは、
  今のスキルが「止める」「原因を調べる」と書くところである（戻らない出力、`changed outs` だけのステージ、
  `references-shell.txt` の食い違い、`dvc status` の失敗、読めない lock）。Python と TOML の正規形は、止まらずに書き直す
  （今のスキルの前半の 2 と同じ）
- コマンドは、計算のステージを自動では再実行しない。再実行するのは、呼ぶ側が名前で指定したステージだけである（案 T4）。
  時間の線（今の文書の「数秒」）は置かない。再実行するかは、その結果が要るかと時間の見積もりで、流す側が決める。指定した
  ステージは「実行」の `-s` の経路で流すので、上流の確認を通る。重いステージを指定するなら、コマンドごと Slurm に投げる
- コマンドは、実行したステージ、残した changed のステージの一覧、コミットするファイルを出して終わる。lock と正規形の
  差分のコミットと、再実行したステージの記録のコミットの書き直し（スキル dvc-relock の前半の 4 と 5。付け替えは
  `commit-refs remap`）は、呼んだ側が行う（記録の本文に書く hash は、コミットの後にしか決まらない）
- スキル dvc-relock の前半は、このコマンドを呼ぶことと、止まったときの調べ方だけにする

### 正規形の置き場

- Python と TOML の正規形は、pre-commit の hook がコミットのその場で書き直す。今の hook（`python-ast`、`toml-values`）は検査だけで、
  止まった後に人が `dvc repro -s` を実行している。hook が書き直したときは、ほかの書式を直す hook と同じく、コミットを止めて
  書き直したファイルを示す
- 置き場は案 P1 にする: 3 種とも直下の `dvc.yaml` のステージのまま残し、hook は Python と TOML の 2 組のステージを
  `dvc repro -s` で実行する。ステージを足すときに、読む .py と TOML を直下の `dvc.yaml` の foreach に登録し、正規形と直下の
  lock を一緒にコミットする手数（スキル compute の deps の項）も、hook が並びを例の deps から書き直すことで無くす。理由は、案 P2 の利点とした直下の lock の衝突の減り方が小さく（直下の lock だけを変えたコミット
  226 のうち 37。`build` を変えた 189 は残る）、案 P2 は、DVC の上流のステージとして今は自動で保たれている性質（`dvc repro` の前の書き直し、元の md5 と
  スクリプトへの依存の記録）を手書きで作り直すことになるためである。正規形と lock の付け替えで無意味な再計算を避けることは、
  DVC を入れた当初から求めていたことである（ユーザー 2026-11-19）
- 実行ファイルの正規形は、コミットの hook では書かない。Rust を変えたコミットは、`build` を実行しなくてもマージできる（今と
  同じ。スキル dvc-relock の後半）。`build` と binary-forms は、付け直しのコマンドと、ステージの実行の前に走る

### 実行

- 上流を飛ばす実行（`-s`）を数秒のステージに限る条件（ADR-0184 の `-s` の 2 つの例外の「数秒で終わる」）をやめる。上流の
  outs が `dvc.lock` のとおりなら、重いステージも `-s` で 1 本だけ実行してよい
- 上流の確認は残す。`scripts/dvc-repro.py` に `-s` の経路を足し、`scripts/check-skip-upstream.py` と
  `scripts/check-references-shell.sh` を通ってから `dvc repro -s <目標>` を実行する。上流が `changed outs`、`changed command`、
  `changed checksum` を持てば止まる（ADR-0184 の決定と同じ種類）。上流の outs を戻していない作業ツリーで下流を作る誤りは、
  `changed outs` で止まる。正規形のステージが changed なら、先に実行する（`RUN_FIRST`）
- 上流が changed（deps だけ）のまま下流を作っても、下流の lock の deps の md5 は上流の lock の outs の md5 と一致し、lock の
  上流と下流の記録はつながったまま残る（ADR-0184 の決定と理由の最後の段落）。上流の古さは、上流の lock の項の deps から読める
- 記録には、ADR-0184 のとおり、上流の出どころ（上流を実行したコミットと分岐点）を下流と別に書く
- 重いステージの `-s` は Slurm に投げる。hook `block-raw-dvc-repro-in-slurm.py` は Slurm に投げる生の `dvc repro` を止めるので、
  上流を飛ばして重いステージを Slurm に流す経路は、ラッパーの `-s` の経路である（段 2 の前は、ラッパーが `-s` を受けず、経路が
  無かった）。走るステージを数える目的は、意図しない上流の実行を防ぐことなので、`-s` では
  走るステージは目標の 1 本で、数える代わりに上の上流の確認を通す。参照解の許可（`--allow-reference`）は `-s` でも掛ける。hook は
  今のまま、Slurm に投げる生の `dvc repro` を `-s` の有無によらず止め、ラッパーへ導く
- 手元でも、例のステージを目標にした `-s` はラッパーを通す（上流の確認を飛ばさないため）。直下の `dvc.yaml` のステージを
  目標にした `dvc repro -s` は、今のまま直接呼ぶ（pre-commit の hook と付け直しのコマンドの中の呼び出しを含む）。python-ast と
  toml-values は上流のステージを持たず、binary-forms は `build` の下流なので、`build` の後に呼ぶ（今のスキル dvc-relock の
  前半の 2 の順）。手元の生の `-s` は、Claude Code の hook で止めない（案 H2）
- 本番の作り直し（記録に載せる一揃いの計算）は、`-s` を付けずに、上流から流す（ADR-0184 の案 B のまま）

### 形式を変える修正の検査

- 位置づけ: この検査は、コードを変えた後に再実行が要るかを決めない。それは DVC が changed で担保する（コードを変えると、
  deps の実行ファイルの正規形が変わる）。検査が答えるのは、changed をためたまま、まとめての作り直しまで、古い上流の出力で
  下流の作業を続けられるか（修正を入れても古い出力を読めるか）だけである。検査が無くても、読めない出力は読み手のエラーで
  止まり、黙って誤った結果にはならない。検査は、それをマージの前に知らせる。実装は、移行の最後に回す（「移行の順」）
- 形式を変える修正とは、その修正の後の実行ファイルが、`dvc.lock` の指す上流の出力を読めなくなる修正である。これを、読んで
  みる検査で決める（案 R1）
- 検査（`scripts/check-readable-outputs.py`）は、ブランチのコードの Rust の読み手で出力を読み、結果を捨てる。計算はしない。
  読み手は crates/outputs の `read-outputs` で、出力の `format` の名前で各形式の `from_msgpack` を選び、`xs range` の書く範囲の
  TOML は xs のライブラリの読み手で読む（案 E1）
- 対象は、xlc の実行ファイルを呼ぶステージ（deps に `binary-forms/` の実行ファイルの正規形を持つステージ）の deps のうち、
  計算の出力であるもののすべてである: 例の lock のステージ（ほかの例の lock のステージを含む）の outs のファイル、outs の
  ディレクトリの中のファイル、deps のディレクトリの下にあるステージの outs（核種ごとのライブラリ）、`.dvc` で保管した生成物
  （ADR-0222）。直下の `dvc.lock` の出力（`build` と正規形）は計算の出力でないので読まない。lock に hash の無い（流していない）
  ステージの出力は対象にしない
- 中身は作業ツリーでなく、DVC のキャッシュから上流の lock の outs の md5 で読む。出力を戻していない worktree でも同じ結果になり、
  走っているジョブが書いている途中の出力（キャッシュと lock に入る前）には当たらない。キャッシュに無い出力は止める
- 実行ファイルを変えうるブランチ（直下の `dvc.yaml` の `build` の deps を変えたブランチ。crates/ のほか、Cargo.lock、
  rust-toolchain.toml、flake.lock などを含む）は、マージの前にこの検査を通す。run-checks.sh がどの差分でも実行する
  `scripts/run-rust-docs-tests.sh` が検査を呼び、検査は main との分岐点からの差分が `build` の deps（と検査の script と下の
  一覧）に当たるときだけ読む。読めない出力があれば、検査は読めない出力とそれを書いたステージ（`.dvc` の生成物は、その
  `.dvc` のファイル）を出して、終了コード 1 で止まる
- 読めない出力を残してマージするには、上流の作り直しの見積もりと時期を書いた open の issue を、検査に示す。通すのは、
  その issue に結び付けた出力（md5 で示す。パスは動かしうる）だけである。issue が open の間は、後のブランチでも同じ出力を通す（main に入った
  後は、作り直すまで読めないままのため）。ほかの出力が読めなくなれば、後のブランチで止まる。上流を作り直したら issue を
  閉じる。一覧は `scripts/unreadable-outputs.toml` の `[[output]]`（`md5`、`issue`、`path`）で、`md5` はファイルの md5 か、
  ディレクトリの outs の `.dir` の md5（中のファイルをすべて通す）である。issue が無いか閉じた項は、差分によらず止まる
- 検査の対象は Rust の読み手だけである。Python のツールが読む出力（ピン出力の 2 つの形式のほか、比較と検査のツールが読む
  履歴、テーブル、チェーン、ライブラリ）が、形式を変える修正の後に Python の読み手で読めるかは検査しない（検討した案の
  Python のツールの読み手を入れる案）。これらは差分を読んで判断する残りである
- 検査が拾えないのは、形を変えずに項目の意味だけを変えた修正である。項目の意味を変える修正は、形式の名前を変える
  （名前に版の数を付ける。`xlc-table-2` など）。名前が変われば、Rust の読み手が古い出力を名前で止め、検査が拾う。同じ名前と形の
  まま意味を変えると、古い出力を黙って読み違えるので、名前を変えることは CLAUDE.md の方針（怪しい入力はエラーで止める）からも
  要る。名前を変えたかは書き手とレビューが見るので、ここは機械の検査にならずに残る
- `#[serde(default)]` の項目を足した修正では、古い出力はその項目が無いものとして読め、検査は通る。下流は止まらないので、
  待たずに入れてよい。古い上流に無い項目を下流がどう扱うか（その項目が要る計算で止まるか）は、読み手の側の検査の範囲である

### パスだけを動かしたとき

- パスだけを動かしたときの扱い（動かしただけでは再計算にしないための、同じファイルかの判定と、lock のパスを書き換える
  ツール）は、この ADR では決めず、ADR-0260 で決める（この ADR のブランチで比べ始めて分けた）

### 移行の順

段ごとに 1 本のブランチにし、各段の後で main は run-checks.sh を通る。重いステージの再実行は、どの段にも無い。テストのケースは
実装のブランチで詰める。段 2 と段 3 は同じ入口（`scripts/dvc-repro.py`）とスキル dvc-relock を変え、段 3 のコマンドは、名前で
指定されたステージを段 2 の `-s` の経路で再実行するので、段 2 を先にする。段 1、段 4、段 5 は、ほかの段に依らない。
パスを動かしたときのツール（ADR-0260 の「移行」）は、examples の下の整理より前に要るので、これらの段より先に着手する。段 5 は
最後に回す（検査が無くても、読めない出力はエラーで止まるため。「形式を変える修正の検査」の位置づけの項）。

1. 正規形の hook。pre-commit の hook `python-ast` と `toml-values` を、検査の前に、直下の `dvc.yaml` の foreach の並びを例の deps に
   合わせ、2 組のステージを実行する形にする。例の lock と正規形のテストは変わらない。スキル compute の、foreach に足す手順を
   合わせる
2. `-s` の経路。`dvc-repro.py` の `-s` の経路を TDD で足し、ADR-0184 の決定と理由の `-s` の 2 つ目の例外と、ADR-0257 の決定の
   「`-s` は受けない」を今の決定に直して、それぞれの「## 変更」に 1 項を足す。手元の生の `-s` を hook で止めると決めたら、
   ADR-0257 の決定の「`slurm-run.sh` の外の `dvc repro` は止めない」も同じ項で直す。スキル compute、dvc-relock、openmc-reference の
   `-s` の記述を合わせる
3. 付け直しのコマンド。コマンドを TDD で作り、スキル dvc-relock の前半をコマンドを呼ぶ形に書き直す。ADR-0130 の帰結の
   「数秒で終わるステージだけは再実行してよい」と、ADR-0184 の `-s` の 1 つ目の例外の「数秒で終わり」を、時間の線を置かない形
   （再実行するかは、その結果が要るかと見積もりで、流す側が決める）に直す
4. changed の扱いを規則に書く。スキル compute の DVC の項と、依頼の書き方（「changed になる修正は行わない」と書かない）に
   決定の「changed の扱い」を書く。docs/plans/upstream-error-budget.md の「作り直しのときに入れる xs と lattice の修正」（今の
   「結果を変えない xs と lattice の修正」）は、結果を変えない修正を作り直しまで待つ形なので、待たずに入れる形に直す。この段は文書だけである
5. 形式を変える修正の検査。読むだけの入口と検査を TDD で作り、スキル topic-start のマージの前の手順と、スキル compute の DVC の
   項に、検査を通すことと、項目の意味を変えるときに形式の名前を変えることを書く

この ADR を書いたブランチ（docs/0258-keep-dvc-and-automate-relock と、ユーザーの返事で決定を書き直した docs/0258-settle-open-points）は決定だけを書き、
スキル、CLAUDE.md、script、hook、`dvc.yaml`、`dvc.lock`、ほかの ADR は変えない（ADR-0259 の 1 行が引いていたこのブランチのコミットの hash を、rebase の後に付け替えたことを除く。その行は、ADR-0259 を ADR-0260 に付け替えたコミット 273129162 で ADR-0259 から消えた）。一部を変える ADR（ADR-0130、ADR-0184、
ADR-0257）は、上の段の実装のブランチで、その ADR の決定と「## 変更」を直す（ADR-0212 は、ADR-0260 のツールのブランチで直す）。ADR-0193 の CPU 時間の記録は変えない。

### 帰結

- 修正のコミットは、作り直しを伴わずにマージできる。changed の残高は増え、作り直しは計画した 1 回で行う
- 残高の大きさは、`scripts/count-changed-stages.py` の changed の数で読む。時間の和を出す手段は無く、ステージごとの実行時間の
  記録も持たない（案 T1 を採らない）ので、作り直しの見積もりは、文書の値（背景の「作り直しの規模」）、検証の記録、Slurm の
  ログから人が出す
- 移行の順の段はすべて入った。段 1（pre-commit の hook `normalized-forms`、`scripts/normalized_forms.py`）、
  段 2（`scripts/dvc-repro.py -s`）と段 3（付け直しのコマンド `scripts/dvc-relock.py`）は入り、ADR-0184 の 2 つの例外、ADR-0130 の
  帰結、ADR-0257 の「使い方」を合わせた。スキル dvc-relock の前半は、コマンドを呼ぶことと、止まったときの調べ方になった。段 4 も入り、
  「changed の扱い」をスキル compute（本番の作り直しの項）と topic-start（記録の計算の後の指摘）、
  docs/plans/upstream-error-budget.md の「結果を変えない xs と lattice の修正」、changed を理由に待っていた open の issue
  （#0174、#0291、#0304）に書いた。依頼の書き方は、全体のスキル（delegate）でなく、親とレビューが常に読む CLAUDE.md の方針に
  1 文で置いた。#0241 が拠る ADR-0232 の決定（lattice の移動を、次に lattice の実行ファイルが変わる作業に回す）は直していない。
  段 5（`scripts/check-readable-outputs.py` と crates/outputs の `read-outputs`）も入り、スキル topic-start のマージの節と compute の
  形式の項が検査を指す
- 形式を変える修正の検査は、実行ファイルを変えうるブランチの run-checks.sh に約 30 秒を足す（main の出力の 2001 ファイル、
  6 GB を 1 コアで読んで 22.0 秒、全体で 27.0 秒。「確認」の段 5）。読むのは 1 ファイルずつで、記憶は最大で約 9.4 GB を使う
  （p2 のライブラリ 1.5 GB を読むとき）。数分を超えないので、対象を変えた crate の読む形式に絞ることはしない
- 差分を読んで判断する残りは 2 つある。Python のツールの読み手が古い出力を読めるか（検討した案の Python のツールの読み手を
  入れる案）と、形を変えずに項目の意味だけを変えた修正である。後者は、形式の名前を変える決まり（スキル topic-start のマージの節と
  compute の形式の項）で検査に拾わせる
- 段 1 の hook は、foreach の並びを、追跡しているすべての `dvc.yaml` のステージが deps にする正規形から決め、並びから外れた項の
  直下の lock の項と正規形のファイルも消す（`dvc repro` は、foreach から消えた項の lock を残すため）。付け直しのコマンドも、正規形を
  実行する前に同じ部品で並びを合わせる（rebase の pick は pre-commit の hook を通らない）。hook は .py、TOML、
  YAML、`dvc.yaml`、直下の `dvc.lock`、正規形を変えたコミットで走り、手元で 1 回 1.4〜3.1 秒かかる（「確認」の段 1）
- `-s` の経路は、上流の正規形のステージが changed なら、目標の前にそれを `dvc repro -s` で実行する。直下の `dvc.lock` と
  `python-ast/`、`toml-values/`、`binary-forms/` が書き換わるので、Slurm のジョブでも、終わった後にこれらを目標の lock と一緒に
  コミットする
- 今の残高には、正規形を入れる前からの changed（実行ファイルだけで changed の 1,046。37e3044cb）が入っている。次の本番の
  作り直しで、これは無くなる
- 実行ファイルの正規形が吸収するのは、ソースの行と列の番号の差だけである（ADR-0255）。結果を変えない Rust の修正のうち、
  ほかのバイトも変えるもの（依存の更新、共通のクレートへの移動。#0241）は、作り直しの後も下流を changed にし、残高に結果を
  変えない修正の分が混ざる。案 C2 を退けた理由（残高から結果を変える修正の分を読めなくなる）は、この範囲で案 F にも残る。
  減らす案は #0150 にある（代表の数核種を先に作り、出力の md5 が変わらないものだけを `dvc commit` で取り込む案。決めていない）。
  小さな問題の組で新旧の実行ファイルの出力の一致を確かめてから lock を付け直す形は、#0150 の案にあり、ブランチ
  feat/0150-relock-unchanged-results の worktree に書きかけがある（コミットは無い。2026-11-19）
- 実行ファイルのバイトが変わる変更では、重いステージの lock を `dvc commit` で付け直せるのは、今も ADR が決めた移行だけである
  （ADR-0212 の (b)、スキル compute の `dvc commit` の項。ADR-0260 は、ツールが確かめた移動を一般に許す形に変える）。小さな問題の組で
  新旧の出力の一致を確かめたら付け直せる形にする方向で、#0150 で決める（設計はこの ADR で決めない）。決める必要があるのは次のとおり
  - 小さな問題の組が、どの範囲の変更について「結果を変えない」を代表できるか。核種の処理の種類、燃料の種類、燃焼度を
    変えた組にする（CLAUDE.md の方針の、既定や近似を決める測定と同じ）。組が通らない経路を変えた修正をどう見分けるか
  - 一致の基準。出力のバイトの一致か、許容する差を置くか。差を置くなら、その値の根拠
  - 付け直した lock の出どころ。付け直すと、lock の deps は出力を実際に作ったファイルでなくなる。出力を作ったコミットと、
    一致を確かめたコミットと組を、どこに残すか（ADR-0122 の記録の出どころとの関係）
  - 対象のステージ。xlc の実行ファイルを呼ぶステージ（xs、lattice、core）に限るか、Python のツールと入力の変更、参照解の
    ステージに広げるか
  - ADR-0212 の (b) の条件をどう直すかと、付け直しを誰が実行するか（付け直しのコマンドに入れるか、別のコマンドにするか）
- DVC の固定費は残る。tomlkit の 2 乗の読みは main adc380560（2026-11-19）で直り、p2 の 1 ステージの `dvc status` は 4.3 秒から
  1.3〜1.8 秒になった。`dvc commit` の 1 回の時間（直す前の Slurm 887 で約 100 秒）は、直した後に測られていない。残りは #0268 に
  ある
- `-s` で作った下流は、上流が後に今の deps で作り直されて出力が変わると、作り直しになる。重い下流を `-s` で作るときは、その
  費用を見積もりに入れる
- ステージと lock の決まり（この ADR、ADR-0184、ADR-0257）が掛かるのは、記録に載せる計算である。検討の計算は DVC のステージに
  しなくてよく、`trials/` に入力を置いて本番の実行ファイルで流す（ADR-0122 の「試行の運用」）
- rebase の後に軽いステージを自動で再実行しないので、指定しなかった軽いステージの lock と比較の JSON は前のコードのまま
  残る。今のコードで軽い問題を再実行して結果の変化に気付く検査は、今も無く（検討した案の案 T5）、#0299 で決める
- `issues` は、実装の残り（#0298）、軽い問題を再実行する検査（#0299）、結果を変えない変更での付け直し（#0150）、DVC の固定費（#0268）を結ぶ。背景に挙げた
  #0241 と #0174 は、この ADR が解決する issue ではないので結ばない（後回しにした理由が無くなるだけで、中身はそれぞれの issue で進める）
