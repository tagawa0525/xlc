# ADR-0260: ファイルを動かしたときは、中身のハッシュで同じファイルかを判定して dvc.lock のパスだけを書き換え、再計算にしない

## 背景

ADR-0258 は、changed を作り直しの残高として扱うと決めた。DVC は、ファイルやディレクトリの名前や置き場だけを変えても、
中身が同じままステージを changed にする（下の「DVC の挙動」）。examples の下の整理（ADR-0259、proposed）は多くの入力と
ディレクトリを動かすので、そのままでは残高に、結果を変えない移動の分が混ざる（ADR-0258 の判断の軸の (d)）。

ユーザーの求めは 2 つある。

- 数値計算ではパスは結果に関わらず、ファイルの md5 で足りる。パスを変えても再計算にしない仕組みは早く要り、DVC がパスの
  厳密さを求めるなら、その上に別の仕組みを置いてよい（ユーザー 2026-11-19）
- パスを動かしたときに lock をどう直すかを、親のセッションが、動かす前後のパスの組で対応を取って lock のパスを書き換えると
  説明した場面で、管理するファイルのハッシュはすべて取ってあるのだから、パスによらないファイルだけのハッシュで同じものかを
  判定すべきだと求めた（ユーザー 2026-11-20）

この決定は、ブランチ docs/0258-settle-open-points で ADR-0258 の一部として書き始め、パスを動かしたときの扱いだけをこの ADR に
分けた。changed の扱い、rebase の後の付け直し、実行、形式を変える修正の検査は ADR-0258 にある。

### 判断の軸

- (a) 同じファイルかを、パスでなく中身で判定すること
- (b) 書き換えで、移動のほかの差（動かす前から changed だった理由、移動と同じ変更で変えた中身）を lock に取り込まないこと
- (c) 確かめられないものは書き換えず、changed に残すこと（黙って最新と示さない）
- (d) 出力を戻していない worktree でも使えること

### DVC の挙動

DVC 3.67.1。断りの無いものは、使い捨てのリポジトリ（2 ステージの `dvc.yaml`。deps は内容の同じ 2 つを含む 3 つのファイルと
1 つのディレクトリ、params のファイルが 1 つ、outs は 2 つのファイルと 1 つのディレクトリ）で確かめた（手元、2026-11-20）。

- lock の md5 は、ファイルでは中身のバイトだけの md5 である（`md5sum` の値と同じ。内容の同じ 2 つのファイルは、パスが違っても
  同じ md5 になる）。例と直下の 24 の `dvc.lock` の項は、すべて `hash: md5` である（9,822 項。main 28668154f）
- ディレクトリの md5（`.dir`）は、中のファイルの md5 と、ディレクトリからの相対パスの組を並べた JSON の md5 である（キャッシュの
  `.dir` のファイルを読み、同じ並びから同じ値を計算し直して確かめた）。ディレクトリ自身の名前と置き場は入らない: 中身の同じ
  deps のディレクトリと outs のディレクトリは同じ md5 になり、deps のディレクトリをそのまま動かして lock の `path` を書き換えると
  changed にならない。中のファイルの名前を 1 つ変えると md5 が変わり、`changed deps` になる
- deps のパスを変えると、そのステージは `changed deps` と `changed command`（cmd の文字列が変わるとき）になる。outs のパスを
  変えると `changed outs` になり、それを deps に持つ下流も changed になる
- `dvc.lock` の `path` と `cmd` の中のパスを新しいパスに書き換えると（md5 は書き換えない）、`dvc status` は changed を出さない。
  ステージが changed かは、今のファイルの md5 を lock のパスごとの項と比べて決まるので、パスによる
- params は、lock にファイルのハッシュでなく、`dvc.yaml` が挙げたキーとその値で入る。params のファイルを動かしたステージは、
  lock の `params` のキー（ファイルのパス）を書き換えると changed でなくなる。挙げていないキーの値を変えても changed にならない
- lock の outs の項は、`dvc.yaml` に書いた並びでなく、パスの順に並ぶ。lock からは、定義の中の outs の並びは分からない。動かす
  前のコミットの定義の並びは、DVC のライブラリで読める（`Repo(rev="HEAD")` の `index.stages` が、動かす前の `dvc.yaml` の outs を
  定義の並びで、lock の md5 とともに返す）
- 出力を消した作業ツリー（出力を戻していない worktree に当たる）で、lock の outs の `path` を新しいパスに書き換えると、
  `scripts/dvc-checkout.py` がキャッシュから新しいパスに出力を戻し、その後の `dvc status` は changed を出さない
- `dvc.yaml` と `dvc.lock` を 1 段深いディレクトリに動かすと、動かしていないファイルの相対パスもすべて変わり、すべてのステージが
  changed になる。lock の `path`、`params` のキー、`cmd` を新しい相対パスに書き換えると changed でなくなる。1 つのステージを別の
  `dvc.yaml` に移し、lock の項を移した先の `dvc.lock` に書いても同じである
- lock のステージの項は、ステージの名前で引かれる。foreach の項目がパスのステージ（名前が `<ステージ>@<パス>`）は、パスを
  変えると名前が変わり、lock の項の名前も書き換えるまで changed のままである
- これとは別の層で、DVC はファイルの md5 を取り直すかを、inode、mtime、size で先に見る（dvc-data 3.18.3 の `hashfile/state.py` と
  `hashfile/hash.py`。ADR-0258 のブランチで 2026-11-19 に読んだ）

### 例の今の姿

main 28668154f（2026-11-20）の例の 23 の `dvc.lock`（1,416 ステージ）と直下の `dvc.lock`（481 ステージ）を、YAML として読んで数えた
（数え方は「## 補足」）。

- 例の 1,054 のステージは、git で追跡する deps に、今の中身が lock の md5 と違うものを持つ（動かす前から changed）。うち 1,048 は
  実行ファイルの正規形（`binary-forms/`）で、ADR-0258 の帰結の、正規形を入れる前からの残高に当たる
- cmd は、deps に無いパスを名指しする。deps にあるのは正規形で、cmd が呼ぶのは元のファイルである: 実行ファイル（951 の
  ステージ）、Python のファイル（384）、入力の TOML（258）。ほかに、params のファイル（989）と、`dvc.yaml` の深さで文字列の変わる
  `../..#references`（285）がある
- 989 のステージが、入力の TOML を params に持つ（lock には TOML の md5 でなく、キーと値が入る）
- outs を 2 つ以上持つステージは 250 で、うち 196 は、cmd に現れない outs を持つ。outs が 1 つも cmd に現れないステージは 112
- 1,398 のステージが、git で追跡しない deps（上流の出力、`references/` の下）を持つ。ディレクトリの deps を持つステージは 784、
  ディレクトリの outs を持つステージは 37
- 1 つのステージの deps に同じ md5 の項が複数あるステージは 2
- 直下の 476 のステージ（python-ast の 40 と toml-values の 436）は、名前に元のファイルのパスを持つ
- 例の入力の TOML のうち 1,288 が、`../` で始まる相対パスを値に持つ（`library = "../vera/vera.msgpack"` など。
  `git grep -l '"\.\./' -- 'examples/**/*.toml'`）。ディレクトリの深さや互いの位置を変える移動では、この値を書き換えるので、
  入力の md5 も値の正規形も変わる。入力が読むファイルは、それぞれステージの deps にも並んでいる（ADR-0254 の決定）
- 比較のツールは、出力の JSON に入力のパスと md5 を書く（`"inputs": [{"path": ..., "md5": ...}]`。
  examples/depletion/compare_branch_cross_terms.py など）。入力を動かした後に再実行すると、出力は前と違うバイトになる。記録の
  出どころを出すツール（examples/record_provenance.py の `input_problems`）は、この `inputs` のパスと md5 を、ステージの lock の
  deps のパスと md5 に照らし、合わなければ終了コード 1 で止まる。計算のステージ（xs、lattice、core）の出力に入力のパスが
  入るかは確かめていない（main 08d0a0d8b、2026-11-19 に読んだ）
- 試行（`trials/`。ADR-0122）は DVC のステージにせずに流すので、流したときの deps の md5 の記録を持たない

## 検討した案

案の記号は、ADR-0258 のブランチで付けたものを引き継ぐ（案 M8 と案 M9 はこの ADR で足した）。

動かしたファイルの lock の扱い:

- 案 M1: 何もしない。動かしたステージは changed のまま残り、結果が要るときに再実行する。採らない。背景の 1 つ目の求めに
  反し、残高に、結果を変えない移動の分が混ざる
- 案 M2: 動かした後に `dvc commit` で lock を付け直す。`dvc commit` は今の deps と outs の md5 を無条件に取り込むので、
  移動のほかの差（前から changed だった理由、移動と同じコミットで変えた中身）も取り込む（判断の軸の (b)）。採らない
- 案 M3（ADR-0258 のブランチで 2026-11-19 に勧めた）: DVC の上に、lock のパスを書き換えるツールを置き、対応を、動かす前後の
  パスの組で取る。動かす前のコミットと動かした後の木を比べ、組にしたパスの中身が同じバイトで、ステージの定義の差がパスの
  置き換えだけであることを確かめてから、lock の `path`、`params` のキー、`cmd` の中のパスを書き換える。採らない。背景の
  2 つ目の求めのとおり、同じものかはパスでなくハッシュで判定する。この案がハッシュの集まりで比べる形を退けた理由は 2 つで、
  どちらも成り立たない
  - 「同じ md5 の項が複数あるステージで対応が決まらない」: 中身が同じなので、どれに対応させても、書き換えた後の lock（パスと
    md5 の組の集まり）は同じになる。当たるステージは 2 つである
  - 「動かしたファイルが動かす前から lock と違う項で対応が決まらない」: lock の md5 では決まらないが、動かす前のコミットの
    中身の md5 で決まる（案 M9）
- 案 M8（親の案）: ハッシュで対応を取るツール。ステージの deps の今の md5 の集まりが、lock の deps の md5 の集まりと同じなら、
  パスが違っても同じ計算とみなし、lock の `path`、`params` のキー、`cmd` の中のパスを今のものに直す。同じでないステージ
  （動かす前から changed）は書き換えず、changed のまま残す。最新のステージでは成り立つ（上の DVC の挙動）。採らない。
  動かす前から changed のステージで、書き換えないと失うものがある
  - 反例（使い捨てのリポジトリ、2026-11-20）: 1 つの deps の中身を変えて changed にしたステージで、ほかの deps と outs のパスを
    動かし、出力を消した。lock を書き換えないと、ステージは元の理由に加えて、動かした deps の `modified`、`changed command`、
    `changed outs` を出し、下流も changed になった。動かした outs は lock に hash が無い扱いになり、`scripts/dvc-checkout.py` は
    新しいパスに出力を戻さなかった（`No file hash info found`。未実行に数えた）。lock の `path` と `cmd` を書き換えると（md5 は
    そのまま）、ステージは元の理由（中身を変えた deps の `modified`）だけを出し、出力は新しいパスに戻り、下流は changed で
    なくなった
  - 当たる範囲: 例の 1,416 のステージのうち 1,054 が、動かす前から changed である（上の「例の今の姿」）。この案では、次の
    作り直しまで、その大半でツールが働かない。書き換えないステージは、残高の理由に移動の分が混ざり、作り直す前の出力を
    新しいパスに戻せず（ADR-0258 の「changed の扱い」の、作り直す前の出力を読む作業ができない）、上流の outs が lock のとおりか
    の確認（ADR-0258 の「実行」）も通らない
- 案 M9（採用）: ハッシュで対応を取るツールで、動かす前のハッシュの出どころを 2 つ持つ。lock の md5（出力を作ったときの
  中身）と、動かす前のコミットの中身の md5（動かす直前の中身）である。lock の md5 で対応の付く項は案 M8 と同じに扱い、
  付かない項（動かす前から lock と違う項）は、動かす前のコミットの同じファイルを、パスが同じか、中身の md5 が同じことで
  見つける。どちらの場合も lock の md5 は書き換えないので、動かす前から changed のステージは、同じ理由で changed のまま残る
  （判断の軸の (b)）。対応はどれもハッシュの一致から出し、パスの組を人や git の改名の検出から受け取らない。ハッシュで
  決められないところが 2 つ残る（決定と理由の「outs の対応」と「cmd の確認」）

入力の中のパスを書き換えた移動（ディレクトリの深さを変えると、入力の TOML の相対パスを書き換えることになる）:

- 案 M4（採用）: 上のツールで、入力の中のパスだけを書き換えた変更も扱う。ツールは、動かす前後の TOML を値として読んで比べ、
  違うのが文字列の値だけで、その値をそれぞれの TOML の置き場から解いたパスが、同じファイル（同じハッシュ）を指すことを
  確かめる。確かめられたら、lock のその TOML の項を、新しいパスと新しい md5 に書き換える。どのキーがパスかを知る必要が無く、
  正規形の決まり（ADR-0254）を変えない。短所は 2 つある。書き換えた項の lock の md5 は、出力を作った入力の正規形のものでなく
  なり、値がパスの置き換えを除いて同じことをツールが確かめた、という根拠に替わる（ADR-0254 の移行は、lock が記録した版の
  正規形の md5 に替えたので、出力を作った入力を指したままだった。それより弱い）。また、その TOML を `inputs` に持つ比較の
  JSON は、前の正規形の md5 を書いているので、lock と合わなくなる（案 M6 で扱う）
- 案 M5: 値の正規形（toml-values）で、ほかのファイルを指す値を、パスの文字列でなく指す先のファイルの md5 にする。相対パスを
  書き換えた入力の正規形が前と同じ md5 になり、lock の md5 が出力を作った入力のもののまま残る。採らない
  - どのキーがパスかを、正規形のスクリプトが知る必要がある（入力の形は Rust の読み手が持ち、Python の側にコピーを持つことになる）
  - 指す先には、git で追跡しない上流の出力（ライブラリ）と、核データのディレクトリがある。正規形を書く pre-commit の hook は、
    出力を戻していない worktree でもコミットのたびに走るので、指す先の md5 を取れない場合がある
  - ADR-0254 の「正規形は参照をたどらない」を変え、今の TOML の正規形 436 の md5 がすべて変わるので、例の lock の deps の
    書き換えが要る。そのとき、今ある比較の JSON の `inputs` の md5 は、どれも lock と合わなくなる
  - 指す先はステージの deps にも並んでいるので、指す先の中身の変化は、今も deps が拾っている。正規形に md5 を入れても、
    拾える変化は増えない
  - この案だけの長所（lock の md5 が出力を作った入力のもののまま残る）は、案 M4 の 1 つ目の短所の裏返しである。その短所を、
    ユーザーは懸念と見なかった（決定と理由）

`inputs`（入力のパスと md5）を持つ JSON を出力にするステージ（比較のツール）:

- 案 M6（採用）: 動かした入力か、案 M4 で中のパスを書き換えた入力が `inputs` にあれば lock を書き換えず、changed に残して
  再実行する。比較は数秒で、付け直しのコマンド（ADR-0258）に名前で指定できる。対象は、出力の JSON を読んで `inputs` のパスを、
  動かしたファイルと書き換えた TOML のパスに照らすので、機械で決まる。書き換えると、lock は最新を示すのに、出力の中のパスと
  （案 M4 で書き換えた TOML では）md5 が lock と合わず、記録の出どころを出すツールが止まる
- 案 M7: 比較のステージも書き換え、記録の出どころを出すツールの照合を、パスでなく md5 だけにする。パスは結果に関わらない
  （背景の 1 つ目の求め）に沿う。採らない。案 M4 で書き換えた TOML は md5 も変わるので、md5 だけの照合でも合わず、その比較は
  どのみち再実行が要る。出力の中には、動かす前のパスが残る

## 決定と理由

案 M9、案 M4、案 M6 にする。同じファイルかをパスでなく中身のハッシュで判定することは、ユーザーの決定である（背景の 2 つ目の
求め）。判定の方式（案 M9 と下の各項）は、担当が DVC の挙動と例の今の姿を確かめて詰めたもので、親の案（案 M8）に反例が
あったので広げた。親のセッションが反例（案 M8 の項）を読み、広げた形を採ると決めた（2026-11-20）。実装がまだ無いので、この ADR は proposed で置き、ツールのブランチで accepted にする（docs/adr/README.md の「運用」）。案 M4 の 1 つ目の短所（lock の md5 が、出力を作った
入力のものでなくなる）を親が伝えたとき、ユーザーは、入力の変更はハッシュで担保すれば足りるとして、懸念と見なかった
（ユーザー 2026-11-20）。案 M6 と、試行の扱いをここで決めないことは、親のセッションの決定である。

### 判定の原則

- ファイルやディレクトリを動かしただけでは再計算しない。パスは名札で、同じファイルかは中身の md5 で判定する。同じと判定した
  ファイルについて、`dvc.lock` の `path`、`params` のキー、`cmd` の中のパス、ステージの名前の中のパスを書き換える。md5、size、
  nfiles は書き換えない
- 書き換えはツールで行う。ツールは、動かした後の木と、動かす前のコミット（コミットの前に実行するときは HEAD）を読む。動かす
  前のコミットから読むのは、動かす直前の中身の md5、動かす前の `dvc.yaml` と `dvc.lock` の置き場、動かす前のステージの定義で
  ある。パスは、それぞれの `dvc.yaml` の置き場からリポジトリの直下のパスに直して扱う
- 判定はステージごとに行い、下の deps、params、outs、cmd のすべてが確かめられたステージだけを書き換える。1 つでも確かめられ
  なければ、そのステージは書き換えずに理由とともに一覧に出し、ツールは終了コード 1 で終わる。そのステージは changed になり、
  残高として扱う。決まりのとおりに書き換えない比較のステージ（下の「比較のステージ」）は、別の一覧に出し、終了コード 1 の
  理由に数えない
- 上流のステージから順に判定する（下流の deps の md5 に、上流の書き換えた lock を使うため）
- `dvc commit` は使わない

### ステージの対応

- 今の `dvc.yaml` のステージ（foreach を展開したもの）と lock の項は、同じ `dvc.lock`（`dvc.yaml` とともに動いたものを含む）の
  同じ名前で対応させる
- 名前で対応の付かないステージ（foreach の項目がパスで名前が変わった、別の `dvc.yaml` に移した）は、動かす前のコミットの lock の
  項のうち、下の deps、params、outs、cmd の確認がすべて通るものを対応させる。通る項が複数あるときは、どれを選んでも書き換えた
  後の lock が同じになるときだけ選び、違えば書き換えない
- lock の 1 つの項は、1 つのステージにだけ対応させる。同じ名前のステージが今の `dvc.yaml` に残る項と、既にほかのステージに
  対応させた項は、候補にしない（ステージを複製しただけでは、複製の側に lock の項を作らない。流していないステージを最新と
  示さないため）

### deps の対応

lock の deps の項と今の `dvc.yaml` の deps を、1 対 1 に対応させる。数が違えば書き換えない。項と今のファイルを同じファイルと
するのは、次のどれかである（上から順に当てる）。

1. lock の md5 が、今のファイルの md5 と同じ
2. 1 で対応の付かない項（動かす前から、中身が lock と違った項）で、リポジトリの直下からのパスが動かす前後で同じ（動かして
   いない）
3. 1 で対応の付かない項で、動かす前のコミットでのその項のパスの md5 が、今のファイルの md5 と同じ（動かす前から lock と違い、
   動かした）。git で追跡しないファイルでは、動かす前のコミットがそのパスに記録した md5（それを outs に持つステージの lock の
   項、`.dvc` のファイル）を使う

- 今のファイルの md5 は、作業ツリーにあればそのファイルから取る（ディレクトリの md5 を含め、DVC のライブラリで取る。計算を
  作り直さない）。作業ツリーに無い上流の出力（出力を戻していない worktree）は、それを outs に持つステージの、書き換えた後の
  lock の md5 を使う。上流のステージが書き換えられなかったときは、その出力を deps に持つ下流も書き換えない
- 同じ md5 の項が複数あるときは、どれに対応させてもよい（書き換えた後の lock が同じになる）。2 と 3 で同じ中身のファイルが
  複数あるときも、lock の md5 の集まりと、ステージが changed かは、対応のさせ方で変わらない
- ディレクトリの deps は、`.dir` の md5 で同じ規則を当てる。そのまま動かしたディレクトリは同じ md5 なので対応が付く。中の
  ファイルの名前や置き場を変えたディレクトリは md5 が変わり、対応が付かない。中のファイルまでは対応を取らない（ステージは
  ディレクトリを名指しし、中のファイルをどの名前で読むかはプログラムが決めるので、中の名前は名札でなく入力の一部である）
- `.dvc` で保管した生成物（ADR-0222）を動かすときは、追跡する `.dvc` のファイルを動かす。生成物の名前を変えるときは、`.dvc` の
  差が `path` の行だけであることを確かめる。生成物は、新しいパスにキャッシュから戻す

### params の対応

- lock の `params` は、ファイルごとにキーと値を持ち、ファイルのハッシュを持たない。lock の項と今の `dvc.yaml` の params の
  ファイルは、ステージが挙げたキーの値がすべて同じことで対応させる（deps の 1 に当たる）。付かない項は、パスが同じか（2）、
  動かす前のコミットのファイルと今のファイルで、挙げたキーの値が同じこと（3）で対応させる
- 対応の付いた項は、lock の `params` のキー（ファイルのパス）だけを書き換え、値は書き換えない（値を書き換えるのは、下の
  「入力の中のパスを書き換えた移動」だけである）

### outs の対応

- git で追跡しない outs は、出力を戻していない worktree には、動かす前のパスにも新しいパスにも無い。中身のハッシュでは対応を
  取れない（判断の軸の (d)）
- lock の outs の項と今の `dvc.yaml` の outs は、ステージの定義の中の並びの位置で対応させる。動かす前の並びは、動かす前の
  コミットの `dvc.yaml` を DVC のライブラリで展開して読む（lock の outs はパスの順なので、lock からは読めない）。数が違えば
  書き換えない。lock の md5 は、対応する新しいパスにそのまま持ち越す。出力は、新しいパスにキャッシュから lock の md5 で戻す
- 位置の対応は、確かめられる範囲で確かめる。cmd に現れる outs は、下の cmd の確認で確かめる。作業ツリーの新しいパスに出力が
  あれば、その md5 が持ち越す md5 と同じことを確かめ、違えば書き換えない
- 確かめられないまま残るのは、outs を 2 つ以上持ち、cmd に現れない outs を持つステージ（196）で、出力を戻していないときに、
  移動と同じ変更で outs の並びを入れ替えた場合である。lock は、入れ替わった md5 を最新として示す。動かす変更では、
  `dvc.yaml` の outs の並びを変えない

### cmd の確認

- lock の cmd（動かす前）と今の `dvc.yaml` の cmd を、shell の語に分けて比べる。語の数が同じで、語ごとに、パスでない語は同じ
  文字列、パスの語は同じファイルを指すことを確かめる。同じ文字列の相対パスも、`dvc.yaml` の置き場が変われば別の場所を
  指すので、パスの語として確かめる
- cmd が名指しするパスの多くは deps に無く（背景の「例の今の姿」）、ステージの deps のハッシュだけでは確かめられない。同じ
  ファイルを指すとするのは、次のどれかである
  - deps、params、outs の対応で組になったパス（同じ md5 の項は、どれと組でもよい）
  - deps の正規形の対応から決まる、元のファイル（`python-ast/<パス>.ast` と `<パス>`、`toml-values/<パス>.json` と `<パス>`、
    `binary-forms/<名前>.md5` と `bin/<名前>`。ADR-0210、ADR-0254、ADR-0255 の置き方）
  - git で追跡するファイルで、動かす前のコミットの中身の md5 と、今の中身の md5 が同じもの
  - 上のどれにも入らない、リポジトリの直下からのパスが動かす前後で同じもの（動かしていない）
- 語の一部がパスである形（`../..#references`、`--json=<パス>`、glob）の読み方は、実装のブランチでテストとともに詰める。
  読めない形の差は、確かめられないものとして扱う（書き換えない）

### 入力の中のパスを書き換えた移動

- 入力の TOML の中のパスを書き換えた移動も、同じツールで扱う（案 M4）。ツールは、動かす前後の TOML を値として読み、違うのが
  文字列の値だけで、その値をそれぞれの置き場から解いたパスが、同じファイルを指すことを確かめる。同じファイルとするのは、
  上の deps の規則で同じもの（TOML の中だけにあり、ステージの deps に無いファイルを含む）と、その TOML を読むステージの outs の
  対応で組になったパスである（例の TOML のうち 155 が、出力のパスを `output` の値に持つ。`git grep -c '^output = '`、
  main 28668154f、2026-11-20）
- 確かめられたら、lock のその TOML の項（例の lock の deps にある正規形の項と、直下の lock の toml-values のステージにある
  元の TOML と正規形の項）を、新しいパスと新しい md5 に書き換える。書き換えるのは、動かす前に lock の md5 が動かす前の
  ファイルと合っていた項だけで、合っていなかった項は lock の md5 を残す
- その TOML を params に持つステージ（989）では、lock に md5 でなく値が入るので、同じ確認が通った文字列の値を、新しい値に
  書き換える。動かす前に lock の値が動かす前のファイルと合っていたキーだけを書き換える（担当が足した項。案 M4 を params に
  当てたもの）
- 書き換えた項の lock の md5 と値は、出力を作った入力のものでなく、違いがパスの置き換えだけで指す先が同じファイルであることを
  ツールが確かめた入力のものになる

### 比較のステージ

- `inputs` を持つ JSON を出力にするステージ（比較のツール）は、動かした入力か、中のパスを書き換えた入力が `inputs` にあれば
  書き換えず、一覧に出して changed に残す（案 M6）。数秒なので、付け直しのコマンド（ADR-0258）に名前で指定して再実行する。
  付け直しのコマンドが入るまでは、その時点の決まりの経路（ADR-0184 の `-s` の例外）で再実行する
- ほかのステージの出力の中に入力のパスが入っていても、書き換える（パスは結果に関わらない。出力の中のパスは動かす前のまま残る）

### 試行を examples に移すとき

- 試行（`trials/`）の出力を examples に移してステージの出力にするときにも、再計算にしない仕組みが要る（ユーザー 2026-11-19）。
  試行は流したときの deps の md5 の記録を持たないので、上のツールは lock の項を作れない
- この ADR では決めない。ADR-0259（proposed）が、検討を始めからステージとして流し、答えが出たら凍結する案を書いている。
  その案が決まれば、新しい検討は始めから lock を持つ。既にある試行の扱いを含め、下のパスのツールの段で、ADR-0259 と合わせて
  決める

### ほかの決まりとの関係

- 正規形のパス（元のファイルのパスに沿う）と直下の `dvc.lock` も、同じ判定で書き換える
- これは、結果を変えない変更での lock の付け直しを ADR が決めた移行に限る決まり（ADR-0212 の決定と理由の (b) と、スキル
  compute の `dvc commit` の項）を、ツールが確かめた移動については、ADR を書かずに一般に許す形に変える
- examples の下の整理（ADR-0259）は、このツールを使う

### 移行

ツールは 1 本のブランチで入れる。ADR-0258 の移行の段 1〜5 に依らず、examples の下の整理より前に要るので、それらより先に着手する
（#0298）。ツールを TDD で作り、ADR-0212 の決定と理由の (b) と、スキル compute の `dvc commit` の項を、ツールが確かめた移動を
許す形に直す。試行を examples に移すときの扱いを ADR-0259 と合わせて決め、この ADR の決定に書き足す。重いステージの再実行は無い。

この ADR を書いたブランチ（docs/0258-settle-open-points）は決定だけを書き、スキル、CLAUDE.md、script、hook、`dvc.yaml`、
`dvc.lock`、ほかの ADR は変えない（ADR-0259 がこのブランチのコミットを引く 1 行の、rebase の後の hash の付け替えを除く）。

### 帰結

- ツールが確かめた移動では、ステージの `dvc status` は動かす前と同じになる。動かす前から changed のステージは、同じ理由で
  changed のまま残り、作り直す前の出力を新しいパスに戻せる
- 実装は決定に追いついていない。ツールは未着手で、#0298 にある。入るまでは、パスを動かしたステージは changed のまま残る
- 比較のステージは、入力を動かすたびに再実行が要る（数秒）。凍結したケースの比較のステージをどうするかは、ADR-0259 の側で
  決める
- 中のパスを書き換えた入力の lock の md5 と値は、出力を作った入力のものでなくなる（案 M4 の短所）。出力を作った入力は、
  ツールの書き換えのコミットの差分から辿る
- outs の並びを移動と同じ変更で入れ替えると、ツールが見つけられない場合がある（「outs の対応」）
- ツールは動かす前のコミットを読むので、移動をコミットした後に実行するときは、動かす前のコミットを指定する

### 確認

この ADR のブランチは決定だけで、確かめたのは、背景の「DVC の挙動」の使い捨てのリポジトリでの確認、`design-records check`、
run-checks.sh である。ツールのブランチで、次をテストで通してからマージする。

- 名前と置き場だけの移動で、lock の `path`、`params` のキー、`cmd`、ステージの名前だけが変わり、`dvc status` が移動の前と同じに
  なること（params のファイルを動かしたステージ、そのまま動かしたディレクトリの deps と outs、foreach の項目がパスのステージを
  含む）
- 動かす前から changed のステージが、同じ理由で changed のまま残り、出力が新しいパスに戻ること（案 M8 の反例の形。動かす前から
  lock と違うファイルを動かした場合を含む）
- 出力を戻していない作業ツリーで、上流の outs と、それを deps に持つ下流が書き換わること
- 内容の同じ deps を複数持つステージが書き換わること。中のファイルの名前を変えたディレクトリを deps に持つステージは、
  書き換えないこと
- `dvc.yaml` の置き場を変えた移動と、ステージを別の `dvc.yaml` に移した移動で、動かしていないファイルの項の相対パスが
  書き換わること
- cmd の差がパスの置き換えでないステージ、パスの置き換えのほかに値を変えた TOML を deps か params に持つステージ、作業ツリーの
  出力の md5 が持ち越す md5 と違うステージは、書き換えないこと
- 入力の TOML の相対パスを書き換えた移動で、その TOML と正規形の項が新しい md5 に、params の値が新しい値になり、比較の
  ステージを除いて `dvc status` が移動の前と同じになること
- 動かした入力を `inputs` に持つ比較のステージは、書き換えずに別の一覧に出て、それだけでは終了コードが 1 にならないこと
- ステージを複製しただけの変更で、複製の側に lock の項ができないこと
- 出力のパスを値に持つ TOML で、outs の置き場を変えた移動が書き換わること

## 補足

「例の今の姿」の数え方（main 28668154f と同じ `dvc.lock` を持つこの ADR のブランチの worktree、2026-11-20）: 追跡する 24 の
`dvc.lock` を YAML で読み、パスを lock の置き場からリポジトリの直下のパスに直した。

- 動かす前から changed: git で追跡するファイルの deps の項の md5 を、作業ツリーのファイルの md5 と比べた。ディレクトリの deps と
  追跡しない deps は比べていないので、1,054 は下限である
- cmd が名指しするパス: cmd を shell の語に分け、語を直下のパスに直して、deps、outs、params のパスと、正規形の置き方から決まる
  元のファイルのパスに照らした。語の一部がパスである形は、`#` の前がリポジトリの直下を指すものだけを数えた
- ディレクトリの deps と outs: md5 が `.dir` で終わる項
