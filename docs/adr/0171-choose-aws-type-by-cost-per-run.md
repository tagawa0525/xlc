# ADR-0171: Start each job on the cheapest (type, AZ) by spot price divided by speed

## 背景

自己完結な実行（ADR-0155）は機種を `--type`（既定 c7a.4xlarge）で固定し、AZ は無指定なら AWS が選ぶ。2026-10-13〜14 の本番 m3 では
c7a.4xlarge のスポットが 20 分〜1 時間ごとに中断され、配置スコアは全 AZ で 1〜3 だった。スポット価格は機種と AZ でちがい、
c8a や 8xlarge のほうが 1 本あたりの費用が安いことがある（2026-10-14 の価格の履歴で、c8a.4xlarge の us-east-1f は c7a.4xlarge の最安より約 26% 安い）。

- 1 本の費用（円ではなく $）を最小にする。結果の物理は機種に依らない（同じ OpenMC、同じ入力）
- OpenMC は 1.4 GB しか使わないので（2026-10-14 の測定で 5B-2D 1.35 GB、3A 1.18 GB。docs/environment.md）、メモリの条件は要らない
- 空きとクォータは起動してみないと分からない。監視のスクリプトが次の回で再試行できること

## 検討した案

- **A. 固定の機種**（今まで）: 単純。短所は、安い機種と AZ に移れないこと。中断が続いても機種を人が選び直す
- **B. 価格だけで並べる**: 8xlarge は 4xlarge の約 2 倍の価格で約 2 倍の速さ（見積もり）なので、価格だけで並べると常に小さい機種になり、
  速い機種の 1 本あたりの費用を比べられない
- **C. 配置スコアで並べる**（`GetSpotPlacementScores`）: 空きやすさの目安だが、費用を含まず、スコアの取得に別の権限と問い合わせが要る。
  本番 m3 ではスコアが全 AZ で 1〜3 で、区別の根拠にならなかった。採らない
- **D. EC2 Fleet / Spot Fleet の price-capacity-optimized**: AWS が価格と空きで選ぶ。起動の仕組み（フリート、タグ、`run-instances` の
  引数、起動の記録、one-time の扱い）を変え、選んだ理由を記録に残しにくい。速度の違い（機種ごとの重み）は重みで表せるが、
  こちらの費用の定義（価格 ÷ 速度）と順位を記録するほうが、失敗の扱いも含めて追える。採らない
- **E. 価格 ÷ 速度で並べ、順に `run-instances` を試す**（採る）

## 決定と理由

E を採る。`aws_run.sh --type auto`（新しい実行と起動し直しの両方）は次のとおり:

1. 候補の機種と速度は `examples/vera/aws_types.toml` の `[speed]` に持つ。速度は c7a.4xlarge を 1 とした 1 本あたりの走る速さの
   見積もりで、**測っていない**（c8a.4xlarge 1.2、c8a.8xlarge 2.4、c7a.8xlarge 2.0、c7a.4xlarge 1.0）。測ったら更新する
2. 各候補の機種の直近 1 時間のスポット価格を AZ ごとに引き（`aws_spot_prices.sh` と同じく AZ ごとの最新）、1 本の費用 = 価格 ÷ 速度の
   昇順に (機種, AZ) を並べる。同じ費用は機種名、AZ の順
3. 順に `run-instances` を試す。`InsufficientInstanceCapacity`（空き）、`MaxSpotInstanceCountExceeded` と `VcpuLimitExceeded`（クォータ。
   8xlarge は 64 vCPU のクォータで同時 2 台）、`SpotMaxPriceTooLow`（価格）で失敗したら次の候補へ。それ以外の失敗は止まる（推測しない）
4. どれも失敗したらジョブごとに「空きがない」と出し、ほかのジョブを続けたうえで終了コード 1 にする。S3 の launch.env は置いてあるので、
   監視のスクリプトは次の回に入力を省いた形（起動し直し）で再試行できる
5. `--az` と `--type <機種>` の明示は今までどおり優先する。`--type auto --az X` は AZ を固定して機種だけ選ぶ。`--type auto` では起動し直しが
   記録の AZ を引き継がない（前に選んだ AZ に固定すると、選び直せない）
6. `--on-demand` とは併用できない（オンデマンド価格は機種ごとの比が一定でなく、この並べ方の前提がスポット価格だから）
7. `launches/` の記録に、選んだ機種（TYPE）と AZ に加えて、`SELECTION=auto`、`SELECTION_RANK`（順位/候補数）、`SPOT_PRICE`、`SPEED`、
   `COST_PER_SPEED` を残す
8. `--dry-run` は候補の表（費用順）と、ジョブごとの最初の候補の起動の引数の検証を出す

物理コア数が機種で違っても、`run_remote.sh` のスレッド数は `lscpu` の物理コア数から決まるので変更は要らない。

## 確認

- `aws_run.sh --dry-run --type auto`（実機の起動はしていない。2026-10-14）: 20 個の候補の表が費用順に出て、最初の候補（c8a.4xlarge
  us-east-1f）の引数が有効。`--az us-east-1b` の併用は 4 個に絞られ、`--on-demand` の併用は 2 で止まる
- `run-instances` が空きの失敗を返す偽の `aws` で、次の候補へ進み（3 番目で成功）、記録に順位と価格が残ること、全部失敗でジョブごとに
  「空きがない」と出ること、ほかの失敗では止まることを手元で確かめた（このリポジトリに AWS を呼ぶツールのテストはない）
- 速度の見積もりが実際の速さと合うかは、測っていない

## 帰結

- 速度が実際とずれると、費用の順位がずれる（最悪でも、割高な機種で流すだけで、結果の物理は変わらない）。測ったら `aws_types.toml` を更新する
- 空きの失敗のたびに `run-instances` を呼ぶので、候補が多いと起動までに数十秒かかりうる
- 失敗の分類が AWS のエラーコードの文字列に依る。新しいコードが出たら止まるので、追加する
