# ADR-0157: ループの先頭を 64 バイトに揃えてビルドする

## 背景

ADR-0144 は、リファクタリングと簡易なチューニングのブランチで、分岐点と変更後の時間を比べ、遅くなっていないことを
示すとしている。#0105 で、無関係な 1 行（`num_cpus::get_physical()` の呼び出し）を足しただけで、M0 の xs が出力を
バイト単位で変えずに 55 秒から 73 秒に遅くなった。遅くなったのは `ReichMooreXs::cross_sections` で、命令列は同一で、
関数の開始アドレスだけが違った（速い版は 64 で割って 16 か 48 余り、遅い版は 0 余り）。この大きさの置き場所のゆらぎが
あると、ADR-0144 の時間の判定が、変更の中身でなく配置で決まる。

関数とループの置き場所は、LLVM の既定では 16 バイトの整列で、そこから先はリンクの順で決まる。整列を 64 バイト（命令キャッシュの
行の大きさ）に揃えれば、置き場所の違いがなくなると考えた。

## 検討した案

M0 の xs（examples/m0/xs.toml）を、3 つのコミット（main の b873a967、速い配置の ebe7c100、遅い配置の d39c5db3。後の 2 つは
ブランチ perf/0088-line-shape-table（#0088）のコミットで、タグ `record/adr-0157-fast-placement` と `record/adr-0157-slow-placement` で残す）のソースから、
整列の設定ごとに release でビルドし、r995 の Slurm の排他のジョブ 277（2026-10-13）で 2 回ずつ実行した。設定は各ソースの
`.cargo/config.toml` の `rustflags`（`target-cpu=znver5`）に `cargo build --config` で足した。ビルドと測定の手順は
examples/build-alignment/ の `build.sh`、`measure-xs.sh`、`measure-lattice-core.sh`、`measure-2A.sh` で、ジョブ 277 と 287 は
同じ内容の手元のスクリプトで実行したあとにコミットした（`build.sh` で作り直した b873a967 の 4 つの `xs` は、277 のものと
バイト単位で同じ）。24 本のライブラリはすべて `cmp` でバイト単位で一致した（md5 `1943d0c43e0a5023686b829cc4029967`）。

| 設定                                                                                      | b873a967（秒） | ebe7c100（秒） | d39c5db3（秒） | xs の大きさ |
| ----------------------------------------------------------------------------------------- | -------------- | -------------- | -------------- | ----------- |
| なし（今まで）                                                                            | 55.03〜55.39   | 53.86〜54.02   | 73.01〜73.03   | 3.49 MB     |
| `-align-all-functions=6`（関数を 64 バイト）                                              | 55.45〜55.52   | 55.56〜55.66   | 55.46〜55.48   | 3.57 MB     |
| 関数と、前から落ちてこないブロックを 64 バイト（`-align-all-nofallthru-blocks=6` を足す） | 53.75〜53.80   | 53.87〜53.92   | 53.68〜53.86   | 4.22 MB     |
| `-align-loops=64`（ループの先頭を 64 バイト）                                             | 53.87〜54.29   | 53.90〜53.91   | 53.93〜53.99   | 3.61 MB     |

（大きさは b873a967 の `xs`。設定は `-C llvm-args=…` で渡す）

- 案 1: 何もしない。置き場所で 30% 変わり、ADR-0144 の判定が揺れる
- 案 2: 関数を 64 バイトに揃える。3 つのコミットの差は消えたが、どれも 55.5 秒前後で、速い配置（53.9 秒）より遅い
- 案 3: 関数と、前から落ちてこないブロック（分岐の先）を 64 バイトに揃える。差は消え、どれも速い配置と同じだが、
  実行ファイルが 21% 大きくなる
- 案 4: ループの先頭を 64 バイトに揃える。差は消え、どれも速い配置と同じで、実行ファイルは 3.5% 大きくなるだけ。
  ループを持つ関数の開始アドレスも 64 バイトに揃った（上の 3 つの版の `cross_sections` は、どれも 64 で割り切れる）

lattice と core（b873a967 のソース）は、同じ 4 つの設定で、M0 のピンセルと炉心、VERA 1B のピンセル、2A の集合体
（examples/build-alignment/ の `pincell-1B.toml` と `assembly-2A.toml`。examples/vera/p1/pincell-1B.toml と
examples/vera/p2/assembly-2A.toml に、少数群定数の全桁の出力 `few-group` を足したもの）を 2 回ずつ実行した（排他のジョブ 287）。少数群定数、2A のピン出力、標準出力は、どの設定でもバイト単位で一致した
（ジョブ 285 でも一致）。時間（秒）:

| 設定 | 2A             | 1B         | M0 の炉心  |
| ---- | -------------- | ---------- | ---------- |
| なし | 123.60〜124.20 | 4.81〜4.83 | 8.95〜8.96 |
| 案 2 | 122.84〜122.96 | 4.79〜4.80 | 8.76〜8.86 |
| 案 3 | 121.83〜124.04 | 4.73〜4.84 | 8.79〜9.11 |
| 案 4 | 122.77〜124.09 | 4.75〜4.75 | 8.74〜8.77 |

287 では、どの設定も今までと 2% の中だった。ただし 2A は、排他のジョブでも 1 回ごとの時間が大きくばらつく。最初の測定
（ジョブ 284、なしと案 4 を 2 回ずつ）では、なし 121.5〜129.6 秒、案 4 145.6〜158.9 秒だった。そこで、なしと案 4 を交互に
4 回ずつ実行した（ジョブ 292、`measure-2A.sh`）:

| 設定 | 2A の 4 回（秒）               |
| ---- | ------------------------------ |
| なし | 127.58、129.72、129.83、142.48 |
| 案 4 | 139.84、131.26、123.67、143.00 |

出力は 8 回ともバイト単位で一致した。同じ実行ファイルで 124〜143 秒（15%）ばらつき、その幅の中で、なしと案 4 の差は
見分けられない。284 の案 4 の 2 回はその幅より遅いが、287 と 292 では再現しなかった。ばらつきと 284 の原因は確かめて
いない（285 は手元の計算と重なったので、時間は使わない）。

## 決定と理由

案 4 を採る。ワークスペースの `.cargo/config.toml` の `rustflags` に `-C llvm-args=-align-loops=64` を足す（ADR-0109 と同じ
ターゲット別の項目）。

置き場所による xs の 30% の差が消え、M0 の xs は今までの速い配置の速さ（約 54 秒）にそろう。lattice と core は、測った
入力で、1 回ごとのばらつき（2A で 15%）を超えて遅くなっていない。測った出力は、xs、lattice、core のどれもバイト単位で
変わらない。案 3 も同じ効果だが、実行ファイルが 21% 大きくなる。案 2 は
差は消えるが、遅い側にそろう。

### 帰結

- ADR-0144 の時間の判定で、ループの置き場所によるゆらぎが減る。ループの外の置き場所（関数の中の分岐の先など）による
  ゆらぎは残りうる。見つかったら、新しい issue にする
- VERA 2A の格子計算は、排他のジョブでも 1 回ごとに 15% ばらつく（上の 292）。ADR-0144 の判定で 2A の時間を比べるときは、
  この幅を超えるかで見る
- `-align-loops` はループの先頭の前に NOP を足すだけで、演算の命令とその順は変えない。出力をバイト単位で確かめたのは、
  上の M0 の xs、lattice、core と、VERA 1B、2A だけである
- `.cargo/config.toml` は DVC のステージの deps なので、`dvc status` はすべての Rust の段階を deps が変わったものとして示す。
  走らせ直しはせず、ほかの変更で段階を実行するときに合わせて `dvc.lock` が更新される
- Zen 5 でない CPU で 64 バイトが最適かは測っていない（ADR-0109 のとおり、別のマシンでは `target-cpu` も変える）

### 確認

上の「検討した案」の測定（ジョブ 277、287、292、2026-10-13）。分岐点 b873a967 のソースにこの設定を足したビルドで、M0 の xs、
lattice、core と VERA 1B、2A の出力が、設定なしとバイト単位で一致した。
