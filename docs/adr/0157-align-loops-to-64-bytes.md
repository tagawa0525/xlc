# ADR-0157: ループの先頭を 64 バイトに揃えてビルドする

## 背景

ADR-0144 は、リファクタリングと簡易なチューニングのブランチで、分岐点と変更後の時間を比べ、遅くなっていないことを
示すとしている。#0105 で、無関係な 1 行（`num_cpus::get_physical()` の呼び出し）を足しただけで、M0 の xs が出力を
バイト単位で変えずに 55 秒から 73 秒に遅くなった。遅くなったのは `ReichMooreXs::cross_sections` で、命令列は同一で、
関数の開始アドレスだけが違った（速い 2 つの版は 64 で割って 16 余り、遅い版は 0 余り）。この大きさの置き場所のゆらぎが
あると、ADR-0144 の時間の判定が、変更の中身でなく配置で決まる。

関数とループの置き場所は、LLVM の既定では 16 バイトの整列で、そこから先はリンクの順で決まる。整列を 64 バイト（命令キャッシュの
行の大きさ）に揃えれば、置き場所の違いがなくなると考えた。

## 検討した案

3 つのコミット（main の 6b39ad13、速い配置の ab7c70b3、遅い配置の b501c22e）のソースを、整列の設定ごとに release で
ビルドし、M0 の xs と、lattice と core（M0 のピンセルと炉心、VERA 1B、2A）を Slurm の排他のジョブで走らせた。手順と
数値は examples/build-alignment/verification.md にある。どの設定でも、測った出力はすべてバイト単位で一致した。

- 案 1: 何もしない。M0 の xs は、b501c22e だけが 78〜81 秒で、ほかの 2 つ（54〜59 秒）より 40% 遅い。ADR-0144 の判定が
  置き場所で揺れる
- 案 2: 関数を 64 バイトに揃える（`-align-all-functions=6`）。3 つのコミットの差は消えたが、どれも 56〜58 秒で、案 4 より遅い
- 案 3: 関数と、前から落ちてこないブロック（分岐の先）を 64 バイトに揃える（案 2 に `-align-all-nofallthru-blocks=6` を
  足す）。差は消えたが、実行ファイルが 21% 大きくなる
- 案 4: ループの先頭を 64 バイトに揃える（`-align-loops=64`）。差は消え、どのコミットも 54.1〜54.9 秒で、実行ファイルは
  3.5% 大きくなるだけ。ループを持つ関数の開始アドレスも 64 バイトに揃った（3 つの版の `cross_sections` は、どれも 64 で
  割り切れる）

lattice と core では、VERA 2A の時間が、同じ実行ファイルでも 1 回ごとに 122〜168 秒ばらつき（#0112）、その中で案 1 と案 4
の差は見分けられなかった（交互に 6 回ずつで、平均 149.6 秒と 142.9 秒）。1B と M0 の炉心では、2 回の速い方どうしで比べて、
どの設定も案 1 と 3% の中だった（1B の案 4 の 1 回は 6.08 秒と遅く、ほかの回は 4.75 秒。ばらつきは #0112 と同じく
確かめていない）。

## 決定と理由

案 4 を採る。ワークスペースの `.cargo/config.toml` の `rustflags` に `-C llvm-args=-align-loops=64` を足す（ADR-0109 と同じ
ターゲット別の項目）。

M0 の xs で、置き場所による 40% の差が消え、どのコミットも今までの速い配置の速さ（約 54 秒）にそろう。案 3 も差は消えるが、
実行ファイルが 21% 大きくなる。案 2 は差は消えるが、案 4 より遅い。lattice と core では、2A のばらつきの中で遅くなったことは
見えず、1B と M0 の炉心では速い方どうしで 3% の中だった。

### 帰結

- ADR-0144 の時間の判定で、ループの置き場所によるゆらぎが減る。ループの外の置き場所（関数の中の分岐の先など）による
  ゆらぎは残りうる。見つかったら、新しい issue にする
- 2A の時間のばらつき（#0112）があるうちは、ADR-0144 の判定で 2A の 10〜20% の差は見分けられない
- `-align-loops` はループの先頭の前に NOP を足すだけで、演算の命令とその順は変えない。出力をバイト単位で確かめたのは、
  M0 の xs、lattice、core と、VERA 1B、2A だけである
- `.cargo/config.toml` は DVC の段階の deps なので、`dvc status` はすべての Rust の段階を deps が変わったものとして示す。
  この ADR では走らせ直さず、ほかの変更で段階を走らせるときに `dvc.lock` が更新される
- Zen 5 でない CPU で 64 バイトが最適かは測っていない（ADR-0109 のとおり、別のマシンでは `target-cpu` も変える）

### 確認

examples/build-alignment/verification.md の測定（c029a27c、ジョブ 302、305、307、2026-10-14）で、6b39ad13 のソースにこの設定を
足したビルドの M0 の xs、lattice、core と VERA 1B、2A の出力が、設定なしとバイト単位で一致し、M0 の xs の置き場所による
差が消えた。
