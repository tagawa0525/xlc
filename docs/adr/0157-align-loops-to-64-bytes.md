# ADR-0157: ループの先頭を 64 バイトに揃えてビルドする

## 背景

ADR-0144 は、リファクタリングと簡易なチューニングのブランチで、分岐点と変更後の時間を比べ、遅くなっていないことを
示すとしている。#0105 で、計算と関係のない変更（xs の依存の `num_cpus` と、`num_cpus::get_physical()` の呼び出し 1 行）を足しただけで、M0 の xs が出力を
バイト単位で変えずに 55 秒から 73 秒に遅くなった。遅くなったのは `ReichMooreXs::cross_sections` で、命令列は同一で、
関数の開始アドレスが違った（速い 2 つの版は 64 で割って 16 余り、遅い版は 0 余り。ほかの関数は確かめていない。開始アドレスの
余りだけで速さが決まるのでないことは、のちの測定で分かった。examples/build-alignment/verification.md）。この大きさの置き場所のゆらぎが
あると、ADR-0144 の時間の判定が、変更の中身でなく配置で決まる。

関数とループの置き場所は、LLVM の既定では 16 バイトの整列で、そこから先はリンクの順で決まる。整列を 64 バイト（命令キャッシュの
行の大きさ）に揃えれば、置き場所の違いがなくなると考えた。

## 検討した案

3 つのコミット（main の b873a967、速い配置の ebe7c100、遅い配置の d39c5db3）のソースを、整列の設定ごとに release で
ビルドし、M0 の xs と、lattice と core（M0 のピンセルと炉心、VERA 1B、2A）を Slurm の排他のジョブで実行した。手順と
数値は examples/build-alignment/verification.md にある。どの設定でも、測った出力はすべてバイト単位で一致した。

- 案 1: 何もしない。#0105 の前の devShell で作った d39c5db3 は、M0 の xs が 73 秒で、ほかの 2 つのコミット（54〜55 秒）より
  33% 遅かった（ジョブ 275）。今の devShell で作ると、遅くなるのは d39c5db3 でなく、案 2 の d39c5db3 になる（下）。どの
  コミットとビルドの環境で遅い置き場所に当たるかは読めず、ADR-0144 の判定が置き場所で揺れる
- 案 2: 関数を 64 バイトに揃える（`-align-all-functions=6`）。差は消えない。d39c5db3 は 73.7〜74.0 秒で、ほかの 2 つの
  コミット（55.9〜56.0 秒）より 32% 遅い
- 案 3: 関数と、前から落ちてこないブロック（分岐の先）を 64 バイトに揃える（案 2 に `-align-all-nofallthru-blocks=6` を
  足す）。3 つのコミットとも 53.9〜54.3 秒にそろったが、実行ファイルが 21% 大きくなる
- 案 4: ループの先頭を 64 バイトに揃える（`-align-loops=64`）。3 つのコミットとも 54.0〜54.4 秒にそろい、実行ファイルは
  3.5% 大きくなるだけ

（M0 の xs の時間は、案 2〜4 がジョブ 313 の 2 回ずつ。3 つの版の `cross_sections` の開始アドレスは、案 4 ではどれも 64 で
割り切れる。数値は examples/build-alignment/verification.md）

lattice と core では、VERA 2A の時間が、同じ実行ファイルでも 1 回ごとに 122〜180 秒ばらつき（#0112）、その中で案 1 と案 4
の差は見分けられなかった（交互に 6 回ずつで、中央値 130.7 秒と 126.8 秒）。1B と M0 の炉心では、2 回の速い方どうしで、
案 4 が案 1 より 1.3% と 3.4% 遅く、同じ実行ファイルの 2 回の差（1B で 0.58 秒、炉心で 0.65 秒）と区別できるかは確かめて
いない（M0 のピンセルは 0.1 秒に満たず、比べない）。

## 決定と理由

案 4 を採る。ワークスペースの `.cargo/config.toml` の `rustflags` に `-C llvm-args=-align-loops=64` を足す（ADR-0109 と同じ
ターゲット別の項目）。

M0 の xs で、置き場所による差が消え、どのコミットも今までの速い配置の速さ（約 54 秒）にそろう。案 3 も同じだが、
実行ファイルが 21% 大きくなる。案 2 は差が消えない。lattice と core では、2A のばらつきの中で遅くなったことは見えず、1B と
M0 の炉心では、速い方どうしで 4% の中で、ばらつきと区別できていない。

## 確認

examples/build-alignment/verification.md の測定（d3e3178f、ジョブ 313、317、319、2026-10-14）で、b873a967 のソースにこの設定を
足したビルドの M0 の xs、lattice、core と VERA 1B、2A の出力が、設定なしとバイト単位で一致し、M0 の xs の置き場所による
差が消えた。

## 帰結

- ADR-0144 の時間の判定で、ループの置き場所によるゆらぎが減る。ループの外の置き場所（関数の中の分岐の先など）による
  ゆらぎは残りうる。`-C llvm-args` はワークスペースのクレート（と依存のクレート）のコンパイルにだけ効き、コンパイル済みの
  標準ライブラリと glibc の libm のループは揃わない（揃えるには `-Zbuild-std` が要る）。見つかったら、新しい issue にする
- 2A の時間のばらつき（#0112）があるうちは、ADR-0144 の判定で 2A の 10〜20% の差は見分けられない
- 出力をバイト単位で確かめたのは、M0 の xs、lattice、core と、VERA 1B、2A だけである（命令列の比較はしていない）
- `.cargo/config.toml` は、ADR-0159 の `build` の段階（リポジトリの直下の `dvc.yaml`）の deps である。この設定は実行ファイルの
  バイトを変えるので、`build` を実行すると、出力は変わらなくても、すべての計算の段階が古くなって再実行する（ADR-0159 の帰結）。
  このブランチでは、コードだけを変えるブランチと同じく（ADR-0130、ADR-0159）`build` と計算の段階を再実行しない
- Zen 5 でない CPU で 64 バイトが最適かは測っていない（ADR-0109 のとおり、別のマシンでは `target-cpu` も変える）
