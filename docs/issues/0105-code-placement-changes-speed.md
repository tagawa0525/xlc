# 命令列が同じでも、関数の置き場所で時間が 30% 変わる

## 問題

ブランチ perf/0088-line-shape-table（#0088）で、J, K 積分の表を作るスレッドの数を物理コアの数にする 1 行
（`num_cpus::get_physical()` を呼ぶ）を足したところ、M0 の xs（examples/m0/xs.toml）は出力をバイト単位で変えずに
55.0〜55.6 秒から 72.8〜73.0 秒に遅くなった（d39c5db3、分岐点 b873a967、2026-10-13、r995 の Slurm の排他のジョブ 275。
それぞれ 2 回）。同じ比較を 1 つ前のコミット ebe7c100 で行ったときは、分岐点 54.79〜54.97 秒、変更後 53.68〜53.84 秒
だった（ジョブ 273）。表の構築は、どちらの版でも 0.03 秒である。

U-238 だけの入力（293.6 K、σ0 = 1e10）を手元で `perf record` で実行した時間の内訳（2026-10-13、load average 8〜12。
割合だけを見る）では、`ReichMooreXs::cross_sections` が ebe7c100 で 57.7%、d39c5db3 で 71.2% だった。

ADR-0157 の設定より前の `.cargo/config.toml` で ebe7c100 と d39c5db3 をビルドすると（タグ `record/adr-0157-fast-placement`
と `record/adr-0157-slow-placement`）、`ReichMooreXs::cross_sections` はどちらも大きさ `0x1430` で、`objdump -d` の命令列は
アドレスと即値のアドレスを除いて同一だった。違うのは開始アドレスで、ebe7c100 は `0x141250`、d39c5db3 は `0x141d00`、
分岐点 b873a967 は `0x1362d0` だった。遅い d39c5db3 だけが 64 バイトの境界に乗っている。関数の中のループや分岐の
置き場所が、Zen 5 の命令のフェッチや分岐予測に効いていることが候補だが、確かめていない。

ADR-0144 は、リファクタリングと簡易なチューニングのブランチで、分岐点と変更後の時間を比べて遅くなっていないことを
示すとしている。置き場所だけで 30% 変わるなら、無関係な 1 行の変更でこの判定が揺れる。

関係する ADR: ADR-0157

## 完了の条件

- 関数とループの整列を揃えるビルドの設定（`-C llvm-args=-align-all-functions=6`、`-align-all-nofallthru-blocks`、
  `-align-loops` など）で、上の 2 つの版の時間の差が縮むかを、ADR-0144 の判定（出力のビット一致と、排他のジョブでの時間）
  で測る
- 効けば、その設定を ADR で決めて入れる。効かなければ、その結果をここに書き、時間の比べ方（ADR-0144）で置き場所の
  ゆらぎをどう扱うかを決める

## 経緯

- 2026-10-13: perf/0088-line-shape-table の時間の比較で見つけた
- 2026-10-13: 整列の設定を比べ、ループの先頭を 64 バイトに揃える設定で差が消えた（ADR-0157）。ループの外の置き場所によるゆらぎは確かめておらず、見つかったら新しい issue にする
