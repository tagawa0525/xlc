# xs のコードの変更で、出力の変わらない核種のライブラリまで作り直す

## 問題

examples/depletion/dvc.yaml の核種ごとの段階（`xs-nuclide@<核種>`。ADR-0138）は `../../bin/xs` を deps に持つ（ADR-0159）。
`bin/xs` のバイトが変わると、変更が一部の核種の出力にしか効かなくても、65 核種のすべてを作り直す。1 本で約 2 時間
（2026-10-22 の Slurm 452 は 2 時間 5 分）。

feat/0133-fission-spectrum では、レビューの 1 周目の xs の修正（216ad6170。MT455 の読み方と LF=5 の積分）で 2 度目の作り直しを
投げ（Slurm 457、見積もり 2 時間 30 分）、2 周目の指摘は作り直しを避けるため #0149 に残した。ADR-0122 のとおり（コードを変えた
ら再実行する）だが、レビューの周ごとに 2 時間の費用がかかる。

手順の側の対処（コードのレビューを打ち切ってから、記録の数値を出す重い計算を 1 度だけ流す）はスキル topic-start に書いた。
この issue は、作り直す量を減らす構造の側を扱う。

関係する ADR: ADR-0138（核種ごとの段階）、ADR-0159（deps を実行ファイルにする）、ADR-0160（strip）、ADR-0122

## 案（決めていない。どれも確かめていない）

- 核種ごとの段階の deps を、実行ファイルでなく、その核種の処理に効く入力（核種の ENDF、温度、ADR-0138 の params の扱い）と、
  処理の版を表す値（xs の処理を変える変更で人が上げる番号）にする。出力を変える変更で版を上げ忘れると、古い出力が残る
  （ADR-0159 の案 B と同じ弱さ）
- 作り直しを 2 段にする: 代表の数核種（U-235、U-238、Pu-239 など、変更が効く核種）を先に作り、出力の md5 が全部変わらない
  ことを確かめた核種だけ `dvc commit` で取り込む。ADR-0143 と ADR-0159 が退けた `dvc commit` の形に当たるかを決める要がある
- 核種ごとの処理を速くする（#0045 と同じく、時間の内訳を測ってから）
- 何もしない（費用は手順の側の順序で抑える）

## 完了の条件

案を ADR で決めるか、手順の側の対処で足りると判断して wontfix で閉じる。
