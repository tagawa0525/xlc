# モジュール式のレイトレーシングを入れるか

## 問題

モジュール式のレイトレーシング（ピンや集合体の大きさの区画で巡回する角度と間隔を選び、区画の種類ごとのトラックの区間の
データを使い回して、区画の境で長いトラックにつなぐ方式）を xlc に入れると、メモリとキャッシュの効率が上がるかを
ユーザーと話した（2026-10-10）。xlc は格子の全体を 1 組の巡回するトラッキングで解き（ADR-0060。ピンセルは ADR-0043、
長方形の格子は ADR-0083）、方位角を tan φ = (H/n_y)/(W/n_x) = H·n_x/(W·n_y)（W と H は格子の幅と高さ、n_x と n_y は
下辺と側辺から出るトラックの本数）に補正する。トラックの間隔もこの整数の組から決まる（Δ = (W/n_x) sin φ）。トラック
ごとに区間の列（領域と長さ）を別々の Vec に保存している（crates/lattice/src/tracking.rs）。MOC のスイープ（crates/lattice/src/moc.rs の `Sweeper`）と、自己遮蔽のダンコフ係数と
固定源のスイープ（crates/lattice/src/moc/dancoff.rs、fixed_source.rs）は、同じトラッキングを使う。

関係する ADR: なし

### 先行例

- MPACT（MPACT 4.4 Theory Manual、ORNL/SPR-2023/3090、2023、5.4 節）: cyclic ray-tracing、direct neutron path
  linking、modular ray-tracing と呼ばれる同じ方式。条件は、区画に構造化した格子を重ねられることと、ある角度の
  トラックが区画の向かい合う辺で同じ整数の本数で交わること（ふつうは等間隔）。角度は既存の求積の方向を、条件を満たす
  近い有理数の方向に少し動かし、重みは変えない（粗い間隔では求積の誤差が無視できなくなりうる、と書いている）。
  利点として、3D の全炉心の PWR でトラッキングのデータの保存が O(10⁷) 倍、1/4 集合体の区画で O(10⁵) 倍減るとする。
  一方で「2D の MOC では、トラッキングのデータを一度作って保存するのが常」で、MPACT も 2D と 3D で区間のデータを
  保存している。スイープは方位角ごとに長いトラックをつないで両方向にスイープし、群を最も内側のループに置くと（Jacobi）、
  区画のつなぎ替えの手間がすべての群で一度で済む
- nTRACER（Lee, Jung, Joo, "Assembly Based Modular Ray Tracing for Rectangular and Hexagonal Lattices", KNS
  Autumn Meeting 2007）: ピンの区画のモジュール式（CMRT）は集合体の間のギャップのセルを表せないので、集合体の
  区画（AMRT）が実用には要る。角度と間隔は、ピッチ P について tan α = N_x / N_y、間隔 ΔR = P / √(N_x² + N_y²)
  （N_x、N_y は入力の角度と間隔から整数に丸める）で決まり、角度ごとの間隔は角度とともに決まる。KSNP 型 16 × 16 の
  集合体で、ギャップを均した CMRT は k∞ で 82 pcm、隅のピンの出力で約 6% の差を生んだ。トラックは、炉心の
  トラック、区画のトラック、セルのトラック、区間の階層に分けて保存する
- DeCART: メモリとプログラムの手間を減らすため、セルの種類ごとの区画（cell-based modular ray-tracing）を使い、
  隣の区画とトラックをつなぐ（nTRACER の文献での紹介。原典は読んでいない）
- OpenMOC: 2D では、xlc と同じく形状の全体で巡回する（global な）トラッキング。3D の MOC では、モジュール式が
  主流とされる（Shaner, "Theoretical Analysis of Track Generation in 3D Method of Characteristics", MIT、2017。
  検索の要約で確かめた範囲。本文は読んでいない）

### 測定（2026-10-10、dd5d9350、スレッド 16）

VERA 2B（examples/vera/assembly-2B.toml、方位角 30・間隔 0.03 cm（ADR-0111）、対称性なし）で、一時的なログで数えた
（コミットしていない）:

- トラッキング: トラック 27,420 本、区間 6,848,224（区間 1 つ 16 バイト（領域の番号と長さ）で約 110 MB）。Vec の容量の
  和は 9,535,992 区間で約 153 MB（`shrink_to_fit` をしていない）。トラック 1 本の構造体は 104 バイトで約 2.9 MB。
  セル 361、領域 28,928
- 最大メモリ（最大 RSS）: 自己遮蔽ありで 11.3 GB（1 状態 2 分 37 秒）、自己遮蔽なしで 9.0 GB。トラッキングのデータは
  容量で数えても約 1.4〜1.7%。残りの内訳は調べていない（候補: MOC の状態の配列、スレッドごとの方向の配列の pool
  （`Directional`）、断面積のライブラリ）
- perf stat（user の計数）:
  - 全体の計算: IPC 4.16（命令 4.39 × 10¹³、サイクル 1.05 × 10¹³）、cache-misses は cache-references の 4.6%
  - 自己遮蔽なし（MOC だけ）: IPC 2.25、cache-misses は cache-references の 11.7%。Zen 5（ADR-0109）では、この
    cache-misses は L2 の失敗に割り当てられ、多くは L3 で当たりうるので、DRAM の通信量には換算しない
  - 自己遮蔽なしで、L1 のデータキャッシュが埋まった元（`ls_any_fills_from_sys`、計数の多重化で 2/3 の時間の値から
    推定）: L1 の外から埋まった 5.7 × 10¹⁰ 回のうち、L2 から 50%、同じ CCX の L3 から 31%、DRAM から 19%。この測定では
    MOC の時間が 65.7 秒と、同じ設定の前の測定（44.0 秒）より長く、理由は確かめていない（ほかの計算は動いていなかった。
    計数の多重化の影響か）。そのため、時間で割った帯域は出さない。メモリの帯域で律速されているかは確かめていない

### 対称性との関係

成り立つ対称操作を使っても（ブランチ feat/0054-symmetry-operations、未マージ）、トラッキング（全トラックの区間）は全体を
持ち、スイープするのが代表のトラックだけになる。トラッキングのデータは減らない。そのブランチの測定（7a605978、2B、自動で
1/8）では、1 状態が 1 分 59 秒、最大 RSS が 5.9 GB（main の対称性なしの 2 分 37 秒、11.3 GB とは別の測定）

## 検討

- メモリ: 2D の格子の計算では、トラッキングのデータは最大 RSS の約 1.4〜1.7%（容量で）で、使い回しで減らせる量は
  小さい。MPACT が挙げる大きな節約は 3D の全炉心のもの。対称性を使っても、トラッキングのデータの量は変わらない
- キャッシュ: 区間はトラックごとに別の Vec にあり、トラックの中では順に（逆向きのスイープでは逆順に）読む。トラックの
  間では連続していない。キャッシュの失敗がどの配列から来るか（区間か、区間の領域の番号で引く領域ごとの線源や tally か）は
  確かめていない。モジュール式で小さくなるのは区間のデータだけで、領域ごとの配列の読み書きは変わらない
- スイープの量: スイープする区間の数は変わらない（長いトラックに沿って、どの区画の中もスイープする）
- 角度と間隔の制約: 今の xlc も、角度と間隔は格子の全体の整数の組 (n_x, n_y) から決まる。ピンの区画では同じ形の整数の
  組をピッチ P の区画で選ぶ（ΔR = P / √(N_x² + N_y²)）ので、違いは選べる細かさで、P/ΔR ≈ 42（ピッチ 1.26 cm、間隔
  0.03 cm）に対して、格子の全体では L/ΔR ≈ 717（約 21.5 cm）の程度。ピンの区画でも、(0, π/2) に 15 の角度、45° を
  含み（N_x = N_y）、間隔 0.03 cm に近い選び方はできる（たとえば N_x = N_y = 30 で ΔR ≈ 0.0297 cm）が、入力の角度からの
  補正は大きくなる。MPACT は補正した方向でも重みを変えないので、粗い間隔では求積の誤差が無視できなくなりうる、と
  書いている。ADR-0111 の方位角 30・間隔 0.03 cm の離散化の誤差がどう変わるかは測っていない
- ギャップ: VERA の集合体の周りの水のギャップ（0.04 cm）は、ピンの区画では表せない（nTRACER の CMRT の制約）。集合体の
  区画（AMRT）にすると、1 体の集合体の格子の計算では区画が格子の全体になり、今の xlc の巡回トラッキングと同じになる
- 自己遮蔽: 1 状態の時間（main の 2B、対称性なしで 2 分 37 秒）の大半は、等価なセルの衝突確率（cp::Cylinder::tracks と
  cp::interpolate）で、トラッキングのデータの持ち方に依らない
- 群のループ: MPACT が挙げる Jacobi のスイープ（群を最も内側にする）の効果は、モジュール式のつなぎ替えの手間を群で
  分け合うためのもの。xlc はつなぎ替えをしないので、この利点はない

結論: 今は入れない。1 体の集合体の 2D の格子の計算では、ギャップを表すには区画が格子の全体になり、今の巡回トラッキングと
同じになる。ピンの区画にしても、減るのはメモリの約 1.4〜1.7% のトラッキングのデータだけで、スイープする区間の数も、
自己遮蔽の衝突確率の時間も変わらず、ギャップを表せなくなり、方位角の補正が大きくなる。得るものが損より小さい。

## 完了の条件

- 次のどれかになったら測り直して決める（それまでこの issue は開いたままにする）:
  - 複数の集合体の 2D の MOC（炉心や、集合体の周りの反射体の大きな格子）や 3D の MOC を作るとき（区画の種類が格子の
    数より少なくなり、使い回しが効く）
  - トラッキングのデータが最大 RSS の 1 割を超える設定（細かい方位角や間隔）を使うとき
- そのとき測ること: トラッキングのデータと最大 RSS の比、キャッシュの失敗がどの配列から来るか（perf の mem か、
  配列ごとの計時）、DRAM から埋まる割合と帯域（AMD の DRAM の計数）、区画の角度の補正の大きさとその離散化の誤差
  （ADR-0111、#0047 との比較）

## 経緯

- 2026-10-10: ユーザーとの対称性の話の中で、ピンセルごとにトラックのパターンを使い回す方式として話題になった。
  対称性（スイープするトラックの本数と未知数を減らす）とは別の軸で、組み合わせられる
- 2026-10-10: 先行例と 2B の測定を調べ、今は入れないとした（上の「検討」）。事実の確認のレビューで 10 件の誤りを直した
  （cache-misses を DRAM の通信量に換算していた、対称性でトラッキングのデータが 1/8 になるとしていた、ピンの区画だと
  ADR-0111 の選び方が使えないと言い過ぎていた、補正の式を正方形の形で書いていた、ADR-0060 を参照していなかった、
  ブランチ名、1 分 59 秒の出どころ、Vec の容量、区間を順に読むという断定、メモリの内訳の断定）。結論は変わらないが、
  理由から「ADR-0111 の選び方が使えなくなる」を外し、補正が大きくなることに改めた。採らなかった案: ピンの区画のモジュール式
  （ギャップを表せない。nTRACER で隅のピンの出力が約 6% 違った）、集合体の区画のモジュール式（1 体の格子の計算では今の
  巡回トラッキングと同じ）。メモリの大半（9 GB）がトラッキング以外にあることは、#0039 の速さとメモリの課題として
  別に調べる
