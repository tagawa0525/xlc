# aws_run.sh の新しい実行で vCPU の上限を入力の数で割らない

## 問題

`--type auto` の新しい実行に入力を 8 本渡したとき、スポットの vCPU の表示が「クォータ 128、走行中 0、残り 128、このジョブの上限 128」になった
（2026-10-15 19:10、m4-assembly）。32 vCPU の c8a.8xlarge が 3 台起動して 128 を使い切り、残りの 3 本が `MaxSpotInstanceCountExceeded` で
起動できなかった。入力を省く起動し直しでは「このジョブの上限 16」と割られた。

ADR-0171 と aws_run.sh の説明の意図は、起動するジョブが複数なら残りをジョブの数で割ること。

関係する ADR: なし

## 原因

上限を割る条件が `((${#inputs[@]} || ${#jobs[@]} == 1 || ${#todo[@]} < 2)) || share=$((remaining / ${#todo[@]}))` で、入力があれば
（新しい実行は必ず）割らなかった。割る式は、欠けたジョブの数を見る起動し直しの経路だけを想定して書かれていた。新しい実行でも `todo` は入力の
数（8）で、割れば 16 になる。`${#jobs[@]} == 1` は `todo` が 2 本未満と同じなので要らない。

## 直し方

- 上限の計算を aws_common.sh の `vcpu_share <残り> <起動するジョブの数> <最小の機種の vCPU>` に出し、新しい実行も起動し直しも `${#todo[@]}` で割る
- examples/aws/test_aws_vcpu.sh（flake の check `aws-vcpu`）が、偽の aws で `spot_vcpu_remaining` と `vcpu_share` を確かめる
- 実機を起動しない `--dry-run` で、8 入力の上限が 16 になることを確認した（クォータ 128、走行中 0 を返す aws の shim。実際の走行中は m4-assembly の
  起動し直しで 128 を使っていたため、shim なしでは「残り 0」になる）

採らなかった案: 1 台起動するたびに走行中を引き直して残りを再計算する。上限は 1 本ごとの機種の絞り込みで、各ジョブは上限以下の機種しか使わない
ので、割った値の合計は初めの残りを超えない（最小の機種まで引き上げる場合を除く。そのとき入りきらないジョブは `VcpuLimitExceeded` で次の候補になる）。
引き直すと、先に起動した小さな機種の分だけ後のジョブの上限が増えるが、API の呼び出しが増え、起動中（pending）の反映の遅れで二重に数えるか数え漏れる
おそれがあるので、現状の固定の割り当てにした。

## 完了の条件

新しい実行でも、入力の数で割った上限で候補を絞る（テストと dry-run で確認済み）。
