# MOC のスイープで組の作業の配列を 0 にする時間

## 問題

- 2A の一般化随伴の源ごとのスイープ（#0279 の「段 3 の後の加速」の B のカウンタの項。Slurm 791）で、スレッドのサイクルの 22.7% が
  `memset`（IPC 0.095）にかかる。1 スイープあたり 9.26e9 サイクルで、スイープの内側のクロージャ（11.40e9）に近い。固有値計算と ESSM の
  スイープも同じ `Sweeper::sweep` を通る（同じ割合かは測っていない）
- 呼び出し元（`perf script` の戻り先の行。0.3 秒の区間の標本 91 個）: 44 個が `Sweeper::sweep` の中の `directional` の呼び出し
  （方位角が変わるたびに、組の通る領域 × 2 × 3 × 群の線源と減衰の和の 2 つの配列を `resize(size, 0.0)` で 0 にする）、47 個がスイープの
  クロージャの中のスライスの `fill`（`Tally::clear` の `[組の中の領域][モーメント][群]` の減衰の和が候補で、どの配列かは分けていない）
- 大きさ: 2A の組の通る領域の和は 125,253（DEBUG のログの `regions held by the tallies of the track groups`）で、1 領域の線源と
  減衰の和は 2 × 3 × 69 × 8 B = 3.3 KB ずつ、組の全体で 830 MB ほど。L3（64 MB）を超えるので、0 にした値をスイープがメモリから
  読み直す（`memset` のメモリからの埋めは 1 スイープ 5.2 百万）。組ごとの方位角の変わる回数は数えていない
- 案（どれも和の順を変えないので、結果はビットで同じ見込み）: 線源の配列は真空でない領域ですぐ上書きするので、真空の領域の分だけ
  0 にする。減衰の和は、`fold` が読んで足し込むときに 0 を書き戻す（読み終えた値をキャッシュにあるうちに 0 にし、別の走査を
  無くす）。見込みは、源ごとのスイープの `memset` の分（区間のサイクルの 2 割ほど）の大半で、#0279 の本番の見込みの一般化随伴の
  時間と、固有値計算の輸送にかかる

関係する ADR: なし

## 完了の条件

2A の固有値計算と一般化随伴の 1 スイープの時間を、`--timed` のジョブで直す前後に測り、k、一般化随伴の解、テーブルの md5 がビットで
同じことを確かめて直す。

## 経緯

- 2026-11-12: #0279 のまとめたスイープの遅さを perf のカウンタで測ったときに、源ごとのスイープの `memset` の大きさに気づいた
