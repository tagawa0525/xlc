# 減速計算の作業の配列の数え方の残り（#0212 のレビュー）

## 問題

issue #0212 の直し（ADR-0213 の「## 変更」、2026-11-03）は、1 回の減速計算の量から、`solve_cell` が手で挙げた格子点に比例する配列の確保を
除いて持つ区間の上限にする。fix/0212-lattice-depletion-memory の 1 周目の /code-review（2026-11-03、HEAD f965ef569）が挙げた次の点は、
落ちるテストか再現する手順が無いので直していない（間引かない格子の 2A の 1 ステップは MaxRSS 69.2 GiB で流れた。Slurm 652）。

- 数えていない配列: `Thermal` の今のスイープの累積の積率（`prefix`。リングごとに格子点（start から）あたり 48 B）、`finish` で前の
  スイープに移した積率と `flux.to_vec()` の中性子束の写し。自由ガスの範囲の広い入力では、数えた列と同じ桁になりうる（測っていない）
- 倍に伸びる確保: `Prefix.values` は空から伸び、`finish` のたびに伸ばし直す。自由ガスの σs の列は `collect::<Result<Vec<_>, _>>()` で
  伸びる。`lethargy_grid` の返す配列も足した点で伸びうる
- 数えすぎ: 自由ガスの枝の `energies` は `Thermal::new` の後に捨てるが数える。核種の格子の和、間引いた格子、`lethargy_grid` の
  `u` と `energies` は格子点を作った後は使わないが、関数の終わりまで残して数える（先に捨てれば、メモリも差し引きも減る）
- 形: 配列を足すたびに `solve_cell` の `work +=` に足す必要があり、漏れやすい。配列を持つ型（`Sweep`、`Thermal`、`Prefix`）が
  自分の確保を返す形にすると、数える場所と確保する場所が揃う。数え漏れを止める試験（小さな入力で held と work の和、または
  計数するアロケータ）が無い
- ログ: `UFG slowing down` の `work` は、`Scattering::Static` と `sweeps = 1`（差し引かない経路）でも出るので、コメントの「持つ区間の
  上限から除いた」が成り立たない
- 数えない段: `release` の後の移行の計数（`segment_groups`、`collapse`）と飛程の表は、どの量にも入らない。間引かない格子で測っていない

3 周目の後の記録のための周（2026-11-03、HEAD bfa85ec1c）が #0212 と ADR-0213 の記録に挙げた指摘のうち、ADR-0213 の決定と理由、帰結、
「## 変更」と #0212 の数値の誤りはマージの前に直した。残りは次の 1 つ。

- 持たないときの 12.4 GiB（Slurm 457、16 スレッド）から 26.8 GiB（Slurm 646、32 スレッド）への増え方は、ADR-0213 では説明できず、
  同じ間に入った ADR-0214（同時に解く数の倍）、ADR-0198（ピンをスレッドごとに 1 本）、ADR-0203〜ADR-0205、ADR-0207、ADR-0209（自由ガスの
  既定。`Thermal` の prefix、σs の列、energies のコピー）が候補で、確かめていない。列の倍の確保は 841375431（2026-10-07）からで、457 にも
  あったので候補でない。試行の入力は 4b17e939f で外したので、
  完了の条件の入力は f965ef569 から戻す（残すなら examples/depletion/ に `git mv`）

08d24a419 の記録のための周（2026-11-03）の指摘のうち、マージの後に文書のブランチで直すもの:

- #0212 の bin の違いの ADR の列挙が、出典に挙げた `git log --first-parent 559fdbed3..b29e4a539 -- crates/lattice/src/ufg* crates/lattice/src/shielding.rs`
  の出力と合わない（ADR-0214 は main.rs の変更でこのコマンドに出ない。出力の ADR-0194 の 457529c55、ADR-0208 の d90bcdf8f、ADR-0211 の
  1ed9b10a8、#0180 の S(α, β) の散乱源の並列化の 00d789a1f が列挙に無い）。上の増え方の候補にも 00d789a1f と ADR-0194 が無い
- GB と GiB の不揃い: ADR-0213 の決定の「MemAvailable 76 GB … 全体 59 GB」（`free -g` は GiB）と帰結の 59 GiB、確認の Slurm 580 の
  「MaxRSS 6.4 → 12.0 GB」（sacct の K を kB と読んだ値。帰結は 12,024,784K = 11.5 GiB）とほかの確認の MaxRSS
- #0212 の 647 の「自己遮蔽の始めから 39 秒」と 648 の「51 秒」の起点は、量を求めた時（`UFG held memory`）で、652 の 4 秒と書き方が揃って
  いない
- Slurm 457 の 12.4 GiB はジョブ全体（xs、1C も流した）の MaxRSS で、2A だけの上限。#0212 と上の増え方の比べ方にその注が無い

fe31114f4 のレビューの周（2026-11-03、medium。打ち切りの周で、指摘は直していない）の指摘:

- ADR-0213 の帰結の「`ufg-hold-memory` を与えたときは … 機械のメモリから量を引いた残りに収まる必要がある」: 実際は、OS とほかの
  プロセス、自己遮蔽の前からのこのプロセスの常駐の分 B も除いた残り（cgroup の memory.max があればその残り）で、既定の量（MemAvailable は
  B を除く）と基準が違う。同じ文の「0.8 も 2 GiB も掛けない」は、2 GiB は引く量なので「2 GiB を引かず 0.8 を掛けない」が正しい。凍結する
  部分の事実の誤りで、マージの後は「## 変更」で直す。帰結の `-c` のジョブとコンテナで `ufg-hold-memory` を勧める項も、数えない配列と B の
  余裕を書いていない
- 上の列挙の項は、コマンドの出力の 1f650c357（#0133。ufg.rs の `slowing_down_fine` と `solve_cell` の経路）を挙げていない（dc6de78e6 と
  55a2ce99a はコメントと語の変更）。増え方の候補にも ADR-0208（d90bcdf8f、間引いた格子の移行の計数）が無い
- Slurm 457 の項: #0212 の「問題」の箇条書きには「ジョブの全体」と書いてあり、足りないのは「原因」の前の比べ方（457 → 646）で 2A だけの
  上限と書いていない点

5b2ff6531 で上の最初の項の 2 文（余裕の基準と「2 GiB を引かず 0.8 を掛けない」）を直した。そのレビューの周（2026-11-03、medium。ブランチの
最後の周で、指摘は直していない）の指摘:

- 帰結の新しい文の「このプロセスの常駐の分」は、自己遮蔽の前からの常駐の分 B と限っていないので、量と数えない配列を 2 度引くとも読める。
  「## 変更」は量を求めた時の B を使うので、2 つの箇所の書き方が揃っていない
- 「（cgroup の上限があればその残り）」は何を引くかを書いていない。memory.high は越えても回収して遅くするだけで OOM にならず、収まる必要の
  ある上限は memory.max
- 既定の場合（MemAvailable は B、OS、ほかのプロセスを除く）と与えた場合（機械のメモリから引く）で、基準が違うことを書いていない
- 帰結の `-c` のジョブとコンテナで `ufg-hold-memory` を勧める項は、数えない配列と B の余裕をまだ書いていない（上の項と同じ）
- docs/adr/README.md の「確定後の運用」では、帰結と確認はマージの後も直せる（凍結しない）。上の項の「凍結する部分の事実の誤りで、
  マージの後は「## 変更」で直す」と 5b2ff6531 のコミットの本文の「帰結が凍結する前に」は、その規則と合わない
