# UFG の 1 ピンの時間が同じ系統の方式より 2 桁大きい理由

## 問題

xlc の自己遮蔽（ピンごとの UFG の減速計算。ADR-0068）は、同じ系統の方式（STREAM の PSM）より 1 ピンあたり 2 桁遅い。項目ごとの
時間と、今の UFG からの差を測って切り分け、直せる非効率を直し、近似になるものは入力で選べる項目にして差を測る（ユーザー
2026-11-13。CLAUDE.md の「方針」の 2 桁は設計の誤り。特定の燃料の種類に合わせ込まないよう、新しいウラン燃料だけでなく燃焼の
進んだ組成、Gd、可燃性毒物と制御棒のある格子、燃料の温度を変えた状態でも差を測る）。

入力と比べるツールは examples/depletion/issue-0286/（`inputs.py` がケースと変種ごとの入力を書き、`compare.py` が時間と既定からの
差の要約の JSON を書く）。下の値の出どころは、断らない限り `timing-825.json`（Slurm 825。パーティション timed の排他のジョブ、
2026-11-13、xlc 625af643c（実行ファイルは同じコードの 6c6bf98a8 でビルドした `target/release/lattice`）、分岐点は main の
6e6abb56d。ピンセルは 1 スレッド（`RAYON_NUM_THREADS=1`）、集合体は 32 スレッド。ログは DEBUG の計数を含む）。

### 1 ピンの時間の内訳と PSM との倍率

PSM は PSM-I の Table 2（60 GWd/t の UO2 のピン、燃料 5 リング、198 核種、0.3 eV〜30 keV の等レサジー 5 万点。計算機とスレッドの
数は書かれていない）。xlc は、2A の 40 MWd/kg の組成のピンセル（`pin-uo2-40`。燃料 5 リングで一様、76 核種、格子点 8.2 万。
1 スレッド）と、2A の 60 MWd/kg の 1 状態（`2A-60`。解くピン 39 本、116 核種、リングごとに組成が違う。32 スレッドの段の和を 39 で
割ったスレッド秒）:

| 減速計算の解と衝突確率（PSM solution）            |   0.011 |           6.84 |     24.52 |                620 |
| うち自由ガスの散乱源                              |         |           5.47 |     16.15 |                    |
| うち S(α, β) の散乱源                             |         |           0.62 |      1.14 |                    |
| うち静止した標的の窓の積分と線形方程式            |         |           0.66 |      1.90 |                    |
| うち衝突確率（表の外の格子点を格子点ごとに）      |         |           0.09 |      5.32 |                    |
| 衝突確率の表（P^iso table）                       |   0.003 |           0.41 |      3.25 |                140 |
| 格子と核種の断面積（Nuclide grouping）            |   0.104 |           0.74 |      2.74 |                  7 |
| 群定数への縮約（XS condensation）                 |   0.115 |   分けていない |           |                    |
| 計（PSM total。xlc は上の段の和）                 |   0.233 |           7.98 |     30.52 |                 34 |
| 移行の割合の区間（ADR-0207。表が空の 1 回目だけ） |      無 |           4.58 |      8.19 |                    |

- 倍率の大半は減速計算の解（620 倍）で、その 8 割が自由ガスの散乱源。静止した標的の部分だけ（0.66 + 0.09 + 0.41 秒）でも、PSM の
  解と表の 0.014 秒の 80 倍ほど
- 演算の数で説明できる分: 自由ガスの散乱源は、核の評価 2,980 万回 × 77 ns、作った区間の積分 4,980 万回 × 13 ns、持った区間の積分
  9,970 万回 × 20 ns と区間の境界で 5.13 秒（段の 5.47 秒の 94%）。回数は掃き直す格子点 × 核種ごとの区間 × リング × スイープで、
  1 ピンの区間 1,420 万の大半は散乱への寄与の小さい核種のもの（下の `share`）。静止した標的の部分は格子点 8.2 万 × リングと核種の組
  277（燃料 5 リング × 50 核種、被覆管 23、水 4）で 2,300 万回、1 回 29 ns。PSM は核種を質量でまとめ（Nuclide grouping）、点 5 万 ×
  5 リング × まとめた組で解く
- 演算の数で説明できない分（2A-60 が pin-uo2-40 の 3.8 倍）: (1) 32 スレッドで 1 回の演算が長い。核の評価 121 ns、作った区間の積分
  35 ns、持った区間の積分 45 ns（1 スレッドの 1.6〜2.7 倍。ピンセルとの比で、組成も違う）。同じ 2A-60 の 1 スレッドとの比は、
  積分が 2.2 倍（作った区間 13.4 → 29.9 ns、持った区間 19.9 → 43.3 ns。`share = 1e-4`）で大半は SMT、核の評価は 32 スレッドのほうが
  短い（189 → 156 ns。1 スレッドの値は表に入れる手間を含み、表の上限は同時に解くピンの数で変わる。分けていない）。下の「32 スレッドで
  1 回の演算が延びる理由」の節。
  (2) リングごとに組成が違うので、表の外の格子点（1 ピン平均 3.12 万、37%）を格子点ごとに求める（衝突確率 5.32 秒）。(3) 核種が
  116 と多い。(4) 39 本を 32 スレッドに配る残りと逐次の区間（自己遮蔽の span 62.9 秒 × 32 = 2,013 スレッド秒に対し、段の和 1,190 と
  移行 320 スレッド秒。#0180 の「32 スレッドの使い方」）

### 32 スレッドで 1 回の演算が延びる理由

2A-60 の 1 状態（既定と `share = 1e-4`）を、使う CPU を `taskset` で選んで流した。r995 は 16 コア 32 スレッドで、CPU 0〜15 が
16 コアに 1 つずつ（0〜7 と 8〜15 が L3 を分ける 2 つの CCX）、16〜31 がその 2 つ目のスレッド。設定は 1（CPU 0）、8（CPU 0〜7、
1 つの CCX）、16（CPU 0〜15、SMT なし）、16s（CPU 0〜7 と 16〜23、8 コアの両方のスレッド）、32（すべて）で、スレッドの数は
許された CPU の数（`RAYON_NUM_THREADS` なし）。Slurm 836（8、16、16s、32）と 838（1）で、どちらもパーティション timed の排他の
ジョブ、2026-11-13、xlc dafce36d2（main。実行ファイルは同じコードの `target/release/lattice`）、`perf stat`（数えるだけで標本は
取らない）の下で流した。少数群定数の md5 はどの設定も同じ（既定 4ed00d4b、`share = 1e-4` 6ef81d78）。ログは同じディレクトリの
`threads-<変種>-<設定>.log`（`.dvc`）、カウンタは `.perf`、要約は `python3 threads.py .`（直した前後は `python3 threads.py . 'ab*.log'`）。837 は別の担当の CPU 0 のビルドと
重なったので取り消し、838 で再測定した。

1 ピンの段の和（スレッド秒。移行の区間は下の直しの対象なので分けた）と、ほかの量（`perf stat` の利用者側の命令 ÷ サイクル、
カーネル側のサイクルの割合、サイクル ÷ task-clock）:

- SMT（同じコアの 2 スレッド）: 1 ピンは同じ 8 コアの 16s と 8 の比で 1.58（`share`）と 1.54（既定）、同じ 16 コアの 32 と 16 の比で 1.64 と
  1.69。スレッドの IPC は 3.7〜4.1 から 2.1〜2.4 に下がる。利用者側の命令の数は 1 から 32 スレッドで 1.17 → 1.33e13（`share`、+14%）、
  1.43 → 1.76e13（既定、+23%）と増え、増えた分の内訳は分けていない（候補は下の移行の区間の重複と rayon の待ち。確かめていない）。持った区間の積分は
  1 回 19.9 ns（1）、22.6 ns（16）、43.3 ns（32）。コアの演算の資源を 2 つのスレッドで分ける分で、32 スレッドの処理量は 16 の 1.07 倍
  （`share`。自己遮蔽 44.2 → 41.4 秒）と 1.04 倍（既定）しか増えない
- 動くコアの数による周波数: サイクル ÷ task-clock は 5.45 GHz（1）から 4.98（16）、4.77 GHz（32）に下がり、1 と 16 の比 1.09 は、1 ピンの
  比 1.15、1.18 の大半
- L2、L3 とメモリ: L1 の外れ（1.09〜1.51e11）、L2 から埋めた数（5.0〜6.8e10）、メモリから埋めた数（0.94〜1.44e9）は設定でほぼ同じで、
  メモリから埋めた量は 64 B × 1.3e9 を自己遮蔽の 41 秒で割って 2 GB/s ほど（帯域には遠い）。同じ CCX の L3 か L2 から埋めた数は 2.0e9（1）
  から 4.0e9（32）に増えるが、1 回 50〜100 サイクルとしても 32 スレッドのサイクル 6e12 の 2〜3%。1 と 16 の比のうち周波数の外の 5〜8% が、
  L3 の共有と、この CCX の間の行き来の上限
- カーネル側（ページフォルト、確保と解放、rayon の待ち）: カーネル側のサイクルは 1.5〜3.6%、ページフォルトはスレッドの数によらず
  1.0〜1.2e7（`share`）と 1.8〜1.9e7（既定）、コンテキストスイッチは 1.2e4（1）から 2.9e6（32。最大は 16 の 3.6e6（`share`）と 5.3e6（既定））。#0180 の Slurm 784 の 7 分 19 秒（利用者側
  4 時間 27 分の 2.7%）と同じ大きさで、1 回の演算の延びの説明にはならない。確保と解放（アロケータのロック。利用者側で待つ分はカーネル側に
  出ない）と false sharing は関数ごとに分けていない（確かめていない）
- 移行の区間（`UFG transfers counted`）だけはスレッドの数とともに 1 ピンの時間が延びた（`share` で 0.14 → 4.30 秒）。32 スレッドでは先の
  32 本が 4.7〜5.9 秒、残りの 7 本が 0.02 秒で、表（`ShareCellCache`）が空のまま同時に移行を数えるピンが、同じ列を 1 本ずつ作って
  いた（8 スレッドでは先の 8 本が 3.4 秒）。列を表に先に入れ、境界ごとに作る番を取り合う形に直した（9a426b1e1。ビットで同じ）

直した前後（Slurm 847 の 32 スレッドは前（dafce36d2）と後（9a426b1e1）を同じジョブで、850 は後の 16 と 32 スレッド。どちらも
パーティション timed の排他、2026-11-13。ログは `ab-<前後>-<変種>-32.log` と `ab2-<変種>-<スレッド>.log`（`.dvc`）。850 は CPU ごとの

  1 状態が 8〜9% 延びるので採らない見込み（メモリは同時に解くピンの数で分けるので減るが、今の 2A-60 は収まっている）

  カーネル側、上の命令の数の増え（分けていない）。結果をビットで変えずに直せるものは、移行の区間のほかに見つけていない

### 項目ごとの速くなる量と今の UFG からの差

差は既定（変種 `default`）からの値で、出どころは `diff-826-835.json`（Slurm 826 のピンセル、827 の集合体、833 の MOX のピンセル、835 の集合体の
`share = 1e-4`。ピンセルと 2A-60 の `share = 1e-4` は 834 の出力で、時間の欄は 834 の 1 スレッドの値。

  散乱で捕獲が変わる重い核種）は比べていない。ミクロ燃焼で追う核種（#0278 の 31 核種）の微視的断面積の差は測っていない
- 既にある項目の反応度の差は、分離共鳴を持つ核種の静止 −12.6〜−22.5 pcm、スイープ 2 回 −3.0〜−11.9 pcm、間引きの許容差 3e−4

  排他でないジョブのものしかなく、記録していない
