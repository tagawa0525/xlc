# 間引かない格子の 2A の燃焼で自己遮蔽が機械のメモリを使い切る

## 問題

examples/depletion/dvc.yaml の `lattice-2A`（`lattice-2A.toml`。1 ステップ、`ufg-tolerance` なし、`few-group` あり）を、main b29e4a539 の
dvc.lock の `bin/lattice`（md5 36667823）で流すと、最初の輸送の自己遮蔽（`shielding:dancoff` の close の後、約 100 秒）で、カーネルの
OOM killer が lattice のプロセスを止めた（Slurm 644、2026-10-31。sacct の State と ExitCode は `FAILED 255:0`。137 は dvc のログ
（/home/tagawa/github/slurm-logs/depletion-repro-644.out）の lattice のプロセスの終了コード）。

- `journalctl -k`（2026-10-31 20:15:04 JST）: `global_oom`、`Killed process 711567 (lattice) total-vm:94595084kB, anon-rss:88861200kB`。
  Slurm の制限ではない（r995 の `TaskPlugin = (null)`、`JobAcctGatherParams = (null)`。ReqMem 86,000M は要求の値で、超えても止めない。
  2026-11-03 に `scontrol show config` で確かめた）。r995 の MemTotal は 96,462,276 kB（92.0 GiB）
- Slurm 644 の MaxRSS 88,276,164K（84.2 GiB。sacct の K は KiB）
- 同じ入力の前の実行（Slurm 457、2026-10-23、ADR-0213 と ADR-0214 の前の bin、16 スレッド）の MaxRSS は 12,959,824K（12.4 GiB。ジョブの全体。
  `lattice-2A` を含む）

2A の一生の燃焼（examples/depletion/p2/lattice-2A.toml）と history/ の入力（Slurm 582、617、621、629、630、638 など。MaxRSS 20,300,752〜25,878,580K、
19.4〜24.7 GiB）は `ufg-tolerance = 1e-4` の間引いた格子で、この入力とは違う。この入力の前の実行からの bin の違い（dvc.lock の
`lattice-2A` の deps の bin は 7cf252f4、2026-10-22 の実行）には ADR-0213 と ADR-0214 が入り、増えたのはその違いによる（下の「原因」）。
依頼が挙げた 2 つの bin の間の違いによるのではない（bin の二分は流していない）:

- 間の bin（40662a570 の 22cf3181 と 2649911d4 の 36667823）の lattice の差は history.rs、residual.rs、main.rs の摂動の解の `h.micro`
  （分岐と履歴の経路）と format のテーブルで、自己遮蔽（shielding.rs、ufg/）と燃焼の経路に変更はない（`git diff 40662a570 2649911d4`）
- この入力は 2026-10-23 の後に流していない（dvc.lock の出力のログの時刻は 2026-10-22T17:46Z）。その間に ADR-0213（自由ガスの
  散乱源の区間を、使用可能メモリ − 2 GiB の 8 割まで持つ）と ADR-0214（スレッドの数の既定を論理 CPU の 32 に）が入った

### 原因

ADR-0213 の量は持つ区間だけを数え、減速計算の作業の配列は残りの 2 割と 2 GiB に収まる前提だった。間引かない格子の 2A の 1 ステップ
（32 スレッドで 39 本の解くピン）では、作業の配列と量の和が、プロセスが使えるメモリを超える。

試行の入力はコミット f965ef569 の trials/0212/ の下にある（646 は 2A-hold0.toml、647 は 2A-default.toml、652 は 2A-fixed2.toml、653 は
2A-thin-main.toml と 2A-thin-fixed.toml。648 は 2A-fixed2.toml と出力の名前だけが違う入力で、コミットしていない）。2A の試行は
examples/depletion/lattice-2A.toml（653 は examples/depletion/p2/lattice-2A.toml の燃焼度を 0.1 だけにしたもの）のライブラリと
chain を、試行の場所からの相対パスにしたもの。手元の 1 本のピン（pin-full-h0.toml、pin-full-h4.toml、pin-full-h0-reserve.toml）は
examples/depletion/issue-0181/pin-2A-1step-full.toml と同じく、ライブラリと chain を main の作業ツリーの絶対パスで引き、流したときの
md5 は examples/depletion/p2/depletion.msgpack e84310af（2A の試行の examples/depletion/depletion.msgpack d86514f8 とは別の
ライブラリ）、chain.msgpack 1f1de180。ログは `RUST_LOG=info,xlc_lattice::shielding=debug`（652、653 と手元は
`xlc_lattice::ufg=debug` も）。ジョブは decision の区分の排他の Slurm のジョブで、時間は記録に使わない。メモリは GiB（2^30 B）で書く
（sacct の K と /proc の kB は KiB）。

| ジョブ | bin              | 入力                  | 自己遮蔽の量（`UFG held memory`） | 結果                                                                                   |
| ------ | ---------------- | --------------------- | --------------------------------- | -------------------------------------------------------------------------------------- |
| 646    | main（36667823） | `ufg-hold-memory = 0` | 0                                 | 完了、MaxRSS 28,065,412K（26.8 GiB）、k は 1.183079 と 1.145585                        |
| 647    | main（36667823） | 既定                  | 67,098,918,912 B（62.5 GiB）      | 自己遮蔽の始めから 39 秒で VmRSS 64,244,956 kB（61.3 GiB）に増え続け、OOM の前に止めた |

量 62.5 GiB は、使用可能メモリ（（62.5 / 0.8）+ 2 ≈ 80.1 GiB）の 8 割から 2 GiB を除いた分で、残りの 17.6 GiB に、持たないときの
26.8 GiB（作業の配列と、自己遮蔽の前からの常駐の分。列が倍に伸びる分を含む）は収まらない。644 で OOM killer が止めたときの anon-rss は
84.7 GiB（88,861,200 kB）で、使用可能メモリを超えていた。

1 回の減速計算の作業の配列のうち、スイープの核種ごとの弾性散乱とリングごとの中性子束の列は、`vec![Vec::with_capacity(n); k]` で
作っていた。複製した Vec は確保を引き継がないので、列は空から倍に伸び、格子点の数の最大 2 倍を確保していた。

### 直し

ADR-0213 の「## 変更」（2026-11-03）: 1 回の減速計算の量（全体の量を同時に解きうる減速計算の数で分けたもの）に、その減速計算の作業の
配列（格子点の数に比例する配列。確保した大きさで数える）を含め、残りを持つ区間の上限にする（`ufg::cells_beside_work`）。スイープの
列は格子点の数で先に確保する（確保した大きさが最後の大きさになり、倍に伸ばす分が無くなる）。持つ区間の数は結果を変えない（ADR-0213 の
試験 `held_cells_give_the_sources_of_rebuilt_cells_bit_for_bit`）。数えていない配列と倍に伸びる確保の残りは #0215。

比べた案:

- 入力の側の対応（examples/depletion/lattice-2A.toml に `ufg-tolerance` か `ufg-hold-memory` を書く）: 採らない。既定は入力によらず
  機械のメモリに収まるべきで、入力で避けると、間引かない格子を同時に多く解くほかの入力（検証の高精度版、ピンの数の多い問題）で同じ
  ことが起きる
- 作業の配列を格子点の数とリングと核種の数の式で見積もる: 採らない。配列の確保した大きさを足せば、式を配列の変更に合わせ続けずに
  済む
- 列を作り直さず作業の配列を数えただけの版（57b583b17）: 手元の 1 本のピン（pin-full-h0.toml、格子点 1,266,014、核種 90）で、1 本の
  作業の配列を 122,442,896 B（0.11 GiB）と数えたが、列を先に確保した版では 1,094,741,648 B（1.02 GiB）で、列が倍に伸びる途中を数えて
  いなかった。この版の 2A の 1 ステップ（Slurm 648）は、自己遮蔽の始めから 51 秒で VmRSS 86,388,804 kB（82.4 GiB）に増え、止めた
  （最初の減速計算が終わる前なので、2A の作業の配列の値はログに無い）

直した版（ブランチ fix/0212-lattice-depletion-memory の 2bf0e9240、分岐点は main の b29e4a539、2026-11-03）で測った値:

## 完了の条件

- 間引かない格子の 2A の 1 ステップの、持った量と、持たないときの MaxRSS を測り、原因を確かめる（上の 646、647）
- 既定の量に減速計算の作業の配列（格子点の数に比例する列）を含め、間引かない格子の 2A の 1 ステップが流れる（上の 652）。数えていない
  配列の残りは #0215 で扱い、ほかの入力で機械のメモリに収まることは確かめていない
