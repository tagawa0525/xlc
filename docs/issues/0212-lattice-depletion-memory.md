# 間引かない格子の 2A の燃焼で自己遮蔽が機械のメモリを使い切る

## 問題

examples/depletion/dvc.yaml の `lattice-2A`（`lattice-2A.toml`。1 ステップ、`ufg-tolerance` なし、`few-group` あり）を、main b29e4a539 の
dvc.lock の `bin/lattice`（md5 36667823）で流すと、最初の輸送の自己遮蔽（`shielding:dancoff` の close の後、約 100 秒）で、カーネルの
OOM killer が lattice のプロセスを止めた（Slurm 644、2026-10-31。sacct の State と ExitCode は `FAILED 255:0`。137 は dvc のログ
（/home/tagawa/github/slurm-logs/depletion-repro-644.out）の lattice のプロセスの終了コード）。

- `journalctl -k`（2026-10-31 20:15:04 JST）: `global_oom`、`Killed process 711567 (lattice) total-vm:94595084kB, anon-rss:88861200kB`。
  Slurm の制限ではない（r995 の `TaskPlugin = (null)`、`JobAcctGatherParams = (null)`。ReqMem 86,000M は要求の値で、超えても止めない。
  2026-11-03 に `scontrol show config` で確かめた）。r995 のメモリは 91 GiB（`free -g`）
- Slurm 644 の MaxRSS 88,276,164K
- 同じ入力の前の実行（Slurm 457、2026-10-23、ADR-0213 と ADR-0214 の前の bin、16 スレッド）の MaxRSS は 12,959,824K（ジョブの全体。
  `lattice-2A` を含む）

2A の一生の燃焼（examples/depletion/p2/lattice-2A.toml）と history/ の入力（Slurm 582、617、621、629、630、638 など。MaxRSS 20〜26 GB）は
`ufg-tolerance = 1e-4` の間引いた格子で、この入力とは違う。88 GB に増えたのは bin の版の違いではない（bin の二分は流していない）:

- 間の bin（40662a570 の 22cf3181 と 2649911d4 の 36667823）の lattice の差は history.rs、residual.rs、main.rs の摂動の解の `h.micro`
  （分岐と履歴の経路）と format のテーブルで、自己遮蔽（shielding.rs、ufg/）と燃焼の経路に変更はない（`git diff 40662a570 2649911d4`）
- この入力は 2026-10-23 の後に流していない（dvc.lock の出力のログの時刻は 2026-10-22T17:46Z）。その間に ADR-0213（自由ガスの
  散乱源の区間を、使用可能メモリ − 2 GiB の 8 割まで持つ）と ADR-0214（スレッドの数の既定を論理 CPU の 32 に）が入った

### 原因

ADR-0213 の量は持つ区間だけを数え、減速計算の作業の配列は残りの 2 割と 2 GiB に収まる前提だった。間引かない格子の 2A の 1 ステップ
（32 スレッドで 39 本の解くピン）では、作業の配列と量の和が機械のメモリを超える。測った値（試行は trials/0212/ の入力で、ログは
`RUST_LOG=info,xlc_lattice::shielding=debug`。ジョブは decision の区分の排他の Slurm のジョブで、時間は記録に使わない）:

| ジョブ | bin              | 入力                  | 自己遮蔽の量（`UFG held memory`） | 結果                                                                               |
| ------ | ---------------- | --------------------- | --------------------------------- | ---------------------------------------------------------------------------------- |
| 646    | main（36667823） | `ufg-hold-memory = 0` | 0                                 | 完了、MaxRSS 28,065,412K、k は 1.183079 と 1.145585                                |
| 647    | main（36667823） | 既定                  | 67,098,918,912 B                  | 自己遮蔽の始めから 39 秒で RSS 64.2 GB（毎秒の VmRSS）に増え続け、OOM の前に止めた |

持たないときの 28.1 GB と量 67.1 GB の和は 91 GiB（97.7 GB）を超え、644 の OOM と合う。

1 回の減速計算の作業の配列のうち、スイープの核種ごとの弾性散乱とリングごとの中性子束の列は、`vec![Vec::with_capacity(n); k]` で
作っていた。複製した Vec は確保を引き継がないので、列は空から倍に伸び、格子点の数の最大 2 倍を確保していた。

### 直し

ADR-0213 の「## 変更」（2026-11-03）: 1 回の減速計算の量（全体の量を同時に解きうる減速計算の数で分けたもの）に、その減速計算の作業の
配列（格子点の数に比例する配列。確保した大きさで数える）を含め、残りを持つ区間の上限にする（`ufg::cells_beside_work`）。スイープの
列は格子点の数で先に確保する（確保した大きさが最後の大きさになり、倍に伸ばす分が無くなる）。持つ区間の数は結果を変えない（ADR-0213 の
試験 `held_cells_give_the_sources_of_rebuilt_cells_bit_for_bit`）。

比べた案:

- 入力の側の対応（examples/depletion/lattice-2A.toml に `ufg-tolerance` か `ufg-hold-memory` を書く）: 採らない。既定は入力によらず
  機械のメモリに収まるべきで、入力で避けると、間引かない格子を同時に多く解くほかの入力（検証の高精度版、ピンの数の多い問題）で同じ
  ことが起きる
- 作業の配列を格子点の数とリングと核種の数の式で見積もる: 採らない。配列の確保した大きさを足せば、式を配列の変更に合わせ続けずに
  済む
- 列を作り直さず作業の配列を数えただけの版（57b583b17、Slurm 648）: 1 本の作業の配列を 0.12 GB と数えたが、手元の 1 本のピン
  （#0181 の pin-2A-1step-full.toml を `ufg-hold-memory = 0` にした入力、1 スレッド）で列を先に確保すると 1.09 GB で、列は倍に伸びる
  途中を数えていなかった。2A の 1 ステップは自己遮蔽の始めから 50 秒で RSS 86.4 GB に増え、止めた

直した版（ブランチ fix/0212-lattice-depletion-memory の 2bf0e9240、分岐点は main の b29e4a539、2026-11-03）で測った値:

| ジョブ | 入力                                                                             | 結果                                                                                                                                                                                                                                       |
| ------ | -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 652    | 間引かない 2A の 1 ステップ（既定の量）                                          | 完了、MaxRSS 72,523,368K（毎秒の VmRSS の最大 72,524,576 kB）。量は 3 回の自己遮蔽で 66.9、48.8、47.8 GB。1 本の作業の配列 623,139,224 B（格子点 944,917、核種 65）、持つ区間 21,496,073〜36,412,019。出力は 646 と `seconds` のほかで同じ |
| 653    | 間引いた 2A の 1 ステップ（../p2/lattice-2A.toml の燃焼度を 0.1 だけにしたもの） | main の bin と直した版の出力が `seconds` のほかで同じ。1 本の作業の配列 0.10 GB で、持つ区間（9,688,403〜9,692,586）は main と同じ。MaxRSS 20,185,188K（2 本を続けて流したジョブの全体）                                                   |

手元の 1 本のピン（上の入力、1 スレッド、時間は記録に使わない）の最大の常駐メモリは、列を先に確保して 3,245,344 kB（57b583b17）→ 2,604,856 kB（2bf0e9240 の fmt の前の作業ツリー）（GNU
time の `%M`）で、出力は `seconds` のほかで同じ。

examples/depletion/lattice-2A.toml に `ufg-tolerance` が無いのは、決めた形ではない: ADR-0185 は「燃焼の入力（examples/depletion）に
1e-4 を書くのは、燃焼の本番の前にそれぞれの入力で行う」とし、48d2b5c98 は集合体の燃焼の本番（p2_inputs.py が書く 8 本）に足し、
ピンセルの検証（lattice-1C-*.toml）を間引かない高精度版として残した。lattice-2A.toml（ADR-0173 の時間の内訳の入力）はどちらにも
挙がっていない。

## 完了の条件

- 間引かない格子の 2A の 1 ステップの、持った量と、持たないときの MaxRSS を測り、原因を確かめる（上の 646、647）
- 既定の量が作業の配列と足して機械のメモリを超えない形にし、間引かない格子の 2A の 1 ステップが流れる（上の 652）

## 経緯
